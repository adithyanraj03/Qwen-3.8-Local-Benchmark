1. Overview

The service maps a short, shareable URL (https://s.x/Ab3xK9qZtW41) to a long target URL. Two fundamentally different operations dominate:

  • Shorten (write): client submits a target URL, service mints a short code, persists the mapping. 50,000/s globally.
  • Redirect (read): any client on the internet hits /{code}; service resolves the code and emits a 302. 1,000,000/s globally. These requests are geographically scattered, mostly anonymous, and latency-sensitive (they sit on the user's critical path).

The design centers on three decisions:

  1. Redirects are served from cache-first, anywhere in the world. Short codes are globally unique and the mapping is immutable (write-once), so any region can serve any redirect without a consistency handshake.
  2. Writes are cheap and conflict-free by construction. Code generation has no two-writer problem (see §5), so multiple regions can mint codes simultaneously; only mutable fields (expiry, deletion, re-target) are routed to a single "home" region per row.
  3. Click analytics is a fire-and-forget side stream. A dropped analytics event must never block or fail a redirect.

The redirect hot path (the 1M/s operation) is strictly local within a region: CDN → L1 (in-process) → L2 (regional Redis) → L3 (regional Postgres). The only cross-region traffic is asynchronous: WAL-based replication, analytics aggregation, and archive streams.

2. Requirements

2.1 Functional

ID Requirement
F1 Create a short URL for a target URL (≤ 2,048 bytes, http/https only)
F2 Resolve /{code} with 302 (or 301 when created with permanent=true)
F3 Batch resolve (up to 100 codes → targets) without following redirects
F4 Vanity codes: creator may choose /{slug} if unreserved and not conflicting with a generated code
F5 Optional TTL; expired codes return 410 Gone
F6 Soft delete; deleted codes return 410
F7 Per-URL click stats (total, timeseries, country, UA class)
F8 Idempotent creation via Idempotency-Key (creator + key → same code)
F9 Rate limiting and per-creator quotas

2.2 Non-functional

ID Requirement Target
N1 Throughput 50k writes/s, 1M reads/s sustained, 2× headroom in steady state
N2 Redirect latency P50 ≤ 25 ms, P95 ≤ 60 ms, P99 ≤ 150 ms (global, including one WAN hop)
N3 Shorten latency P50 ≤ 15 ms, P99 ≤ 100 ms
N4 Availability (reads) 99.99 % (≤ 52.6 min downtime/yr)
N5 Availability (writes) 99.95 %
N6 Durability No loss of confirmed writes (RPO ≤ 5 s, sync in-region replica)
N7 Region RTO ≤ 5 min (reads), ≤ 10 min (writes)
N8 Analytics delivery ≥ 99.9 % of clicks visible in near-real-time counters within 60 s; lossy is acceptable
N9 Multi-region 3 regions active for reads; any 1 region can absorb 100 % of read traffic
N10 Scale-out Adding a region is a deploy, not a migration

2.3 Constraints and assumptions

  • Average target URL length: 384 bytes (design max 2,048).
  • Click traffic follows a Zipf-like distribution (α ≈ 1.2): a small head of codes absorbs the majority of reads. The top 1M codes are assumed to absorb ≥ 60 % of read traffic; the top 50M codes absorb ≥ 99 %. These are assumptions validated in Phase 0 load tests (§12) — if the distribution is flatter, the L1/Redis tiers are sized to absorb it (§6.3).
  • Clients accept 302; a Cache-Control: public, max-age=10 on 302 responses is allowed to be honored by browsers/CDNs only for 301/308 (permanent) codes; short-lived 302s are not browser-cached but are CDN-cacheable at the edge (see §7.4).
  • No PII stored beyond hashed IPs (see §10.5).

Latency budget (P99 target ≤ 150 ms end-to-end): edge hop ≤ 10 ms, L1 path ≤ 1 ms, L2 path ≈ 5–20 ms (intra-region), L3 path ≈ 10–40 ms (index-only PK lookup). The DB path is the exception (~2 % of traffic, §6.3), so the blended P99 is dominated by the L1/L2 paths.

3.4 Errors

Standard problem+json body: { "error": { "code": "target_too_long", "message": "..." } }. Error codes: invalid_target, target_too_long, vanity_taken, vanity_invalid, expired, deleted, not_found, idempotency_conflict, quota_exceeded, rate_limited, unauthorized, internal.

4. Data Model

4.1 urls table (system of record)

Sharded by short_code (hash → 32 shards). Write-once core row; mutable tail fields are versioned for last-writer-wins across regions (§8.3).

CREATE TABLE urls (
    short_code    char(12)      PRIMARY KEY,          -- base62, see §5
    target_url    text          NOT NULL,
    creator_id    bigint        NULL,                 -- NULL for anonymous creates
    created_at    timestamptz   NOT NULL,
    expires_at    timestamptz   NULL,
    permanent     boolean       NOT NULL DEFAULT false,
    deleted_at    timestamptz   NULL,
    version       bigint        NOT NULL DEFAULT 0,   -- LWW counter for mutable fields
    CONSTRAINT target_len CHECK (char_length(target_url) <= 2048)
);
-- Partitioned by RANGE (created_at), one partition per month.
-- Partitions older than 30 days are detached and archived to object storage (§6.1).
-- Per-shard unique index on short_code is sufficient: the shard key IS the code.
CREATE INDEX urls_creator_ix ON urls (creator_id, created_at DESC) WHERE creator_id IS NOT NULL;

Row size budget: 12 (code) + 384 (avg target) + 8 (creator) + 8+8+8+8 (timestamps/flags) + 4 (version) + ~40 (row/index overhead) ≈ 472 B → budgeted at 512 B/row.

Deliberately absent from this table: click counts. Clicks are 20× writes and are kept in the cache/stats path (Redis, ClickHouse) to avoid write amplification on the hot table.

4.2 Idempotency table

CREATE TABLE idempotency (
    creator_id      bigint      NOT NULL,
    idem_key        char(32)    NOT NULL,   -- sha256(key)
    body_hash       char(32)    NOT NULL,
    short_code      char(12)    NOT NULL,
    created_at      timestamptz NOT NULL,
    PRIMARY KEY (creator_id, idem_key)
);  -- same shard as urls (creator_id routes both), TTL 24 h

4.3 Cache value layout (Redis)

Key: u:{code} → value: target_url (raw bytes; permanent encoded as a 1-byte prefix 0x01/0x00, expiry not cached — expired codes simply miss and the DB path returns 410). TTL 86,400 s (30 d), never refreshed on read (L1/L2 are bounded and re-populate naturally).

4.4 Stats (not in the hot DB)

  • Live counters: Redis sc:{code}:{minute} (15-min windows, TTL 1 h), per-creator 24 h totals.
  • Durable aggregates: ClickHouse clicks_hourly / clicks_daily (§10.4).
  • /stats API reads ClickHouse (P99 ≤ 300 ms) with a Redis fast path for the trailing 15 min.

5. Short Code (ID) Generation

Requirements: globally unique, collision probability negligible at 50k/s minting, no (or minimal) cross-node coordination, code length practical for humans (≤ 12 chars), and vanity codes must never collide with generated codes.

Alphabet: base62 = 26 lowercase + 26 uppercase + 10 digits (visually distinct characters like 0/O, 1/l/I are kept for space; the code is not human-transcribed in practice and ambiguity only costs a mistyped link, not a collision).

Code-space sizes (M = 62^L):

L M = 62^L 30-day live codes N (4.32e9 × 30) p(collide on next insert) = N / M Expected collision rate at 50k/s
8 2.18 × 10¹⁴ 1.30 × 10¹¹ 5.9 × 10⁻⁴ ~30/s (infeasible)
10 8.39 × 10¹⁷ 1.30 × 10¹¹ 1.5 × 10⁻⁷ ~1/2 min
11 5.20 × 10¹⁹ 1.30 × 10¹¹ 2.5 × 10⁻⁹ ~1/2.2 h
12 3.23 × 10²¹ 1.30 × 10¹¹ 4.0 × 10⁻¹¹ ~1/5.8 d

(30-day live set N = 4.32e9/day × 30 = 1.30 × 10¹¹, assuming 30-day online retention, §6.1. p = N/M is the probability a fresh random code hits an existing live code; expected collisions/day = p × 50,000 × 86,400.)

5.1 Option A — Global counter (single INCR in one Redis)

  • How: one Redis node (dedicated, in the primary write region) serves INCR code:seq; encode value in base62, zero-pad to 11 chars. 50k/s on one key is trivial for Redis (single key, 100+ MB/s of keyspace, single-threaded ~1M ops/s).
  • Pros: strictly unique by construction, zero retries, ordered (11 chars), one-line implementation.
  • Cons: a global hot key — the only true single point in the write path; if that Redis is down or partitioned, all regions stop minting (mitigation: per-region counter fallback that burns a reserved "region prefix" range, degrading to 12-char codes); sequence leaks creation volume over time (minor); 11-char padding is only safe while seq < 62¹¹ ≈ 5.2 × 10¹⁹, i.e. at 50k/s that's ~3.3 years — need a migration plan (or start at 12 chars).

5.2 Option B — Segment allocator (batched DB ranges)

  • How: each node holds a locally-allocated range from a DB sequence table: UPDATE id_ranges SET next = next + 10000 WHERE shard = m (m = my worker id mod 32). Local dispense is a plain in-memory counter; no coordination at mint time.
  • Arithmetic: 50,000/s ÷ 10,000 per segment = 5 DB round-trips/s globally (~0.2/s per region) — steady-state DB load for ID generation is ~0.
  • Pros: no hot key, unique by construction (disjoint ranges), bounded waste on node crash ≤ 10,000 codes (gaps in an ordered space are harmless), fails over per-region independently, no clock dependence.
  • Cons: ordered sequence (same information leak as A); needs a small allocator service or careful node-startup protocol (claim range with node_id fence to avoid double-claim after crash); 11–12 chars.

5.3 Option C — Snowflake-style (timestamp + worker + sequence)

  • How: 64-bit ID = 41-bit ms-timestamp (~69 years) + 10-bit worker id (1,024 workers) + 12-bit sequence (4,096 IDs/ms/worker). Encode in base62 → ⌈log₆₂(2⁶³)⌉ = 11 chars (62¹¹ ≈ 5.2 × 10¹⁹ > 9.22 × 10¹⁸ = 2⁶³ − 1). Capacity: 4,096 × 1,024 = 4.19M IDs/ms = 4.19 × 10⁹ IDs/s ≈ 84,000× our 50k/s.
  • Pros: fully decentralized (no allocator service), 11 chars, per-worker state is tiny, ordered within a worker.
  • Cons: worker-id assignment must be unique and stable (service registry + lease; a duplicate worker id can produce a duplicate code — the unique index catches it, but then you retry); clock going backwards requires wait-or-steal (steal a fresh worker id, gap in sequence); needs disciplined NTP (PTP recommended); 10-bit worker space means ≤ 1,024 concurrent minting workers — fine, but a constraint to remember at scale-out.

5.4 Option D — Random 12-char + retry on unique violation (recommended for v1)

  • How: 12 random base62 chars (97.2 bits of entropy, CSPRNG). Insert with the per-shard unique index; on 23505 (duplicate key) re-roll (max 3 attempts, then 503 + alert — astronomically unlikely: §5 table, ~1/week).
  • Arithmetic: p per insert ≈ 4.0 × 10⁻¹¹ (12-char, 30-day live set) → expected collisions ≈ 4.0 × 10⁻¹¹ × 50,000/s ≈ 2.0 × 10⁻⁶/s ≈ 1 retry per ~5.8 days cluster-wide. Collision handling is a plain retry — no extra infrastructure.
  • Pros: zero coordination (no allocator, no worker ids, no clocks, no hot key), region-symmetric (any region can mint), no ordering information leaked, simplest ops story, and the unique index is the single source of truth so even a pathological distribution can't corrupt data.
  • Cons: 12 chars (1 longer than A/B/C — immaterial in practice); unbounded codespace means no "how many URLs exist" from the codes themselves (we track that anyway); vanity namespace must be disjoint (§5.5).

5.5 Vanity namespace

Vanity slugs (alphanumeric, 3–32 chars, no --) live in the same keyspace as generated codes (enforced by the same unique index — a taken slug returns 409). Generated codes are 12 chars; to guarantee a generated code never "accidentally" lands on a popular future slug, slugs shorter than 12 chars are simply reserved on claim, and the 12-char generated space avoids a small denylist (e.g., admin, api, health, www, r, plus any slug ≤ 3 chars which are reserved entirely for internal/system use). Because uniqueness is index-enforced, this is a UX consideration, not a correctness one.

5.6 Recommendation

Option D for v1 (random 12-char + index retry). It has the fewest moving parts, no global dependencies, and the collision arithmetic shows retries are a non-event at this scale. Keep Option B (segment allocator) as the documented upgrade path if we later want shorter/ordered codes (e.g., branded 10-char codes for premium customers) — the sharding by short_code and the cache layout are identical under either scheme.

6. Capacity Estimates

All arithmetic shown. Assumptions: 1 day = 86,400 s; 1 TB = 10¹² B; W = 50,000 writes/s; R = 1,000,000 reads/s.

6.1 Storage — urls

URLs/day            = W × 86,400 = 50,000 × 86,400        = 4.32 × 10⁹
Growth/day          = 4.32 × 10⁹ × 512 B                  = 2.21 × 10¹² B = 2.21 TB/day
30-day online set   = 4.32 × 10⁹ × 30                     = 1.30 × 10¹¹ rows
Online raw size     = 1.30 × 10¹¹ × 512 B                 = 66.4 TB
With index overhead (×1.5)                                = 99.6 TB
With 3 replicas (×3)                                      ≈ 299 TB per region
Per shard instance  = 299 TB ÷ 32 shards                  = 9.3 TB

Policy: 30 days online (Postgres, monthly partitions, DETACH + copy to object storage as compressed Parquet — ~10× compression on URL-heavy data ≈ 5 B/row → archive grows 4.32e9 × 5 B = 21.6 GB/day, ~7.9 TB/month, ~95 TB/year). Cache TTL (30 d) is aligned to online retention so a cache miss always resolves from the DB; a cold code older than 30 days that is not cached resolves via the archive lookup path (S3 range read against the partitioned code index, P99 ≈ 1 s) — acceptable for the long tail, since by definition such codes are low-traffic (the 99 % hot set is < 30 days old under the Zipf assumption, §2.3).

6.2 Database throughput

Writes per shard    = 50,000 ÷ 32                          = 1,563 txn/s
Reads per shard     = cache-miss reads ÷ 32
                      (miss budget: 20,000/s, §7)           = 625 queries/s
Peak headroom       = single Postgres shard ≈ 30,000 txn/s  →  ~13× on writes, ~40× on reads

Writes are single-row inserts with one index — the 13× headroom means a shard can absorb a cache-wide outage (1M reads/s ÷ 32 = 31k/s reads + 1.6k/s writes per shard) for short bursts; sustained outage is a degradation scenario, not steady state (§11).

6.3 Cache

Working set (assumption, §2.3): top 50M codes absorb ≥ 99 % of reads.

Memory per entry (Redis)   = key "u:"+12B + target 384 B + overhead ≈ 550 B
50M entries per region DS  = 50 × 10⁶ × 550 B              = 27.5 GB

Traffic split through the tiers (global 1,000,000 reads/s):

L1 (in-process LRU)        60 %  =   600,000/s absorbed (no network hop)
→ remaining                40 %  =   400,000/s to L2 (regional Redis)
L2 hit rate on remainder   95 %  =   380,000/s absorbed
→ DB cache misses          5 %   =    20,000/s globally

If the Zipf tail is flatter and L1 absorbs only 40 %: 600k/s hit L2; 3 % miss → 18k/s DB misses. If L1 absorbs only 20 % (very flat): 800k/s hit L2; 5 % miss → 40k/s. In all cases DB reads stay ≤ 40k/s = 1,250/s per shard — the DB is never the constraint; only Redis QPS grows (see below), and the L1 LRU size is the knob to turn (it is RAM on the redirect nodes, cheap to raise).

Redis QPS per region (3 regions sharing reads equally):

GET  = 400,000 ÷ 3          = 133,333/s
SET  = 50,000 ÷ 3           =  16,667/s   (write path primes cache; fire-and-forget)
Total                        = 150,000/s per region
Per shard (3 shards)         =  50,000/s  →  3× headroom vs ~150k ops/s per node

L1 sizing: 24 redirect nodes/region × 1M-entry LRU × 600 B/entry (code+target+struct) = 14.4 GB/region of L1 aggregate (overlapping sets; effective unique coverage ≈ 5–8M entries). 24 nodes × (600 MB LRU + ~1 GB runtime) → 16 GB nodes.

6.6 Cost-of-scale sanity check (back-of-envelope)

The dominant cost is DB storage: 3 regions × 299 TB ≈ 0.9 PB of online data. Every month of retention adds 2.21 TB/day ≈ 66 TB × 3 replicas × 1.5 index ≈ 299 TB per region — i.e., retention, not traffic, sets the storage bill. If economics force it, the first lever is online retention (30 d → 14 d cuts online storage 47 %; the archive path already covers older codes), the second is compressing target URLs with a dictionary for the long tail.

7. Caching Strategy

Three tiers, each sized in §6.3:

7.1 L1 — in-process LRU on redirect-svc

  • 1M entries, 600 B/entry, LRU eviction, no TTL (data is immutable; expiry is checked only on the DB path).
  • Populated on every L2/DB hit (write-through to L1 after the response is committed — the L1 populate is done before sending the 302 since the value is already in memory).
  • Cold start: no warmup needed (misses flow through L2); after ~10 min at full traffic the head codes are resident.
  • Correctness: L1 can hold a stale target only after a re-target (PATCH), which publishes a cache-invalidation event (rare: re-targets are < 0.01 % of writes); invalidations fan out via Kafka to all redirect nodes (at-least-once, idempotent LRU.del).

7.2 L2 — regional Redis

  • 3 shards per region (key = CRC16(code) mod 3), 2 replicas each (async replication, sentinel/managed failover; failover target ≤ 30 s).
  • u:{code} TTL 30 d, never refreshed on read. Writes prime it (SET fire-and-forget after DB commit — a lost SET just causes one extra DB read later).
  • GET is the only read op (no pipelines needed; the miss path is the exception, not the norm).
  • No cross-region Redis sync: Redis is a cache, rebuilt on demand. A new region starts cold; its miss rate decays to steady state within minutes (misses hit DB shards it already replicates, §8.3).

7.3 L3 — Postgres (sharded)

  • Serves the residual ~2 % of reads (§6.3) plus all of writes.
  • Per-shard SELECT target_url, permanent, deleted_at, expires_at WHERE short_code = ? — PK point lookup, index-only where possible.

7.4 Edge behavior

  • 301/308 (permanent) responses carry Cache-Control: public, max-age=300: the CDN can absorb viral permanent links entirely (a single hot 301 code at 1M/s becomes ~0 backend load after 5 s).
  • 302 responses carry Cache-Control: public, max-age=10 and are edge-cacheable at the CDN (custom edge rule) — this is the viral-302 protection: one code at 1M/s saturates to ≤ 100/s of origin fetches per edge PoP. 410 (expired/deleted) is edge-cached for 60 s to stop repeated misses.
  • HEAD and GET /r/{code} are not edge-cached.
  • Vary: none (response is code-scoped, no user dimension).

Degradation ladder (automatic, by admission control in redirect-svc):

  1. Healthy: L1 → L2 → L3 as above.
  2. Redis degraded: L1 + L3 directly (DB absorbs ≤ 40k/s, §6.3).
  3. DB shard lagging (replication lag > 5 s on the requested shard): serve from any healthy replica, emit X-Short-Stale: 1.
  4. DB unavailable for a shard: serve L1/L2 only; codes not in cache return 503 + Retry-After: 5 (availability-first: most users still get redirected).

8. Replication and Multi-Region Strategy

8.1 Topology

Three regions (us-east, eu-west, ap-southeast), each a full copy of the topology in §6.5. All regions serve reads. All regions serve writes for creation (no conflict by construction, §5.6); mutations (re-target, TTL change, delete) route to the row's home region.

8.2 Why reads are trivially multi-region

  • Short codes are globally unique (single namespace, index-enforced).
  • The core mapping is immutable; the only fields that mutate after create are target_url (re-target), expires_at, deleted_at, version — each changed < 0.01 % of the time.
  • A read in region X therefore needs only region X's local replica set; freshness cost is bounded by cross-region replication lag (~100–500 ms) and matters only for the rare mutation (a re-targeted URL takes ≤ 1 s to reflect globally).

8.3 Replication

Within region:

  • Postgres: primary + 2 synchronous streaming replicas per shard (RPO ≤ 5 s even on primary+replica dual failure is not claimed; dual-primary loss on one shard = write failover to another region's copy, RPO ≤ replication lag ≈ seconds).
  • Redis: primary + 2 replicas, managed failover ≤ 30 s (cache: no RPO requirement).
  • Kafka: RF = 3 across 3 AZ racks, min-ISR = 2.

Cross region (async, logical):

  • Postgres logical replication (WAL → logical decoder → apply on peer regions' shards), one writer per shard per region at a time. Lag target P95 ≤ 500 ms, alert at 5 s, "stale" routing flag at 30 s.
  • Single-writer-per-row rule: create is unique by code (no conflict); every UPDATE/DELETE is issued by exactly one region: home(code) = hash(short_code) mod 3. The API gateway forwards mutations to the home region (client sees one extra hop, P99 + 80 ms on a < 0.01 % operation). version is monotonically incremented on each mutation and applied LWW, so even an anomalous double-apply cannot resurrect a deleted row.
  • Kafka: no cross-region replication of clicks.raw — each region's analytics pipeline consumes its own traffic (see §10); raw events are also streamed to central object storage (region-scoped prefixes) for durable replay.
  • Redis: none (rebuilt from DB on miss).
  • Object storage (archive): async cross-region bucket replication, 11-nines durability.

8.4 Failure semantics

  • 1 region down: DNS/GSLB shifts all reads to the other 2 (each absorbs 50 % = 500k/s, 2× nominal — supported, §N9). Writes continue (creation is region-symmetric); mutations whose home was the dead region queue in the surviving regions' outbox and replay after recovery (order preserved by version; duplicates are LWW-idempotent).
  • 2 regions down: the survivor runs at 3× nominal on reads. L1 + Redis absorb the hot set; DB shards at ~31k/s each (briefly OK, §6.2); cold-miss codes return 503+Retry-After. Writes: creation still works (no cross-region dependency); mutations buffer.
  • Split-brain region (WAN partition, region alive but cut off): reads continue locally (stale ≤ partition duration — acceptable for a URL service; X-Short-Stale emitted when local lag estimator exceeds 10 s). Mutations: the partitioned region's mutations are versioned; on rejoin, LWW by (version, ts) — the rare re-target conflict is resolved to the higher version, logged + alerted.
  • New region bring-up (§N10): deploy services → subscribe logical replication (stream from current position; a full backfill of the 30-day set takes ~hours via parallel snapshot + WAL tail) → shadow-serve reads at 1 % → ramp to 33 %.

9. Abuse Prevention

9.1 Rate limiting and quotas

  • Per-IP and per-key token buckets (§3.5) at the edge (IP) and gateway (key), counters in Redis (10k keys/s of counter traffic is negligible next to 150k/s of URL lookups).
  • Per-creator hard quota (10M live codes) and soft daily create budget (100k/day); excess → 429/403 quota_exceeded.
  • Anonymous creates (public API tier) are capped at 100/day per IP and must carry a valid User-Agent + pass a proof-of-work micro-challenge (16-byte hash, ~5 ms client CPU).

9.2 Click-flood and bot control

  • Per-IP-per-code 20/s (§3.5): a single scraper hammering one viral code 1M times/s costs us cache reads, not DB reads — but it also poisons analytics, so excess clicks are rate-limited at the edge before the analytics emitter (dropped clicks are counted in clicks.rate_limited for honest stats).
  • Bot detection: ASN-based (datacenter/VPN ASNs flagged), HTTP/2 fingerprint heuristics, missing/inconsistent headers; flagged events are tagged is_bot (stored, not dropped) — customers can filter.
  • Redirect chain depth ≤ 2 in the resolution of vanity/system links; X-Short-Id header loop detection: if a client presents X-Short-Id: {code} while requesting /{code}, respond 421 (self-redirect loop) instead of recursing.

9.3 Target URL validation (write path)

  • Scheme http/https only; hostname resolves (DNS at write time, 250 ms budget, async retry if it times out — creation succeeds, resolution validated lazily); length ≤ 2,048 B.
  • SSRF guard: reject private/loopback/link-local/metadata ranges (10/8, 172.16/12, 192.168/16, 127/8, 169.254/16, fc00::/7, ::1, 169.254.169.254) as targets — shorteners are classic SSRF pivots.
  • Reject targets with unbalanced angle brackets/CR/LF (header injection if echoed).

9.4 DDoS

  • CDN edge absorbs volumetric floods (anycast + per-IP SYN/HTTP rate rules); origin sees post-WAF traffic only.
  • Per-code "hot key" DDoS (one code, 10M/s): edge caching of the 302/301 + per-IP-per-code limit bounds origin load to ~ (edge PoPs × 100/s) regardless of client volume.
  • A Sinkhole mode: ops can mark a code sunk (stored as a flag) → redirect-svc returns 410 from cache for it, cutting even cache traffic.

9.5 Vanity/namespace abuse

  • Slugs ≤ 3 chars reserved for system use; slugs in the premium denylist (go, on, t, s) require the premium tier; profanity filter (allowlist override); all claims are reversible (deleted slugs re-enter a 30-day cooldown before reuse, to avoid typo-squatting on recently deleted brands).

9.6 Idempotency and retry storms

  • Client retries of POST /v1/urls with Idempotency-Key return the original code (§4.2) — prevents duplicate-URL spam from flaky clients.
  • POST /v1/urls is also deduped on (creator_id, sha256(target_url)) for 24 h: the same creator shortening the same target twice gets the same code (documented behavior).

10. Analytics Pipeline

10.1 Design constraints

  • The redirect hot path must not depend on it: emission is fire-and-forget; worst case we drop events (metered), never slow a redirect > 1 µs.
  • ≥ 99.9 % delivery to near-real-time counters within 60 s (N8).
  • Volume: 1M events/s = 8.64e10/day (§6.4) — this is a stream system problem, not a DB problem. No click counter ever writes to Postgres.

10.5 Serving /stats

  • Trailing 15 min: Redis sc:{code}:{minute} (fast path, < 5 ms).
  • History: ClickHouse SELECT … FROM clicks_daily WHERE code = ? AND day BETWEEN … (PK on code), P99 ≤ 300 ms. Timeseries granularity 1 h/1 d/30 d.
  • Country/UA breakdown: top-20 precomputed per (code, day) in clicks_daily (denormalized countries_top, ua_top columns) — avoids scanning raw events per request.

10.6 Failure behavior

  • Kafka down: producer queue fills (10 s at 1M/s), then drops with clicks.dropped (target: < 0.1 % sustained); redirect path unaffected. Backfill: redirect-svc access logs (structured, 24 h retention) can re-emit a degraded event (no referrer/UA).
  • Flink lag > 5 min: alert; dashboards show "data as of T−lag". Batch compaction catches up from clicks.raw (72 h) or object storage (180 d) — the pipeline is re-runnable by design (idempotent upserts into ClickHouse keyed by (code, bucket)).
  • Redis stats down: /stats degrades to ClickHouse-only (P99 300 ms), no redirect impact.

12. Rollout Plan

Capacity target for load tests: 2× nominal = 100k writes/s, 2M reads/s (1 h soak), plus failure-injection runs.

Phase 0 — Foundations (weeks 1–4)

  • Services, schema, code generation (Option D), single-region topology, 4 DB shards (enough for test volume), Redis, Kafka, Flink, ClickHouse.
  • Load harness (scripted client fleet in 3 geo locations); Zipf calibration of the read mix against real reference traffic — gate: validate the §2.3 hot-set assumptions; if the distribution is flatter, re-size L1/Redis per §6.3 before proceeding.
  • Exit gate: 72 h soak at 2× single-region nominal (i.e., full global load on 1 region) with SLOs met; chaos runs: Redis failover, DB shard failover, Kafka kill — all pass with < 1 % error and no data loss.

Phase 1 — Single-region launch (weeks 5–6)

  • Production region A live, internal + partner API keys, 10 % of projected volume (5k writes/s, 100k reads/s).
  • Shadow analytics: dual-path (new pipeline vs. reference) reconciliation; ≥ 99.9 % event-count match before declaring the pipeline GA.
  • Exit gate: 2 weeks at SLOs (N2–N6), zero Sev-1/2, backup/restore drill passed.

Phase 2 — Multi-region reads (weeks 7–9)

  • Regions B and C: services deployed, DB shards backfilled (snapshot + WAL tail, §8.4), shadow-serve reads at 1 % → 10 % → 50 % of global traffic.
  • Validate: cross-region replication lag P95 ≤ 500 ms; cache-warmup time < 15 min per region; no hot-shard skew.
  • Exit gate: 1-week soak with GSLB region-kill drill (A down → B/C absorb 100 % reads for 24 h) within SLOs.

Phase 3 — Multi-region writes (weeks 10–11)

  • Enable creation writes in B and C (50/33/17 then even); enable mutation home-routing (outbox replay tested in staging with injected partitions).
  • 100 % of global traffic; enable CDN edge-caching of 302/301 responses (staged per PoP).
  • Exit gate: 72 h at 2× nominal with 1 region in maintenance mode (writes only); split-brain drill (partition B for 10 min, heal, LWW replay verified).

Phase 4 — Analytics + abuse GA, steady state (weeks 12+)

  • ClickHouse GA for /stats; customer exports; anomaly detection (per-code spikes, per-ASN floods) wired to alerting + auto-sinkhole.
  • Monthly game-days: region kill, AZ kill, shard failover, Kafka outage, clock-skew (if/when Option C is introduced), archive restore.
  • Quarterly capacity review against the §6 model; retention tuning (the storage lever, §6.6).

Rollback policy

Each phase has an explicit rollback: Phase 2 → GSLB weights to A-only (reads) in < 1 min; Phase 3 → writes flag per-region (feature-flag controlled, instant); Phase 4 → pipeline components are independently switchable (raw→Kafka on, Flink off = counters degrade to batch-only). Rollback triggers (automatic): p99 redirect > 150 ms for 5 min, error rate > 0.1 % for 5 min, cross-region lag > 10 s for 15 min, any confirmed data-loss signal (idempotency conflict rate spike, duplicate-key rate > 1/h).

13. Open Questions

  1. 301 default vs 302: 302 is the default (re-targets work, analytics stay clean); some customers want 301 as default for link-in-bio use. Config per API key — confirm product intent.
  2. Price of 12-char codes: Option D costs 1 char vs. the allocator options. If the premium tier demands ≤ 10-char codes, the segment allocator (Option B) ships as the premium path — both coexist (namespaces don't collide; length is a namespace).
  3. Edge caching of 302: honored by our CDN contract; verify browser/intermediate-proxy behavior on max-age=10 302s before Phase 3 staging (fallback: 1 s max-age).
  4. Vanity code search: is "is this slug available?" a public endpoint? (It's a fingerprinting/DoS vector; if yes, rate-limit hard and cache answers.)
  5. Multi-tenant SLO tiers: do premium keys get a dedicated shard/Redis pool? (Affects the §6.5 inventory by ~20 % if yes.)
