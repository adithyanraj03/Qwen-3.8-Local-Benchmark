1. Overview

A global URL-shortening service: it mints short codes for long URLs, serves HTTP redirects at very high read volume, records click analytics, and survives region failures. The read path (redirects) dominates: a 20:1 read/write ratio. The design optimizes the redirect path to be served almost entirely from caches close to users, and treats the write path and analytics as asynchronous, horizontally scalable subsystems.

Non-goals (v1): A/B testing per link, password-protected links, mobile deep linking / UTM templating beyond simple query passthrough, and a consumer web UI (API-first product; UI is a separate client).

2. Requirements

2.1 Functional

  • F1. Create a short link from a long URL; return a short code (6-8 chars, base62).
  • F2. Optional custom alias (/my-promo), reserved words rejected.
  • F3. Optional expiry (expires_at) and click cap (max_clicks).
  • F4. Redirect GET /{code} to the target URL (302 by default, 301 opt-in).
  • F5. Manage links: read metadata, update target/expiry, soft-delete.
  • F6. Per-link analytics: total clicks, unique visitors, geo/device/referrer breakdowns, time series.
  • F7. Multi-tenant API keys with per-tier quotas.
  • F8. Idempotent link creation (same Idempotency-Key returns the same code).

2.2 Non-functional

Redirect availability 99.99% monthly (~52 min budget)

3. High-Level Architecture

Three planes:

  1. Edge plane (every region): anycast L7 LB + WAF/rate limiter, a stateless Go redirect service with an in-process LRU, and a regional Redis cluster (L2 cache).
  2. Core plane: link service (write API, validation, ID allocation), link store (sharded wide-column DB, multi-DC), and the ID lease allocator (strongly consistent KV).
  3. Analytics plane: edge emits click events to Kafka; Flink jobs filter/enrich/ aggregate into ClickHouse (dashboards), S3 (raw lake), and Redis (live counters).

4. API Design

Base URL https://api.sh.rt (versioned, JSON, RFC 7807 errors, Idempotency-Key honored on POST). Auth: Authorization: Bearer <api-key> (OAuth client-credentials for partners). Standard X-RateLimit-* headers on every response.

4.1 Write/read management API

{
  "url": "https://example.com/a/very/long/path?utm=x",

4.2 Redirect hot path (separate host, no auth)

GET https://sh.rt/{code}
--> 302 Location: <target>            (or 301 if redirect_mode=301)
    Cache-Control: private, no-store  (302) / public, max-age=86400 (301)
    Via: sl-edge-iad-17               (debug hop)
404 -> tiny branded page + no-store   (negative cached 60 s)
410 -> "link expired"                 429 -> "slow down"

301 vs 302 trade-off: 301 lets browsers cache the redirect (cheaper for us, but we lose click counts and cannot revoke or edit a link). 302 keeps counting and revocability at the cost of a read per click. Default 302; 301 is an explicit per-link opt-in for "set and forget" links.

5. Data Model

Primary store: ScyllaDB (LSM, cheap writes, TTL, multi-DC). Relational alternative in §6 notes; the wide-column model is chosen for the 4.3 TB/day ingest (§11).

-- Hot path table, partition key = code (single-partition read, ~1 KB)
CREATE TABLE links (
    code         text PRIMARY KEY,          -- base62 short code
    url          text,
    account_id   uuid,
    status       text,                      -- pending_scan|active|quarantined|deleted
    redirect_mode text,                     -- 301|302
    max_clicks   int,
    clicks_seen  counter,                   -- approximate cap enforcement
    meta         map<text, text>,
    created_at   timestamp,
    updated_at   timestamp,                 -- LWW column for cross-DC merge
    expires_at   timestamp
) WITH default_time_to_live = 31536000      -- 1y backstop TTL; explicit expires_at wins
  AND compaction = {'class': 'TWCS'};

-- Dedupe index (only queried when dedupe=true): xxhash64(url) bucketed
CREATE TABLE url_dedupe (
    url_hash     bigint,                    -- xxhash64(url)
    url          text,                      -- full URL kept to resolve hash collisions
    code         text,
    PRIMARY KEY (url_hash, url)
);

-- Alias namespace (custom codes): same shape as links, written transactionally
-- via LWT insert-if-absent on code.

-- ID leases (strong store: etcd/FDB, not Scylla)
-- key: id/counter          value: {next: 812_000_000_000, block: 100_000}
-- key: id/worker/<host>    value: {lease_until: ts}   (only if snowflake variant used)

Analytics data lives in ClickHouse (see §10), not in the OLTP path. Click counters in Scylla are approximate (for max_clicks); ClickHouse is the source of truth.

6. ID Generation: Options and Trade-offs

Constraints: codes must be short (URL length is the product), unique globally, cheap to mint at 50k/s, and ideally not trivially enumerable by competitors.

Option How Length Coordination Dedupe Enumerable Failure mode Verdict
A. Batch-leased counter + base62 Allocator leases blocks of 100k IDs to API nodes; encode counter in base62 7 now, 8 later ~0.5 leases/s (trivial) No Yes (guessable neighbors) Allocator down -> nodes drain buffered leases, then fall back to B Primary
B. Random base62 + insert-if-absent (LWT) Uniform random 8 chars; LWT write; retry on collision 8 None No No Retry storm if space fills; LWT (Paxos) cost per write Fallback
C. Truncated hash of URL xxhash64(url) -> base62; collision list on exact-URL check 11 (64-bit) None Yes, free No Birthday collisions: at 780B live links, 48-bit space expects ~1e9 collisions, 64-bit ~16k -> must keep full URL + fallback rehash Optional, behind dedupe=true
D. Snowflake (ts + worker + seq) 41-bit ms + 10-bit worker + 12-bit seq -> base62 11 Worker registry (etcd) No Yes (time + volume leak) Clock skew -> dup risk; needs NTP discipline + epoch guard Rejected: too long
E. Encrypted counter (Hashids/HMAC of A) Format counter with secret so neighbors aren't guessable 7-8 Same as A No No Key rotation: old codes must stay decodable; key = prod secret Later, if enumeration becomes a real cost

Recommendation: A primary, B fallback, C behind a flag.

  • Space math: 62^7 = 3.52e12 codes. At 4.32B new links/day (§11), 7 chars exhausts in 3.52e12 / 4.32e9 ≈ 815 days (~2.2 years). Ship with 7-char codes from a reserved range, pre-allocate the 8-char range (62^8 = 2.18e14, ~140 years at this rate), and make the parser length-agnostic so no migration is needed.
  • Enumeration: codes are capability-URLs (anyone with the code sees the target); guessability matters little, but Option E is a drop-in later if scraping costs show up in cache-miss metrics.
  • Allocator HA: leases are 100k blocks held in API-node memory (10 blocks buffered = 1M IDs = 20 s of traffic at 50k/s per node); etcd quorum loss for > 20 s of fleet-wide drain triggers B. On recovery, the counter jumps forward (gaps are fine).

7. Redirect Hot Path

The redirect service is read-only, stateless, and aggressively cached. Single-flight (request coalescing) prevents thundering herd on cold keys: concurrent misses for the same code share one origin fetch.

sequenceDiagram
    autonumber
    participant U as User browser
    participant E as Edge (redirect svc)
    participant R as Redis (L2)
    participant O as Origin (link service)
    participant D as Scylla
    participant K as Kafka
    U->>E: GET https://sh.rt/aB3xZ9
    E->>E: rate limit (per-IP token bucket)
    alt L1 LRU hit (~60%)
        E-->>U: 302 Location: target
    else L1 miss
        E->>R: GET link:aB3xZ9
        alt L2 hit (~95% of remainder)
            R-->>E: record (or negative marker)
        else L2 miss -> origin (~10k/s)
            E->>O: GET /internal/links/aB3xZ9 (single-flight)
            O->>D: SELECT ... WHERE code = ?
            D-->>O: record
            O-->>E: record (fill L2, TTL 1h + jitter)
        end
        E-->>U: 302 + Via header
    end
    E--)K: click event {event_id, code, ts, geo, ua_hash} (fire-and-forget)

If Kafka is unreachable, the edge writes events to a local disk ring buffer (backpressure-safe, 24 h capacity) and a sidecar replays them. Redirects never block on analytics.

8. Caching

Tier What Hit target Notes
Browser 301 links only n/a max-age=86400; 302 is no-store
L1 in-proc LRU code -> record, 1M entries/node (~300 MB) ~60% Evicts on invalidate message
L2 Redis cluster code -> record, ~2B hot entries ~95% of L1 misses Keys: link:{code}; negative cache nil 60 s
L3 origin Scylla single-partition read 100% Sized for full miss storm (§11)
  • Invalidation: link service publishes invalidate {code} on Redis pub/sub and to edge nodes over a gossip channel; worst-case staleness = L2 TTL (1 h + jitter) if the message is lost. Deletes write a tombstone record so a stale cache entry revalidated against origin returns 410, not a resurrected redirect.
  • Hot key (viral link): L1 makes a hot key free after first hit per node; L2 shards by code so a single hot code lands on one shard -> replicate hot codes to a dedicated hot: keyspace mirrored on all L2 shards, and the edge load-balances reads across replicas.
  • Cache poisoning: responses vary only on path; Vary is not used; host header is validated against an allowlist so sh.rt.evil.com style tricks can't inject a Location into a shared cache.

9. Replication and Multi-Region Strategy

Topology: 5 regions (us-east, us-west, eu-central, ap-southeast, sa-east). Each region is a full cell: edge fleet, Redis, a Scylla DC, Kafka, and link service.

  • Writes: regional primary DC. A link is created in the user's nearest region and replicated asynchronously to the other DCs (Scylla DC/DC, per-column LWW on updated_at). Codes are immutable after creation and updates are rare, so LWW is safe; the only real conflict is concurrent edit-vs-edit, resolved by newest timestamp. Deletes are tombstones with the same rule.
  • Reads: served from the local DC, so a link created 200 ms ago may 404 in another region briefly. Mitigations: read-your-writes is guaranteed in the creating region; the API response carries the short URL so the creator never depends on cross-region propagation; cross-region miss rate is bounded by replication lag (p99 < 2 s).
  • Routing: anycast for sh.rt (redirects) so users hit the nearest edge; geo-DNS (TTL 30 s) for api.sh.rt.
  • Failover: health-checked DNS removes a region in < 60 s. Remaining regions are sized for N-1 (§11). A failed region's write traffic lands in the next nearest region; its ID leases are simply unused (gaps are harmless).
  • Why not strongly consistent global writes? 50k writes/s across regions with quorum consensus would add ~150-250 ms and couple regions' availability. The workload tolerates eventual consistency; we spend the consistency budget only on the ID allocator (etcd quorum inside one region, with a second region as failover).

10. Abuse Prevention and Safety

Vector Control
Write spam Token bucket at edge: anonymous 10 writes/min/IP; API tiers 50-1,000 writes/s. New accounts: 100 links/day until email/payment verified.
Read scraping 100 req/s/IP burst 200 on redirects; 429 + Retry-After. L1/L2 absorb floods; hot-key replication caps per-key cost.
Malicious targets Sync: exact-match blocklist + regex (known malware domains, URL-shortener loops). Async: Safe Browsing API, headless fetch of redirect chains (max 4 hops), screenshot + classifier. New links start pending_scan; links from trusted tenants activate immediately.
SSRF on preview fetch Fetcher resolves DNS first; rejects private/reserved ranges; no redirects followed inside the fetcher beyond the hop cap.
Open-redirect laundering Target must be http(s); no credentials in URL userinfo; no sh.rt self-targets.
Click fraud Dedupe by (code, ip_hash, ua_hash) in 10-min windows; known-bot UA/ASN lists; "valid clicks" metric for billing, raw clicks kept for forensics.
Quarantine flow active -> quarantined on scan verdict or user report; edge serves interstitial for quarantined codes; tombstone on confirmed abuse.
Tenant abuse Per-tenant kill switch (status=quarantined bulk), spend caps, anomaly alerts on write-rate per key.

12. Capacity Estimates (arithmetic shown)

All figures are sustained-peak; bursts (2x/30 min) are absorbed by 50% headroom.

12.1 Volume

Writes:  50,000/s * 86,400 s/day            = 4.32B new links/day
                                          ~= 1.58T links/year
Reads:   1,000,000/s * 86,400 s/day          = 86.4B redirects/day

12.2 Storage

Record size: code 8B + url 250B + meta 150B + index/LSM overhead ~2x  ~= 1 KB
Ingest:      50,000/s * 1 KB = 50 MB/s = 4.3 TB/day = 1.58 PB/year (pre-TTL)
Live set:    median TTL 180 days -> 4.3 TB/day * 180            ~= 780 TB
With RF3:    780 TB * 3                                          ~= 2.3 PB
Per shard:   64 shards -> 780/64 ~= 12 TB logical, ~36 TB disk;
             ingest 4.3 TB/day * 3 / 64 ~= 200 GB/day/shard (~2.3 MB/s) -- trivial for LSM

64 shards chosen for size, not write throughput (16 nodes could take the writes; 36 TB/shard keeps repair and bootstrap times sane).

12.3 Read path

Bandwidth: 1M/s * ~600 B response ~= 600 MB/s ~= 4.8 Gbps (+TLS overhead ~5.5 Gbps)
Absorption: L1+browser ~60%, L2 95% of remainder
  -> L2 load:    400k/s * ...  ~= 200k ops/s to Redis
  -> origin load: 200k * 5%    = 10k reads/s
Redis: 200k/s / ~60k/s per node (network-bound) ~= 4 primaries -> 8 nodes + 8 replicas
Redis memory: hot set ~2B entries * 200 B ~= 400 GB -> 8 x 64 GB shards + replicas
Origin: 10k reads + 50k writes = 60k ops/s / 64 shards ~= ~1k ops/s/shard (easy)

12.4 Edge fleet

Node capacity: ~25k rps (Go, keep-alive, TLS terminated at LB)
Need: 1M / 25k = 40 nodes; +50% headroom = 60; N-1 region loss => size per region
  for 1M/4 = 250k/s -> 10 nodes minimum per region.
Deploy: 5 regions x 20 nodes = 100 edge nodes (each region 500k/s capacity;
  losing one region still leaves 2M/s > 1M/s).

12.5 ID allocator

Lease rate: 50k/s / 100k per lease = 0.5 leases/s (etcd handles this idle-fast)
Buffer: 10 blocks/node * 12 link-service nodes/region = 12M IDs/region
        = 240 s of fleet-wide drain before fallback B engages

12.6 Analytics

Events: 1M/s * 300 B = 300 MB/s; LZ4 ~3:1 -> 100 MB/s; RF3 -> 300 MB/s network
Kafka: 12 brokers (4 per AZ x 3) -> 25 MB/s/broker sustained (well under ~150 MB/s)
Retention 3d: 100 MB/s * 86,400 * 3 ~= 26 TB logical, ~78 TB on disk (RF3)
ClickHouse: ~70% valid clicks -> 700k/s * ~120 B columnar ~= 84 MB/s ~= 7.3 TB/day
  raw 30d ~= 219 TB; 1-min rollups 13 months ~= single-digit TB
Flink: 1M events/s, keyed dedupe state ~24h -> ~20 TaskManagers

12.7 Cost order of magnitude

Storage ~2.3 PB NVMe (~$230k/mo at $0.10/GB-mo) + S3 lake (~$25k/mo) + ~350 VMs edge/DB/Kafka/Flink (~$250-400k/mo) => ~$0.5M/mo at full scale. The dominant costs are link storage and the edge fleet; both scale linearly and are the first targets for the cost-optimization phase (§14).

14. Rollout Plan

Phase Duration Scope Exit criteria
P0 Foundations 4 wk Single region, single AZ: link service, Scylla (4 shards), Redis, etcd allocator, redirect svc. No analytics. Functional tests green; 5k rps soak.
P1 MVP + shadow 6 wk Multi-AZ in us-east. Shadow-traffic 10% of a partner's reads. Basic click events to Kafka (raw sink only). Shadow diff < 0.01% wrong redirects; p99 < 100 ms at 200k rps.
P2 Load hardening 4 wk Load test at 2x targets (100k w/s, 2M r/s) with traffic generator from 3 continents. Hot-key and herd drills. L1/L2 tuning. 2x sustained 30 min, zero 5xx budget breach; runbooks for FMs 1-4.
P3 Analytics GA 6 wk Flink dedupe/enrich/aggregate, ClickHouse, live counters, stats API, bot filtering. Billing usage feed. Counters within 1% of S3-recomputed truth; dashboard lag p95 < 60 s.
P4 Multi-region reads 6 wk Stand up eu-central + ap-southeast cells; DC/DC replication; geo-DNS for API, anycast for redirects. Cross-region lag p99 < 2 s; region-drill failover < 5 min.
P5 Multi-region writes + abuse 6 wk Regional write DCs, safety scanning pipeline, quarantine flow, tiered quotas live. Abuse drill (simulated spam campaign) contained without human action.
P6 Scale + cost ongoing 64-shard topology, 8-char code range enabled, chaos game days, storage tiering (cold links -> S3-backed cache), Option E evaluation. Game day: kill a region + a Kafka broker + etcd leader simultaneously; SLOs hold.

Rollback posture: every phase ships behind flags; the redirect service is stateless (instant rollback); schema changes are expand-contract; DC/DC replication can be disabled per-DC; the ID allocator fallback (B) is exercised weekly in staging so it is never a cold path.

SLO monitoring from day one: redirect availability (synthetic probes from 25 cities), L1/L2/L3 hit rates, origin fan-in, DC/DC lag, lease age, Kafka buffer depth, per-key QPS top-N. Error budget policy: redirect path burns > 25% of the monthly budget in one incident -> feature freeze on the edge plane until RCA.

15. Open Questions

  1. Is 301-by-default worth offering for a "static" tier (saves ~30% of read volume but forfeits revocation)?
  2. TTL policy: 180-day median assumed for the live-set estimate; confirm with product whether anonymous (no-account) links should expire faster (they are ~40% of volume in comparable services, which would cut storage ~30%).
  3. Do we need per-link A/B or geo-targeted redirects in v2? That changes the record shape (target list instead of a single URL) and the cache key (adds geo bucket) -- worth deciding before P4 to avoid a second cache design.
  4. Legal: click-event retention (18 mo raw) vs GDPR erasure SLA -- may force keyed deletion in the S3 lake or a shorter raw window.
