1. Requirements

1.1 Functional

ID Requirement
F1 Create a short link from a long URL; return the short code
F2 Resolve a short code to the destination via HTTP redirect
F3 Support custom aliases (acme.io/go/launch) and auto-generated codes
F4 Support TTL / expiry (410 Gone after expiry)
F5 Idempotent creates: same long URL + owner → same code (dedup)
F6 Get link metadata + click stats; delete / soft-archive links
F7 Per-owner analytics: clicks over time, geo, referrer, device/UA class
F8 Webhooks on click (opt-in, sampled or full)

1.2 Non-functional

ID Requirement
N1 Throughput: 50,000 writes/s and 1,000,000 reads/s global, sustained (burst 2× for 5 min)
N2 Latency (redirect): p50 < 20 ms, p99 < 100 ms, p99.9 < 250 ms from nearest region
N3 Availability: reads 99.99% (≤ 4.3 min downtime/month), writes 99.9%
N4 Durability: no loss of committed writes (RPO = 0 within a region; ≤ 5 min cross-region)
N5 Data: serve 30 days hot, 180 days warm, 2 years archive; reads served from hot/warm
N6 Multi-region: reads served locally in ≥ 3 regions; writes accepted in any region
N7 Abuse: a single malicious owner must not degrade p99 for the rest of the fleet
N8 Analytics: no click event dropped from the stream under nominal load; detail retained 14 days, rollups 2 years

1.3 Workload assumptions (used for all arithmetic)

  • Read:write ratio ≈ 20:1 (1,000,000 / 50,000)
  • Clicks follow a heavy Zipf distribution: ~80% of reads hit the most popular ~10M codes
  • Average destination URL: 100 bytes; average row on disk ≈ 400 bytes (incl. index overhead)
  • 3 active regions, traffic split evenly (≈ 333,333 reads/s per region)
  • Average click event: ~200 bytes serialized; ~120 bytes compressed in the warehouse

2. API

Base: https://api.shrt.example/v1. All endpoints JSON. Auth: Authorization: Bearer <api-key> (keys are scoped: read, write, admin). Writes accept Idempotency-Key.

2.1 Create

POST /v1/urls
{
  "long_url": "https://example.com/very/long/path?x=1",
  "alias": "launch",            // optional; validated against owner's namespace
  "ttl_seconds": 86400,         // optional; default = never
  "owner_id": "acct_01H...",    // optional for self-owned API keys
  "tags": ["marketing", "q4"]
}
  • 201 Created → { "id": "abc1234", "short_url": "https://shrt.example/abc1234", "created_at_ms": 1761500000000, "dedup": false }
  • Same long_url + owner already exists → 200 with existing code, "dedup": true (F5)
  • 409 Conflict on alias taken; 422 invalid/expiring TTL; 429 with Retry-After

2.2 Read / update / delete

GET    /v1/urls/{code}                  → metadata + counters (30d clicks, last_clicked)
PATCH  /v1/urls/{code}                  → { "ttl_seconds": ..., "archived": true }
DELETE /v1/urls/{code}                  → soft delete; code retained 90 days, then re-usable
GET    /v1/urls/{code}/stats?window=24h → pre-aggregated rollups (not per-event)
POST   /v1/urls/{code}/webhooks         → opt into click webhooks

2.3 Redirect (public, no auth)

GET https://shrt.example/{code}
→ 307 Temporary Redirect, Location: <long_url>
  • 307 is the default (preserves method/body, lets us change destinations); 301 configurable per link for permanent moves
  • 404 unknown; 410 Gone expired; 451/429 when the link is rate-limited or quarantined
  • GET /{code}/info (JSON, for clients that must resolve without following)
  • Response headers: X-Click-Id (analytics correlation), standard Cache-Control: no-store

2.4 Rate limits

Scope Limit
Per API key, writes 1,000 req/s (token bucket in the cache tier)
Per API key, reads 10,000 req/s
Per source IP, redirect 200 req/s
Per code, redirect 5,000 req/s (above → 429 + quarantine flag)

3. Data Model

Storage: sharded transactional KV/SQL store (Postgres-compatible wire protocol, custom operator; 32 shards, sharded by code).

3.1 Tables

-- Primary record. Sharding key: code (uniform base62 → uniform shard distribution).
CREATE TABLE links (
  code            VARCHAR(8)  PRIMARY KEY,   -- base62, 7-8 chars
  long_url        VARCHAR(2048) NOT NULL,
  url_sha256      CHAR(64)     NOT NULL,     -- sha256(long_url), for dedup
  owner_id        VARCHAR(32)  NOT NULL,
  status          SMALLINT     NOT NULL,     -- 0 active, 1 archived, 2 soft-deleted, 3 quarantined
  created_at_ms   BIGINT       NOT NULL,
  expires_at_ms   BIGINT       NULL,
  redirect_type   SMALLINT     NOT NULL,     -- 307 / 301
  version         BIGINT       NOT NULL      -- optimistic concurrency for PATCH
);

-- Unique dedup index: (owner_id, url_sha256) → code.
-- Enforces F5: same owner + same long URL maps to exactly one live code.
CREATE UNIQUE INDEX links_dedup ON links (owner_id, url_sha256) WHERE status = 0;

-- Custom aliases are just links with code = alias (validated charset, owner-scoped check
-- against a per-namespace set stored in the cache tier, not a global index).

-- Low-cardinality rollups kept next to the row for /stats (updated async, never on the
-- redirect hot path). Authoritative analytics live in the warehouse (§8).
CREATE TABLE link_rollups (
  code        VARCHAR(8) PRIMARY KEY,
  clicks_24h  BIGINT NOT NULL,
  clicks_30d  BIGINT NOT NULL,
  last_click_ms BIGINT NULL,
  updated_at_ms BIGINT NOT NULL
);

-- Code allocator bookkeeping (single small Raft group; see §4).
CREATE TABLE code_blocks (
  block_id    BIGINT PRIMARY KEY,      -- monotonic
  node_id     VARCHAR(64) NOT NULL,
  range_lo    BIGINT NOT NULL,
  range_hi    BIGINT NOT NULL,
  granted_at_ms BIGINT NOT NULL
);

3.2 Storage tiers

Tier Content Engine Retention
Hot Last 30 days (≈ 52 TB raw, §9) NVMe-backed shard leaders + 2 followers each 30 days
Warm 30–180 days Object store (S3-class) + point-lookup index in the same KV (index-only rows) 180 days
Cold 180 days–2 years Object store, Parquet, queryable via warehouse 2 years

A redirect for a warm/cold code does an extra index lookup (~3 ms p99) and warms the cache on the way back. Expiry is evaluated at read time (expires_at_ms < now → 410), so no mass-delete jobs are needed; a nightly compactor reclaims soft-deleted codes after 90 days.

3.3 What is not in the OLTP store

Per-click events. Clicks are appended to the event stream (§8) and folded into link_rollups and the warehouse asynchronously. The redirect path performs one cache get and, on miss, one row get — nothing else.

4. ID Generation: Options and Trade-offs

4.1 The constraints (arithmetic first)

Annual volume:

50,000 writes/s × 86,400 s/day = 4.32e9 codes/day
4.32e9 × 365 days              = 1.58e12 codes/year

Code space sizes (base62, unreserved chars — no 0/O, 1/I):

62^7 = 3.52e12     → exhausted after 3.52e12 / 1.58e12 ≈ 2.2 years at our write rate
62^8 = 2.18e14     → ≈ 138 years

And the classic birthday-bound check for sampling (random or hash) codes from a space N, drawing n codes: expected collisions ≈ n² / 2N. For n = 1.58e12 codes/year:

N = 62^7 (3.52e12):  (1.58e12)² / (2 × 3.52e12) ≈ 3.5e11 collisions/year   ← hopeless
N = 62^8 (2.18e14):  (1.58e12)² / (2 × 2.18e14) ≈ 5.7e9 collisions/year    ← hopeless
N = 62^11 (5.2e19):  ≈ 2 collisions/year                                    ← finally safe

Conclusion: at 50k writes/s you cannot sample short codes and rely on the space to absorb collisions. Either (a) assign codes from bookkeeping so collisions are impossible by construction, (b) accept 11+ char codes for hash/random generation, or (c) coordinate per-shard/per-region sub-spaces.

4.2 Options

# Option Code length Coordination cost Collision behavior Failure behavior Verdict
A Central block allocator (chosen): a small global Raft group hands each writer node a block of 250k contiguous 8-char codes 7–8 chars 1 RPC per 250k writes → 50,000 / 250,000 = 0.2 allocs/s globally None by construction (assignment, not sampling) Allocator down: each writer keeps writing from its reserved block; 8 writers × 250k = 2M codes ≈ 40 s of autonomy at peak, then writes queue Recommended
B Pure random/base62, probe-and-insert 11+ chars (see §4.1) None (collision = rare read+retry) ~2/year at 11 chars; 3.5e11/year at 7 Stateless; nothing fails, codes just get long Good fallback, ugly codes
C Deterministic hash of long_url (truncated BLAKE3) 11+ chars to be safe (7 chars → ~3.5e11 collisions/yr, §4.1) None; idempotent for free (same URL → same code, no dedup index needed) Birthday-collision dominated; needs lookup anyway to resolve Stateless Great for a side-channel idempotency key, not the public ID: guessable (attacker who knows your URL can brute-force your code) and collision math forces length
D Snowflake (41-bit ms + 10-bit node + 12-bit seq) base62-encoded 12 chars None per-write; needs clock None by construction Clock step-back → wait or fail (monotonic-tilt needed) Solid, but longest codes; encodes creation time and node → leaks traffic shape and volume
E Per-region allocator with region-prefixed first char 8 chars (7 + region) Zero cross-region coordination; each region owns ⅓ of the space None within region; prefixes partition the space A region's allocator failure only stalls that region's writes Best when you want region-of-record; slight info leak (region in code), space per region = 7.3e13 ≈ 46 yr headroom, fine

4.3 Design decision

  • Primary: Option A. Allocator = 3-node Raft group (one member per region; quorum exists as long as any 2 regions are up, so a single-region outage does not stall global writes). Blocks are non-overlapping ranges → grant is commutative; grants are replicated to all members so failover loses at most the in-flight grant.
  • Codes are 8-char base62 (≈138 years of headroom, §4.1); a per-block permutation table (4-byte XOR-feistel on the low bits) is applied so codes within a block are not sequential — hides per-owner creation rate and approximate volume. Cost: one in-memory table per block, ~2 MB, discarded with the block.
  • Dedup (F5) uses Option C as a key, not an ID: sha256(long_url) is the dedup index (§3.1); a hit returns the existing code, no new ID is minted.
  • Custom aliases bypass the allocator entirely (owner-scoped uniqueness enforced via the namespace set in the cache tier + unique index on commit).
  • Expiry/retention: deleted codes are reusable after 90 days via the compactor (§3.2); re-use is safe because version and created_at_ms change, and the dedup index is status-scoped.

5. Caching

5.1 Topology

  • Read path is cache-first. Each region runs its own Redis Cluster (3 master shards × 1 replica, 16 GB each ≈ 48 GB usable per region). Cache is read-only from the store's perspective: populated by redirect misses (write-through of the fetched row) and invalidated by PATCH/DELETE via a per-region pub/sub channel. No cross-region cache of record — a write in region A invalidates region A immediately and regions B/C within ≤ 500 ms (pub/sub over the replication stream).
  • Why per-region and not shared: the redirect path must stay a single local memory get; a cross-region cache hop would break the p99 budget.

5.2 Working set and sizing (arithmetic)

Cacheable working set ≈ top 10M codes (Zipf: ~80% of reads land here)
Entry: 16 B key + ~200 B value + ~60 B overhead ≈ 280 B, call it 450 B w/ allocator overhead
10e6 × 450 B = 4.5 GB  →  ≈ 8 GB with fragmentation/headroom, per region

Provision 48 GB/region → room for the 10M hot set plus a 20M-entry overflow at reduced TTL.

5.3 TTL and behavior

Situation TTL
Normal hit 300 s
Hot keys (top 1%) 600 s, jittered ±20% (thundering-herd protection)
Expired link (410) negative cache 60 s (poison-URL defense, §10)
Quarantined code 30 s (fast re-check)
After invalidation event key deleted in origin region; others ≤ 500 ms
  • Single-flight: one miss per key per node in flight; concurrent misses coalesce (no cache stampede).
  • Cache hit rate target ≥ 90% (see §9: 1M rps → 100k/s to the store, not 1M).
  • Cache cluster failure: fail open to the store with per-shard read caps (store serves ~200k/s read headroom total) + serve the "top 100k codes" static snapshot for the hottest keys; shed analytics first, then cold reads. (§10, F1.)

5.4 Write-side caching

  • Token-bucket rate-limit state (§2.4) lives in the same Redis (different key space, NX + Lua).
  • Per-namespace alias sets live in Redis with a DB-authoritative rebuild job.

6. Replication and Multi-Region Strategy

6.1 Regions and roles

  • 3 symmetric regions (e.g., us-east, eu-west, ap-south). All serve reads. All accept writes (N6) during steady state.
  • Region of record (RoR): the region that accepted a write is the RoR for that code; its shard leader is the write authority for the row.
  • Read locality: GSLB (GeoDNS + anycast edge) pins clients to the nearest healthy region; reads never cross regions in steady state.

6.2 Replication

Path Mechanism RPO / lag
Within region, shard leader → 2 followers Synchronous (semi-sync: commit waits for 1 follower) RPO 0
RoR leader → followers in other regions Async logical replication via the store's log stream, ordered per shard ≤ 500 ms p99
Code allocator Raft (3 members, one per region); quorum = any 2 regions Blocks granted pre-outage survive the outage (§4.2)
Invalidation events Piggyback on the replication log (no separate bus) ≤ 500 ms p99
  • Conflict policy: version column + last-writer-wins on status transitions only; long_url is immutable after create except an explicit PATCH which bumps version. Two regions PATCHing the same row concurrently → the RoR's log entry wins; the other is applied only if its version is newer.
  • Split brain / network partition between regions: writes continue in the partition holding the shard leader (and ≥1 in-region follower). A partitioned minority region serves reads (eventually consistent, ≤ lag) and queues writes (durable local queue, ≤ 5 min) rather than writing to a stale follower — protects RPO=0. The allocator keeps granting from blocks already held by writers in the partitioned region.
  • Store topology per region: 32 shards × (1 leader + 2 followers) = 96 nodes; non-RoR regions run all shards in read-replica mode (they hold full copies for read locality and can be promoted if the RoR region is lost).
  • Disaster recovery: full-region loss → traffic shifts to the other 2 regions (each ~500k reads/s, within 2× burst capacity, §9); write authority for affected shards promotes the freshest follower; RPO = replication lag (≤ 500 ms), RTO < 5 min.

6.3 Data gravity

  • Analytics streams are regional (each region produces; one global consumer, §8).
  • Raw event archive lands in a single global object store (multi-region replication built in).

7. Abuse Prevention

Threats: spam/short-link farms, phishing relays, SSRF via short link, click-fraud for pay-per-click owners, DoS via code-guessing.

7.1 At create time (write path)

  1. Per-key and per-owner quotas (links/day, open codes, concurrent TTLs) — enforced in the cache tier, hard caps in the store at commit.
  2. Destination validation: resolve scheme (https/http only by default), block file://, gopher://, IPv6-mapped oddities; block private/link-local ranges (10/8, 172.16/12, 192.168/16, 169.254/16, ::1, fc00::/7) unless the owner has allow_private_dest; block the cloud IMDS IP 169.254.169.254 outright (SSRF).
  3. Reputation screen: destination domain against a daily-updated blocklist (phishing/brand abuse); new-owner first 1k links are "probation" — their codes are rate-limited to 500 redirects/hour automatically.
  4. Idempotency + dedup (§3.1) prevents farm-style re-creation storms.
  5. Honeypot + CAPTCHA on the web console (not the API): a hidden form field + timing heuristics; API keys from datacenter ASNs on the web console get challenged.

7.2 At redirect time (read path)

  1. Rate limits (§2.4) per IP and per code — the per-code limit is the key anti-fraud control: 5,000 rps on one code is abnormal at our scale.
  2. Click-velocity anomaly detection: Flink job (§8) computes per-code z-scores vs the owner's 7-day baseline; z > 8 for 2 consecutive minutes → status = quarantined (redirects still work but return 429 to non-browser UAs and get flagged), owner notified.
  3. Bot scoring: JA3/TLS fingerprint + ASN class (hosting ASN + headless-UA combination → challenged via X-Click-Id echo check).
  4. Poison destinations: if a code's destination 5xx-fails > 1% of the time, it's flagged for the owner and negative-cached for clients (§5.3).
  5. Quarantine is reversible and automatic: median-velocity recovery over 10 min clears it; persistent abuse → human queue.

7.3 Enforcement layers (defense in depth)

Edge rate limit (per IP, cheap)
  → cache-tier token bucket (per key/IP/code, authoritative for limits)
    → store commit-time hard caps (quotas, dedup)
      → async anomaly detection (quarantine, flags)
        → human abuse queue (suspend owner, purge namespace)

Every layer is independently testable; a failure of the async detector must never block legitimate traffic (detect-only, not gate).

8. Analytics Pipeline

8.1 Design goals

  • Never on the redirect critical path: the handler appends to a local in-memory buffer (64 KB ring) and moves on; flush is best-effort-with-retry.
  • 1M events/s sustained (one event per redirect, plus create/update events ≪ 50k/s).
  • Detail 14 days, rollups 2 years (N8).

8.3 Sizing (arithmetic)

Ingest:   1e6 events/s × 250 B (incl. Kafka framing) = 250 MB/s
Kafka:    100 partitions → 10k events/s, 2.5 MB/s per partition (well under per-partition limits)
          10 brokers, RF = 3 → internal replication traffic 250 MB/s × 3 = 750 MB/s
Flink:    25 slots × (2 jobs parallel) ≈ 50k events/s per slot — 20× headroom over need
Dedup state: active (client_fp, code) pairs in a 1 h window ≈ 10M × ~100 B ≈ 1 GB (RocksDB)
ClickHouse: 1e6 rows/s × ~120 B compressed ≈ 120 MB/s ≈ 10.4 TB/day
            14-day detail ≈ 146 TB on a 10-node cluster ≈ 14.6 TB/node + 2 replicas (provision 20)
            2-year rollups ≈ 365 × 2 × (24 × 60 × 3600 × 1e6 × 40 B rollup-compressed)
                           ≈ manageable single-digit TB/day; retained as Parquet in S3

8.4 Dedup semantics

"Unique visitors" is computed as distinct hash(client_fingerprint, code) per (code, day), where client_fingerprint = stable browser ID if present, else IP+UA-class+ASN. This is approximate (cookie-less clients over-count) and documented as such; per-owner billing uses the same definition for fairness. Webhook fan-out (§2.2) consumes the deduped stream so fraud doesn't pay the owner twice.

8.5 Failure behavior

  • Kafka down: local buffers retry with backoff (max 60 s retention → under sustained outage we sample to 10% rather than lose the pipeline; sampling flag recorded per batch). Redirects are unaffected (buffer overflow drops the event, never the redirect).
  • Flink checkpoint loss: at-least-once delivery into ClickHouse with ReplacingMergeTree on event ID (idempotent upsert) → no double counting.
  • Exactly-once for rollups is achieved by (a) idempotent upserts and (b) rollup windows computed from archived raw Parquet as a nightly reconciliation job (self-healing).

9. Capacity Estimates

All arithmetic shown. Assumptions from §1.3.

9.1 Storage

Writes/day:    50,000/s × 86,400 s = 4.32e9 rows/day
Writes/year:   4.32e9 × 365        = 1.58e12 rows/year

Hot (30 days): 4.32e9 rows/day × 400 B/row = 1.728e12 B/day ≈ 1.73 TB/day
               30 × 1.73 TB ≈ 52 TB raw
Per shard:     52 TB / 32 shards ≈ 1.6 TB per leader (≈ 4.8 TB with 2 followers)

Warm (30–180 d): 150 × 1.73 TB ≈ 260 TB in object store (index-only rows + archived rows)

9.2 Read path

Global reads:   1e6/s → per region (3 regions): 1e6 / 3 ≈ 333,333/s
Cache hit 90%:  misses = 1e6 × 0.10 = 100,000/s global
Per shard:      100,000 / 32 ≈ 3,125 lookups/s   (target ≤ 20k/s/shard → 6× headroom)

Cache memory:   10e6 entries × 450 B ≈ 4.5 GB ≈ 8 GB w/ headroom per region (§5.3)

App instances:  333,333 rps / 10k rps per instance ≈ 34 → provision 40 per region (×3 = 120)

Wire:           1e6 req/s × ~500 B (headers + TLS amortized, HTTP/2) = 500 MB/s
                ≈ 4 Gb/s global ≈ 1.3 Gb/s per region edge

9.3 Write path

Per shard writes: 50,000 / 32 ≈ 1,563/s (≤ 5k/s target → 3× headroom)
Writer instances: 50,000 / 8k/s per instance ≈ 6.25 → 10 (5 per write region, 2 regions)
Allocator load:   50,000 / 250k per block = 0.2 block grants/s (§4.2)
Write wire:       50,000 × ~300 B = 15 MB/s — negligible

9.4 Datastores and streams

Store nodes:  32 shards × (1 leader + 2 followers) = 96 per RoR region
Kafka:        10 brokers, 100 partitions, RF=3; 250 MB/s ingest (§8.3)
Flink:        1 session cluster, 50 slots, 3 jobs
ClickHouse:   10 shards × 2 replicas = 20 nodes, ~15 TB/node detail working set
Object store: raw archive 10.4 TB/day + warm links 260 TB (growing) ≈ 45 TB/month

9.5 Burst check (2× for 5 min)

2e6 reads/s: cache absorbs the delta only if working set is cached (it is, §5.3);
store sees 200k/s → 6,250/s/shard, still < 20k/s target.
2× writes:   allocator 0.4/s; per-shard 3,125/s < 5k/s target.
Buffers:     5 min at 2× on Kafka down: 2e6 × 300 s × 250 B = 150 TB — impossible,
hence the 10% sampling fallback (§8.5) keeps worst case ≈ 15 TB across regional buffers+Kafka.

10. Failure Modes

F6 Poisoned destination (target site down / 5xx) Client sees failures "caused by us" Negative cache 60 s on 410; 5xx tracking flags the code; Retry-After hints Short window of passed-through errors
F7 Kafka down Analytics loss Buffer 60 s → 10% sampling; redirects unaffected (§8.5) ≤ 10% of clicks sampled during outage

F11 Bad deploy (regression in redirect path) Elevated 5xx / p99 globally Canary 1% → 10% → 50% with SLO-gated auto-promotion; instant rollback (stateless apps, version-pinned cache values) ≤ minutes of partial exposure
F12 Clock skew (any time-derived logic, e.g., Snowflake fallback) Duplicate/rollback sequence IDs Primary scheme (blocks) is clock-free; fallback uses wait-forward with per-node sequence hold Only affects fallback mode

Game days (monthly): kill a region (F3), kill a cache cluster (F1), partition regions (F5), fail the allocator (F4). Each has a written runbook and measured RTO.

11. Rollout Plan

11.0 Gates

Every phase must pass: SLO dashboard green for 48 h, chaos runbook for that phase's failure modes executed, on-call handoff complete, rollback tested.

Phase 0 — Single region, internal (weeks 1–4)

  • 1 region; 10 shards (re-shard to 32 at Phase 1 via code-hash migration — codes are content-addressed so re-sharding is a data move, not an ID change); 1 allocator (3-node Raft in one zone cluster)
  • Internal dogfood team only; 1% of target load (500 writes/s, 10k reads/s)
  • Analytics pipeline live end-to-end at 1% volume; verify dedup + rollup reconciliation against ground truth
  • Exit: p99 redirect < 100 ms at 10% scale; zero data-loss in 48 h of chaos (leader kills, cache kills)

Phase 1 — Single region at full load (weeks 5–8)

  • Scale to 32 shards, full 50k/1M load via traffic-mirrored + real external beta (2 public partners)
  • Abuse stack active in detection-only mode (no auto-quarantine yet); calibrate thresholds against real traffic
  • Exit: 7 days SLO-green at full load; abuse false-positive rate < 0.1% of owners

Phase 2 — Multi-region reads (weeks 9–12)

  • Stand up regions B and C as read replicas (full shard copies, read-only mode, §6.2)
  • Flip GSLB: reads served locally in all 3 regions; writes still single-region (RoR = region A)
  • Replication lag p99 ≤ 500 ms verified; invalidation lag ≤ 500 ms verified
  • Chaos: full-region-kill drill with reads shifting to 2 regions (§9.5 burst check)
  • Exit: 7 days green; region-kill drill RTO < 5 min

Phase 3 — Multi-region writes (weeks 13–16)

  • Enable write acceptance in regions B and C: allocator Raft members join B/C (quorum across any 2 regions)
  • Canary: 1% of writes → region B, 10% → C, 50/50/50, gated on conflict-free log replay (zero version-conflict anomalies)
  • Enable auto-quarantine (abuse stack moves from detection to enforcement)
  • Exit: 2 consecutive weekly game days passed; conflict rate = 0; per-region write RPO=0 verified by checksum audit

Phase 4 — GA + hardening (weeks 17–20)

  • Public launch (owned domain + custom aliases); webhooks GA
  • Analytics GA: owner console dashboards, billing-grade unique-click reports, 2-year rollup backfill from Parquet complete
  • Cost pass: warm-tier compaction verified (260 TB warm, §9.1), cache TTL optimization, app-tier right-sizing
  • Steady state: monthly game days, quarterly capacity re-estimate (write growth re-checks the 138-year code headroom and shard count)

Rollback

  • Phases 2→1 and 3→2 are flag flips (GSLB + write-enable flag) executable in < 10 min; no data is ever region-exclusive, so rollback loses no data (worst case: ≤ 500 ms replication lag reconciliation).
  • Full service rollback path: pinned previous app version + previous schema version (all migrations forward-compatible for 2 release cycles).
