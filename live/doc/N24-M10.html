Design Document: Global URL Shortener ("sho.rt")

Status: Draft v1 · Target scale: 50,000 writes/s, 1,000,000 reads/s, global

1. Requirements

1.1 Functional

# Requirement
F1 Create a short link from a long URL; returns a short code (≤ 8 chars, base62).
F2 Resolve GET /{code} → HTTP redirect to the long URL.
F3 Vanity codes (sho.rt/my-campaign) with reserved-name protection.
F4 Update / delete (tombstone) a link; expiry timestamps.
F5 Per-link click analytics (counts, geo, referrer, device) with near-real-time freshness.
F6 Abuse reporting and takedown workflow.
F7 Authenticated API with keys, quotas, and per-tenant grouping.

1.2 Non-functional (SLOs)

Metric Target
Redirect availability 99.99% (≈ 52 min downtime/yr)
Redirect latency p50 ≤ 30 ms, p99 ≤ 150 ms in-region; p99 ≤ 350 ms global
Create latency p99 ≤ 300 ms
Analytics freshness live counters < 5 s; dashboards < 60 s
Durability links durable (RPO ≈ 0 intra-region, ≤ 1 s cross-region)
Consistency redirect staleness ≤ 60 s after an update; read-your-writes for the creator
Privacy IPs hashed with rotating salt; GDPR deletion supported

1.3 Non-goals

  • Archiving target-page content.
  • Full edit history / versioning UI (we keep only a monotonic row version).
  • Custom domains in v1 (design leaves room: code space is per-domain).

2. API

2.1 Management API (JSON, versioned)

POST /v4/shorten
  Headers: Authorization: Bearer <key>, Idempotency-Key: <uuid>
  Body: {
    "longUrl":  "https://example.com/very/long/path",
    "expiresAt": "2027-01-01T00:00:00Z",      // optional
    "vanity":   "my-campaign",                // optional
    "group":    "team-42"                     // optional
  }
  201 -> {"code":"aB3xK9","shortUrl":"https://sho.rt/aB3xK9","createdAt":"..."}
  409 vanity taken · 422 invalid/blocked URL · 429 rate limited · 451 policy-blocked

GET    /v4/links/{code}                 -> link metadata
PATCH  /v4/links/{code}                 -> update target/expiry; bumps version, purges caches
DELETE /v4/links/{code}                 -> tombstone (kept 30 days, then GC)
GET    /v4/links?group=...&cursor=...   -> paginated list
GET    /v4/links/{code}/stats?window=1h|1d|7d
POST   /v4/report   {code, reason}      -> abuse report

Rate-limit responses carry Retry-After and X-RateLimit-* headers. Idempotency-Key makes retries safe during failovers (stored 24 h).

2.2 Redirect endpoint

GET /{code}
  302 Location: https://example.com/...
      Cache-Control: public, max-age=60     // lets CDN/edge cache the redirect
      Via: sho.rt;region=eu
  404 unknown · 410 expired/deleted · 451 blocked

301 vs 302: we use 302 + short CDN TTL. A permanent 301 is cached by browsers forever, which (a) undercounts clicks, (b) makes takedowns/updates ineffective. 60 s of edge cache gives most of the scale benefit while keeping control.

3. Data Model

CREATE TABLE links (
  code        VARCHAR(10) PRIMARY KEY,      -- base62 (or vanity); shard key = hash(code)
  long_url    TEXT        NOT NULL,
  owner_id    BIGINT,
  grp         BIGINT,
  created_at  TIMESTAMPTZ NOT NULL DEFAULT now(),
  expires_at  TIMESTAMPTZ,
  status      SMALLINT    NOT NULL DEFAULT 0,  -- 0 active, 1 blocked, 2 deleted
  safety      SMALLINT    NOT NULL DEFAULT 0,  -- 0 unchecked, 1 clean, 2 suspicious, 3 malicious
  vanity      BOOLEAN     NOT NULL DEFAULT false,
  row_version BIGINT      NOT NULL             -- for cache invalidation / LWW
);
CREATE INDEX ON links (owner_id, created_at);
CREATE INDEX ON links (long_url_hash);          -- dedup lookup

CREATE TABLE tombstones (code PK, deleted_at);  -- 30-day anti-reissue
CREATE TABLE blocklist (url_hash PK, reason, added_at);
CREATE TABLE api_keys (key_hash PK, owner_id, plan, quotas);

Click events are not rows in the OLTP DB — they go to Kafka (§8).

Sharding: shard = hash(code) % 16. Point lookups by code are single-shard. Owner-scoped lists use a secondary index maintained by the DB layer (CockroachDB/Vitess). Vanity codes live in the same table; a reservation step prevents squatting reserved names.

4. ID Generation — Options and Trade-offs

Code space: base62 [0-9A-Za-z]. 62^6 = 5.7e10, 62^7 = 3.5e12, 62^8 = 2.2e14.

Option How Length Coordination Collisions Enumeration/leakage Dedup Verdict
A. Central counter + base62 auto-increment, encode 6–7 1 hot row; 50k/s contention none severe — rivals infer volume; sequential codes scrapable free No at this scale
B. Sharded counter (segment/lease allocator) each API node leases blocks of 10k from per-shard allocator; Feistel/XOR obfuscation of the counter before base62 7 trivial: 50k/s ÷ 10k = 5 leases/s none low after obfuscation (bijection hides order) free Chosen
C. Random 64-bit + base62 CSPRNG, check uniqueness on insert 11 none birthday: expected collisions ≈ n²/2⁶⁵; at n = 1e11 links ≈ 271 collisions → retry loop mandatory none no Wasteful length; retries at write peak
D. UUIDv4 122 random bits 22 none negligible none no Codes far too long
E. Snowflake (41b ts + 10b worker + 12b seq) local, clock-based 11 (2⁶³ ≈ 9.2e18 needs 62¹¹) clock sync only none leaks creation time; sortable no Good, but 11 chars and clock-skew hazards
F. Truncated hash of URL (e.g., 40-bit SHA-256) deterministic 7 none ~1e11 links → n²/2⁴¹ ≈ 5e5 collisions → salt+retry none free dedup Collisions too frequent without retries

Decision: Option B. Per-shard segment allocator hands out monotonic blocks; each ID is passed through a keyed Feistel permutation over the 7-char domain before base62 encoding. Result: no coordination bottleneck (allocator sees ~5 QPS), zero collisions by construction, codes look random, and identical URLs dedup for free (lookup by long_url_hash first). Nodes buffer 2 segments each → survives allocator outage for ~40 min at average write rate. Vanity codes bypass the allocator but share the same keyspace with a reserved-name blocklist.

5. Caching

Read/write ratio = 1M:50k = 20:1, and clicks follow a Zipf distribution (top ~10% of links take ~90% of traffic) — caching is the load-bearing wall.

Tier Where Hit-rate target Notes
T0 Browser/CDN via Cache-Control: max-age=60 ~50% of all GETs 302 is cacheable; takedown staleness ≤ 60 s
T1 Edge KV (CDN edge compute) ~90% of requests that reach the edge code→URL map, 60 s TTL, purge on update
T2 In-process LRU per API node ~30% of origin hits 5M entries × 200 B ≈ 1 GB/node
T3 Redis cluster per region ~95% of remaining 500M hot entries × 250 B ≈ 125 GB → 6-node cluster
T4 Sharded OLTP DB last resort sized for cache-miss storm (§10)

Invalidation: PATCH/DELETE bumps row_version, deletes Redis keys via a pub/sub purge broadcast in every region, and issues CDN purge. Negative caching (404s cached 10 s) stops scraper hammering of random codes. Singleflight coalesces concurrent misses for the same code so a viral link triggers one DB read, not thousands.

6. Replication and Multi-Region

  • Per shard: 1 leader + 2 followers. Leader→follower is semi-sync (one intra-region ack before commit) → RPO ≈ 0 in-region. Automatic failover < 10 s (lease-based, e.g., CockroachDB/Raft or Vitess+Orchestrator).
  • Cross-region: async replication, lag typically 100–300 ms. Redirect reads are served from the nearest region and tolerate ≤ ~1 s staleness — a stale redirect is harmless; a stale takedown is covered by the blocklist, which is replicated synchronously to all regions (small dataset, correctness-critical).
  • Writes: routed to the shard leader. ~5% of traffic may cross a region for +100–200 ms — acceptable inside the 300 ms create SLO. (Alternative considered: geo-partition leaders by owner region; deferred to Phase 4.)
  • Traffic steering: anycast DNS + health-checked LBs; each region is sized to absorb 60% of global peak alone (N+2 posture: lose one region, two absorb).
  • Conflict policy: link edits = last-writer-wins on row_version; click counters are CRDT-style sums computed in analytics, never in the OLTP row.

7. Abuse Prevention

Layer Control
Create-time URL syntax + scheme allowlist (http/https); resolve redirect chains server-side and cap depth; sync check against blocklist (Bloom filter + exact set, ~10M URL hashes, replicated sync); reputation check for anonymous users
Create-time quota Anonymous: 5 creates/min/IP, no vanity. API keys: per-plan quotas (e.g., 10k creates/day). Burst token buckets at edge
Post-publish Async deep scan (Safe Browsing / VirusTotal / in-house classifier) within minutes; safety=3 flips status to blocked and purges caches globally; re-scan on target change and periodically for high-traffic links (targets can be repurposed after approval)
Read-time Per-IP and per-API-key rate limits; per-code read caps to blunt scrapers while allowing genuine viral spikes (hot-key allowlist); bot fingerprinting; negative caching of 404s
Governance POST /v4/report + registrar-style takedown SLA (malicious: 15 min auto + human review); hashed-URL blocklist so re-registered codes for the same payload stay blocked; law-enforcement contact flow
Vanity Reserved-name blocklist (admin, login, api, …); trademark claim process

 "ua":"...","referer":"...","country":"DE","device":"mobile","status":302,"region":"eu"}

flowchart LR
    API["link-api"] -->|"1M/s events"| K["Kafka click-events (256 partitions, RF3)"]
    K --> FL["Flink: dedup by eventId, geo/UA enrich, 1min/1h windows"]
    FL --> CH["ClickHouse: raw 30d + rollups forever"]
    FL --> RC["Redis live counters (CRDT sums)"]
    K --> ARC["Object storage archive (Parquet, 1yr)"]
    ARC --> BT["Batch: reprocessing, backfills, ML abuse signals"]
    BT --> CH
    CH --> DS["Stats API + dashboards"]
    RC --> DS
  • Delivery: at-least-once; Flink dedups by eventId (keyed state, 10-min TTL); ClickHouse raw table is a ReplacingMergeTree keyed by eventId → idempotent sinks give effectively-exactly-once counts.
  • Backpressure: API nodes write to a local ring buffer (spill to disk); if Kafka is down > 10 min, drop lowest-priority events (anonymous traffic) before dropping authenticated ones.
  • Retention: raw events 30 days in ClickHouse, 1 year Parquet in object storage, hourly rollups forever.

9. Capacity Estimates (arithmetic)

Assumptions: peak = 50k writes/s and 1M reads/s; average = 10–30% of peak (diurnal); seconds/year = 365×24×3600 = 31,536,000.

Link volume & storage - Avg creates = 5,000/s → 5,000 × 31.5M ≈ 1.6e11 links/year (160B). - Row ≈ 300 B (code 8 + URL 120 + metadata 60 + index overhead ~110). - Raw = 1.6e11 × 300 B ≈ 48 TB/year; ×3 replicas ≈ 144 TB/year. - 5-year horizon with 20% churn + cold-tiering of links with no clicks in 24 months → hot set ≈ 150–250 TB across 48 DB nodes (~5 TB/node). Comfortable.

ID space - 62⁷ = 3.5e12 ÷ 1.6e11/yr ≈ 22 years at 7 chars; auto-grow to 8 chars (62⁸ = 2.2e14 → ~1,400 years). Fine.

Read path - Peak 1M/s; edge absorbs 90% → 100k/s to regional APIs; Redis absorbs 95% → 5k/s DB reads. - Response ≈ 400 B → peak egress = 1M × 400 B = 400 MB/s ≈ 3.2 Gbps global; avg (300k/s) ≈ 1 Gbps.

Write path - 50k/s ÷ 16 shards = 3.1k writes/s/shard (+312 reads/s/shard) — trivial per node. - Allocator load = 50k ÷ 10k-block = 5 leases/s.

Compute - API node (16 vCPU): ~25k cache-hit redirects/s or ~3k creates/s. - Nodes needed at peak: reads 100k/25k = 4; writes 50k/3k ≈ 17; mixed + 2× headroom → 24 nodes across 3 regions (8/region).

Kafka - 1M/s × 150 B = 150 MB/s ≈ 1.2 Gbps ingest; broker egress with RF3 + consumers ≈ 900 MB/s → 10 Gbps NICs suffice on 5 brokers. - Retention 3 days: 150 MB/s × 259,200 s = 38.9 TB × RF3 ≈ 117 TB; ÷2.5 compression ≈ 47 TB.

ClickHouse - Ingest 1M/s → ~100k/s/node → 12 nodes. Raw 30 days: 150 MB/s × 2.6M s ≈ 389 TB raw ÷ 9 compression ≈ 43 TB ×2 replicas ≈ 86 TB.

Redis - Hot set 500M × 250 B = 125 GB/region → 6-node cluster (3 masters + 3 replicas), each ~40 GB.

10. Failure Modes

Failure Blast radius Mitigation / behavior
Redis cluster down DB sees up to 100k qps LRU + singleflight absorb ~30%; circuit breaker; extend edge TTL to 300 s (stale-while-revalidate); shed stats API; DB sized for 2× miss storm
Shard leader dies writes to 1/16 of keyspace Raft failover < 10 s; clients retry with Idempotency-Key → no duplicate links; reads served by followers
Cross-region link cut stale reads ≤ few s regions serve locally; blocklist sync queues and applies on partition heal; writes reroute to leader region or 202-queue
Kafka down analytics lag/drops local spill buffers (10 min), then priority-based drop; counts are eventually consistent; no user-facing impact
CDN outage all traffic to origins DNS failover to regional LBs; autoscale; origin sized for 60% of peak; edge KV is a different provider than CDN routing
Viral hot key cache-miss stampede singleflight, edge cache, per-key Redis replica, allowlist from rate limiter
Allocator down creates stall after buffers 2 buffered segments/node ≈ 40 min at avg rate; allocator itself is Raft-replicated
Code collision on insert one request unique-PK guard + retry with next counter (should be ~never with Option B)
Hot/skewed shard one shard slow consistent hashing + online split; monitor p99 per shard
Bad deploy global canary 1% → 10% → 100%, auto-rollback on error-rate/latency burn rate
DB corruption one shard nightly snapshots + PITR WAL; checksum backups; restore drill quarterly
Traffic flood / scrape edge rate limits, bot rules, negative caching; abuse traffic is the cheapest to shed (429)

Degradation ladder: stats API off → analytics sampling → longer cache TTLs → anonymous creates paused → authenticated creates queued. Redirects are the last thing to ever fail.

12. Key Decisions Summary

  1. 302 + 60 s CDN cache, not 301 — control beats permanence.
  2. Segment-leased counter + Feistel obfuscation + base62 — zero collisions, ~5 allocator QPS, non-enumerable codes.
  3. Four cache tiers with singleflight; DB sized only for the miss storm.
  4. 16 shards × (1 leader + 2 followers), semi-sync intra-region, async cross-region; blocklist is the only synchronously replicated dataset.
  5. Clicks are events, not rows — Kafka + Flink + ClickHouse, idempotent sinks.
  6. Region absorbs 60% of peak alone; redirects degrade last, everything else sheds first.
