1. Goals & requirements

1.1 Functional

ID Requirement
F1 Create a short code for any http(s) URL up to 4 KB, with optional custom alias, expiry, and owner (API key).
F2 GET /{code} returns an HTTP redirect (301/302/307 selectable) to the original URL.
F3 Update and revoke (soft-delete) existing codes; deleted codes return 410.
F4 Per-code click analytics: total clicks, unique visitors, referrer/country/device buckets, hourly resolution.
F5 Public safety API: report/flag a code; internal blocklist enforcement.
F6 Idempotent creation: re-submitting the same URL for the same owner returns the same code (dedupe).

1.2 Non-functional (the numbers this design is sized for)

ID Requirement Target
N1 Write throughput 50,000/s sustained peak, ~20,000/s average
N2 Read throughput 1,000,000/s sustained peak, ~500,000/s average
N3 Redirect latency p50 < 10 ms in-region, p99 < 100 ms global
N4 Create latency p99 < 250 ms
N5 Availability 99.99% redirect path (~52 min/yr), 99.9% create path
N6 Durability 99.999999999% (11 nines) for mappings; zero data loss on single-AZ loss
N7 Consistency Read-your-write for the creator (session); eventual (≤ 2 s) globally
N8 Data retention Mappings: indefinite; click events: 90 d raw, 5 y rollups
N9 Compliance GDPR (right to erasure of owner PII), data residency option per region

1.3 Explicit non-goals (v1)

  • Client-side JS interstitial pages (pure HTTP redirects only).
  • QR code generation, link-in-bio pages, A/B routing.
  • Strong cross-region read-after-write for other readers (a reader in EU may see a code created in US up to ~2 s later).

2. System API

Base URL: https://api.snip.example (management) and https://snip.example/{code} (redirect).

2.1 Create short link

POST /v1/shorten
Authorization: Bearer <api-key>
Idempotency-Key: <uuid>            # optional, echoed back
Content-Type: application/json

{
  "url": "https://example.com/very/long/path?utm=...",
  "custom_code": "spring26",        // optional, 3-32 chars, [0-9A-Za-z_-]
  "ttl_seconds": 31536000,          // optional; absent = never expires
  "redirect_mode": "302",           // 301 | 302 | 307 (default 302)
  "metadata": {"campaign": "spring26"}
}

Response 201 Created (or 200 OK if deduped/idempotent replay):

{
  "code": "x7Kp2Qa",
  "short_url": "https://snip.example/x7Kp2Qa",
  "url": "https://example.com/very/long/path?utm=...",
  "created_at": "2026-11-13T09:00:00Z",
  "expires_at": "2027-11-13T09:00:00Z"
}

Errors: 400 invalid URL, 403 blocklisted destination, 409 custom code taken, 429 rate limited (Retry-After), 5xx with Retry-After on overload.

2.2 Redirect (hot path)

GET https://snip.example/{code}
  • 302 Found (+ Location, Cache-Control: public, max-age=60, stale-while-revalidate=300, Vary: Accept-Language only if geo-routing is on).
  • 301/307 when the mapping requests it.
  • 404 unknown code (cached negatively for 60 s), 410 revoked, 302 → /expired for expired.
  • Click is recorded asynchronously (fire-and-forget to a local queue); the redirect never blocks on analytics.

2.3 Management & stats

GET    /v1/urls/{code}                 # mapping details (owner-scoped)
PATCH  /v1/urls/{code}                 # update target URL, TTL, status
DELETE /v1/urls/{code}                 # soft delete → 410
GET    /v1/urls/{code}/stats?from=..&to=..&granularity=hour
GET    /v1/urls?cursor=..&limit=100    # list owner's links
POST   /v1/urls/{code}/report          # abuse report {reason}

2.4 Conventions

  • Rate-limit headers on every response: X-RateLimit-Limit/Remaining/Reset.
  • All timestamps RFC 3339 UTC. All errors RFC 7807 (application/problem+json).
  • Redirect path is auth-free and cookie-free (no cookies ⇒ CDN-friendly, no PII on the hot path).

3.2 OLTP schema (MySQL 8, 16 shards)

CREATE TABLE urls (
  short_code    VARBINARY(16) PRIMARY KEY,
  url_hash      BINARY(16) GENERATED ALWAYS AS (LEFT(SHA2(original_url,256),16)) STORED,
  original_url  VARCHAR(4096) NOT NULL,
  owner_id      BINARY(16) NULL,
  redirect_mode TINYINT NOT NULL DEFAULT 302,
  status        ENUM('active','revoked','expired') NOT NULL DEFAULT 'active',
  dest_domain   VARCHAR(255) NOT NULL,
  created_at    TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
  expires_at    TIMESTAMP NULL,
  UNIQUE KEY uk_owner_hash (owner_id, url_hash),   -- dedupe within owner
  KEY ix_hash (url_hash)                            -- global dedupe lookup
) ENGINE=InnoDB;   -- shard key: KEY(short_code) via consistent hash
  • url_hash unique index gives F6 dedupe: insert-or-select on (url_hash).
  • Clicks are not written to OLTP; they flow through Kafka (section 9). URL_ROLLUP lives in ClickHouse, not MySQL.
  • Sharding by short_code (not by owner) because the hot read path is code → row.

3.3 What is not stored

  • No per-click rows in OLTP (would add ~1M writes/s there).
  • No HTML bodies; only the redirect target.
  • IP addresses are hashed (salted daily) before analytics storage ⇒ GDPR-light.

4. Short-ID generation: options & trade-offs

Target alphabet: base62 (0-9A-Za-z). Code length ≤ 11.

4.1 Candidate schemes

# Scheme How Coordination Ordering Collision handling Cache locality Dedupe Enumerable?
A Central counter + base62 Redis/DB INCR, encode Yes (hot single point or segment lease) Strict None Terrible (sequential ⇒ B-tree right-edge hotspot, predictable) n/a Trivially
B Random ID + check CSPRNG → base62, retry on collision None (optimistic) None Retry loop (read-before-write or unique index) Good (uniform) n/a No
C Snowflake-style 41-bit ms timestamp + 10-bit worker + 12-bit seq → base62 (11 chars) Per-worker only (worker-ID registry) Roughly monotonic None by construction Medium (time-bucketed) n/a Partially (time-ordered)
D Pre-generated ticket pool Workers lease blocks of IDs from a segment service Batched (lease every N) Strict within block None Terrible n/a Trivially
E Truncated hash of URL base62(sha256(url)[0:5..6 bytes]) + probe on collision None None Open-addressing probe (counter suffix) Good Built-in No

4.2 Collision arithmetic (why "random 6-char" dies at this scale)

Space of an n-char base62 code: 62^n.

  • 6 chars: 62^6 ≈ 5.68e10. With N = 1e11 codes stored, collision probability per insert ≈ N / 62^6 ≈ 176% — impossible.
  • 7 chars: 62^7 ≈ 3.52e12 → 1e11 / 3.52e12 ≈ 2.8% per insert → ~2.8 retries average at year-1 scale. Unacceptable write amplification.
  • 8 chars: 62^8 ≈ 2.18e14 → 1e11 / 2.18e14 ≈ 0.046% → ~1.0005 attempts. Workable.
  • 11 chars: 62^11 ≈ 5.2e19 > 2^64 ≈ 1.84e19 → a full 64-bit ID always fits in 11 chars, collisions impossible by construction.

Conclusion: at 100B+ codes, random IDs need ≥ 8 chars; any 64-bit scheme fits in 11.

4.3 Decision

Primary: (C) Snowflake-style 64-bit → base62, 11 chars, with (E) URL-hash dedupe as a pre-step:

  1. Compute url_hash; if (owner_id, url_hash) exists → return existing code (F6, saves ~25% of writes — see §10).
  2. Else mint snowflake(worker_id) → base62 → insert.

Why C over the others:

  • No coordination on the write path (unlike A/D): each API pod owns a worker ID from a ZooKeeper/etcd-leased registry; 4,096 IDs/ms/pod = 4.1M/s per pod ceiling ≫ our 50k/s.
  • No collision retries (unlike B/E): deterministic uniqueness beats probabilistic at 50k writes/s.
  • Roughly time-ordered ⇒ inserts are append-ish on the shard B-trees; shard migration/TTL scans are cheap.
  • Clock skew guard: if wall clock < last issued, wait out the skew (≤ 2 ms typical) and alarm; never issue backwards (NTP + PTP, monotonic guard in the ID library).
  • Trade-off accepted: 11 chars is longer than a random 7-char code. Mitigation: custom aliases (F1) for users who care, and vanity tier.
  • Trade-off accepted: partial enumerability leaks creation order, not content; codes are not a security boundary (revocation is the control).

6. Caching strategy

6.1 Why caching is the whole ballgame

1M reads/s vs. a DB that comfortably serves ~30–50k origin reads/s total ⇒ we need ≥ 95% effective hit rate. Traffic is Zipf-ish: measurements from comparable services show the top ~2% of codes serve ~85–90% of reads.

6.2 Tiers

Tier Where Size (per §10) TTL Purpose
L0 Browser/CDN Cache-Control max-age=60, SWR=300 60 s Absorb bot/refresh storms
L1 In-process LRU (gateway RAM) ~50M entries/node 60 s + jitter Kill hot-key fan-out
L2 Distributed cache cluster/region ~5B entries 24 h + jitter Serve the working set
L3 MySQL replicas full data set — Source of truth

6.3 Rules

  • Negative caching: unknown codes cached as 404 for 60 s (bots hammer random codes; without this, every miss hits a shard).
  • Stampede control: single-flight request coalescing per code at L1 (only one miss fans to L2/DB); probabilistic early refresh at 90% of TTL.
  • Invalidation: updates/revokes publish to url-events; consumers delete L2 keys in all regions (≤ 2 s staleness, N7). L0 staleness is bounded by the 60 s TTL — acceptable for redirects; revocation additionally flips a status check that bypasses L0 via a short-lived bloom filter of revoked codes.
  • Warm-up: on shard failover or region spin-up, L2 is pre-warmed from CDC replay before the region takes reads.
  • Entry format: compact binary (code|url|mode|status|expires) ≈ 600 B average, not JSON.

7. Replication & multi-region strategy

7.1 Topology

  • 3 regions (e.g., us-east, eu-central, ap-southeast), active-active for reads, region-primary for writes per shard (each of the 16 shards has exactly one writable primary; primaries are spread across regions).
  • GeoDNS/anycast sends users to the nearest edge; the gateway routes writes to the shard's primary region (intra-shard consistency is single-writer ⇒ no conflict resolution on the hot path).
  • Cross-region replication: MySQL group-replication async channel / binlog shipping, target lag < 1 s (alarm at 5 s). Reads served from local replicas ⇒ ≤ 2 s staleness (N7).

7.2 Failure containment

  • Region down → DNS TTL 60 s + health-checked anycast drains traffic; remaining 2 regions absorb 1.5× (fleet sized for N+1 region, see §10.7).
  • Shard primary down → orchestrator (e.g., Orchestrator/Patroni-style) promotes a local replica with a fencing token from etcd; old primary is STONITH'd (read_only + token revoked) ⇒ no split-brain double-writes.
  • Cross-region link partition → writes queue at primary; replicas lag; on heal, catch up. Reads never block.

7.3 Data placement & residency

  • Default: global replication (a US-created link is readable everywhere).
  • Residency tier (opt-in): shard tagged region=eu; EU-only links are served from EU and 302'd from elsewhere to eu.snip.example.

8. Abuse prevention & safety

Vector Control
Write spam (link farms) Per-API-key token bucket (default 50 rps, burst 100); per-IP unauthenticated cap; proof-of-work/CAPTCHA challenge above soft limit
Read floods / scraping Edge rate limiter (Redis-synced token buckets, 10k rps/IP), WAF geo+ASN rules, TLS fingerprinting; 429 + Retry-After
Hot-key DoS (one code, 100k rps) L1 single-flight + L0 CDN caching; per-code circuit breaker that serves from cache-only mode
Malicious destinations Async scan on url-events (Safe Browsing API + internal classifier + VirusTotal); new links get status=probation (redirect with X-Robots-Tag: noindex, no CDN caching) until scanned; blocklist checked synchronously on create (bloom filter, < 1 ms)
Phishing via lookalikes Heuristics (punycode, homoglyphs, URL shortener-of-a-shortener) → flag + human queue
Enumeration scraping Codes are 11-char snowflake (not sequential); sequential prefixes leak only creation time; global per-IP read budget
Analytics poisoning visit_id = H(salt_day ‖ IP ‖ UA); bot UA list + JS-less heuristic marks suspect=1 (excluded from uniques, kept for raw audit)
Revoked-code resurrection Revoked codes are tombstoned forever (status, not row delete)

10. Capacity estimates (arithmetic shown)

Assumptions are stated; every number derives from them.

10.1 Write volume

Peak writes            = 50,000/s
Average (40% of peak)  = 20,000/s
URLs created / day     = 20,000 × 86,400            = 1.728e9  (~1.7B/day)
Dedupe saves 25%       → new rows/day               = 1.296e9  (~1.3B/day)
Row size: code 16B + hash 16B + url 500B(avg) + meta 100B ≈ 632B
With InnoDB/page overhead ≈ 1 KB/row
New data/day           = 1.3e9 × 1 KB                ≈ 1.3 TB/day
Year 1 raw             = 1.3 TB × 365                ≈ 475 TB
× 3 replicas           ≈ 1.43 PB
× 1.4 index/fragment.  ≈ 2.0 PB  (year-1 footprint)

Write bandwidth is trivial (50k/s × 1 KB = 50 MB/s); the constraint is operations/s, which drives sharding (§10.5).

10.2 Read volume & bandwidth

Peak reads             = 1,000,000/s
Redirect response      ≈ 500 B (headers + tiny body)
Peak egress            = 1e6 × 500 B = 500 MB/s ≈ 4 Gbps
+ TLS/overhead ×2.5    ≈ 10 Gbps total, split across 3 regions
Origin reads @ 97% hit = 3% × 1e6 = 30,000/s peak

10.3 Edge fleet

Sustained per node (Go + TLS resumption, 8 vCPU) ≈ 20,000 rps
Nodes = 1e6 / 2e4 = 50
× 1.5 headroom = 75 → round to 78 (26 per region)
Region-loss check: 1e6 / 52 nodes = 19.2k rps/node < 20k ✓ (N+1 region)

10.4 Cache fleet (L2)

Codes stored after yr 1 ≈ 1.3B/day × 365 ≈ 475B (say ~500B)
Zipf: top 2% ≈ 10B codes serve ~90% of reads; +24h working set ⇒ cache 5B entries
Entry ≈ 600 B → 5e9 × 600 B = 3 TB RAM
Per region: 3 TB / 3 regions... (each region caches its own traffic)
→ 1 TB/region = 8 × 128 GB nodes, RF=2 ⇒ 16 nodes/region
Hit-rate budget: L0+L1+L2 ≥ 97% (measured via gateway metrics; alarm < 95%)

10.5 Database shards

Sustained writes per shard (MySQL 8, NVMe, semi-sync ack) ≈ 4,000/s
Shards for peak writes = 50,000 / 4,000 = 12.5 → 16 shards (power of two)
Per-shard peak writes  = 50,000 / 16 ≈ 3,125/s  (78% of ceiling)
Origin reads per shard = 30,000 / 16 ≈ 1,875/s  → served by 2 replicas
Nodes = 16 shards × 3 (1 primary + 2 replicas) = 48 DB nodes
Per-shard year-1 data  = 2.0 PB / 16 ≈ 125 TB → fine for a single instance

10.6 Kafka & analytics

Clicks: 1e6/s × 150 B = 150 MB/s ; url-events: 50k/s × 200 B = 10 MB/s
Total raw = 160 MB/s ; snappy 3:1 → ~53 MB/s stored
7-day retention: 53 MB/s × 86,400 × 7 ≈ 32 TB × RF3 ≈ 96 TB
Brokers @ ~100 MB/s sustained each → 6 brokers (RF=3, min.insync=2)
Flink: ~10k events/s per core → 1e6/1e4 = 100 cores × 2 headroom = 200 vCPU
ClickHouse ingest: 1e6 rows/s → 12 nodes (3 shards × 2 replicas, batched inserts)
