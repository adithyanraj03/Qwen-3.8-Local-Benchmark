Typer Architecture

Typer builds CLI applications from plain Python functions and type hints. It is a thin, type-driven layer over a vendored copy of Click 8.3.1 (typer/_click/): user code declares what the CLI looks like via decorators and annotations; Typer translates that into Click objects lazily, and Click does the actual parsing, prompting, and invocation at runtime.

Request flow: decorated function → parsed command line

Take this program:

app = typer.Typer()

@app.command()
def main(name: Annotated[str, typer.Argument()], count: int = typer.Option(1)):
    print(f"{name} x{count}")

Phase 1 — declaration (import time, no Click objects yet)

  1. typer.Typer() — Typer.__init__ (main.py:164) stores app-level settings in a TyperInfo (main.py:556) and empty registries: registered_groups (main.py:574), registered_commands (main.py:575), registered_callback (main.py:576).
  2. @app.command() — Typer.command (main.py:783) returns a decorator that appends a CommandInfo (main.py:921-940) holding the function and metadata; the function itself is returned unchanged.
  3. Parameter metadata is just data on the function: typer.Option(1) is an OptionInfo instance used as the default value (params.py:948); Annotated[str, typer.Argument()] keeps an ArgumentInfo inside the annotation (params.py:145). Nothing is executed.

Phase 2 — translation (first call of the app)

  1. app() (or typer.run(), main.py:2045) → Typer.__call__ (main.py:1259) installs the pretty-exception sys.excepthook (main.py:63-111, installed at main.py:1260-1261) and calls get_command(self)(*args, **kwargs) (main.py:1263).
  2. get_command (main.py:1314) decides the shape: a callback, sub-groups, or more than one registered command produce a TyperGroup (main.py:1317-1324); exactly one command produces a single TyperCommand (main.py:1330-1348). If add_completion=True (default), the --install-completion/--show-completion parameters are appended to click_command.params (main.py:1325-1327, 1344-1346); they are built by reusing the same introspection pipeline on a fake placeholder function (main.py:114-118, completion.py:17-27, 64-97). If a version option was registered, _add_version_param_to_command appends the eager --version parameter the same way (main.py:1299-1311, wired at main.py:1328/1347).
  3. get_group_from_info (main.py:1426) recursively translates: each registered_command → get_command_from_info (main.py:1535), each registered_group → itself (main.py:1445-1453); an unnamed sub-app has its commands flattened into the parent (main.py:1454-1463). Layered DefaultPlaceholder values are resolved in solve_typer_info_defaults (main.py:1391-1423) and help text via the six-priority chain in solve_typer_info_help (main.py:1354-1388).
  4. For the callback function, get_params_convertors_ctx_param_name_from_function (main.py:1516) calls get_params_from_function (utils.py:107), which reads the signature and type hints and returns one ParamMeta (name, default, annotation) per parameter. A parameter annotated typer.Context is excluded from CLI parameters and remembered as context_param_name (main.py:1525-1527).
  5. Each ParamMeta is converted by get_click_param (main.py:1775): - required vs optional: an OptionInfo/ArgumentInfo default, ..., or no default (main.py:1784-1795); - annotation → Click type via get_click_type (main.py:1673-1768): str/int/float/bool/UUID/datetime directly, Path → TyperPath (models.py:666), file types → click.types.File, Enum/Literal → TyperChoice (_types.py:12); - bool options become flags with --name/--no-name declarations (main.py:1848-1862); list[T] → multiple, nargs=-1; tuple → composite type (main.py:1806-1840); - post-parsing value convertors are generated for Path/Enum/list/tuple (main.py:1580-1636); - result: a TyperOption (core.py:435) or TyperArgument (core.py:245) with an optional param callback wrapper (main.py:1940-1989).
  6. get_callback (main.py:1639) wraps the user function: at call time it applies the convertors, injects the current click.Context when requested (main.py:1658-1667), and forwards kwargs.

Phase 3 — runtime (parsing and invocation)

  1. The returned Click command is called with sys.argv[1:] → TyperCommand.main / TyperGroup.main (core.py:955/1188) → Typer's own _main (core.py:158), a copy of click.main that adds: shell-completion interception (core.py:182 → _typer_main_shell_completion, core.py:882 → completion.shell_complete, completion.py:105), Rich error formatting (core.py:203-212), and handling of typer.Exit/Abort (core.py:220-242).
  2. Command.make_context (_click/core.py:687) → Command.parse_args (_click/core.py:711) → _OptionParser.parse_args (_click/parser.py:275) tokenizes --option value, -x, and positional arguments.
  3. Parameters are processed eager-first (_click/core.py:718, iter_params_for_processing): Parameter.handle_parse_result (_click/core.py:1051) → consume_value (command line → env var → prompt; TyperOption prompts at core.py:627-671) → process_value (_click/core.py:988): type conversion, required-check, then the parameter's callback. Eager parameters (e.g. is_eager=True) run before the rest, so they can exit the program early — which is how --version prints and exits before the rest of the CLI is processed.
  4. Command.invoke (_click/core.py:729) calls the wrapped callback. For groups, TyperGroup.invoke (core.py:1088-1119) resolves the subcommand via resolve_command (core.py:1171, with "Did you mean …?" suggestions at core.py:1176-1185), builds a child context, and invokes the subcommand — i.e. the user's decorated function, now receiving fully typed, converted values.

Design decisions

What's good

  1. Two-phase design: declaration data vs Click construction. Decorators only record plain data (CommandInfo at main.py:922-939, TyperInfo at main.py:1139-1160); the Click object graph is built only when the app is invoked (main.py:1263 → main.py:1314). This keeps @app.command() free of Click side effects, lets sub-apps be defined in separate modules and composed with add_typer (main.py:945), and enables the single-command optimization (main.py:1330-1348) where a one-command app gets no Group wrapper at all.

  2. Default/DefaultPlaceholder sentinel with centralized resolution. Because None is a legitimate value (e.g. help=None), the sentinel (models.py:170-197) distinguishes "not set" from "explicitly None". Resolution is explicit and testable: solve_typer_info_defaults (main.py:1391-1423) walks the priority chain add_typer → sub-app @callback → sub-app Typer() for every field, and solve_typer_info_help (main.py:1354-1388) does the same for help text (explicit value → docstring inference). This makes nested-app semantics precise instead of implicit.

  3. Vendored Click plus thin subclassing, instead of monkey-patching. The runtime engine is a pinned vendored Click 8.3.1 (_click/__init__.py:2); Typer subclasses only what it needs (TyperCommand/TyperGroup at core.py:903/991, TyperOption/TyperArgument at core.py:245/435) and the single point where runtime behavior diverges from Click is _main (core.py:158), which layers in Rich error rendering and Exit/Abort handling. Even the exception hierarchy is wired through Typer (ClickException(TyperException), _click/exceptions.py:20), so one except_hook (main.py:63) pretty-prints both Typer and Click errors. Behavior is auditable in one tree, and the type-driven mapping from annotations to CLI stays a pure, unit-testable function (get_click_param, main.py:1775).

What I'd change

  1. The duplicated option surface in main.py and params.py. Typer.__init__ (main.py:164-577), Typer.callback (main.py:579-781), Typer.command (main.py:783-943) and Typer.add_typer (main.py:945-1161) each re-declare almost the same kwarg list (help, epilog, short_help, hidden, deprecated, options_metavar, context_settings, rich_help_panel, …), and params.py repeats the full parameter list four times across two @overload pairs plus the real implementations (params.py:16-1114). The same triplication exists in models.py (ParameterInfo/OptionInfo/ArgumentInfo, models.py:280-617). A single shared option spec (one dataclass per concern, forwarding **kwargs, with the Doc metadata defined once) would cut several thousand lines and prevent the four signatures drifting apart.

  2. Copy-pasted overrides of Click internals marked "Typer override". _main is a near-verbatim copy of click.main with branches added (core.py:158-242), and TyperOption.get_help_record is, in its own words, "Duplicate all of Click's logic only to modify a single line" (core.py:752-755). These copies silently drift from the vendored version and must be re-reconciled by hand on every vendored update. I'd keep vendored Click untouched and express Typer behavior through subclass hooks (e.g. override format_help/format_error on TyperCommand/TyperGroup, and upstream the bool-flag help tweak to Click), which is what rich_markup_mode already does via format_help (core.py:975-988). Related: the pretty-exception machinery attaches a custom attribute to the exception object and relies on sys.excepthook (main.py:1264-1280); catching around invoke inside _main would be more local, easier to test, and would not affect unrelated exceptions.

New feature: --version option helper

Typer.add_version_option() adds a --version flag to any app with one line:

app = typer.Typer()
app.add_version_option(version="1.2.3")  # or a callable returning the version

Implementation: Typer.add_version_option (typer/main.py:1163) stores a VersionOptionInfo (typer/models.py:648); get_command (typer/main.py:1314) appends an eager TyperOption built by get_version_param (typer/main.py:121) via _add_version_param_to_command (typer/main.py:1299), following the same pattern as the --install-completion options. The option is eager and expose_value=False, so --version works even when required arguments are missing, prints "<prog> <version>" (or a custom message/prog_name with %(prog)s/%(version)s placeholders), and exits 0 without invoking the command body. Registering it when the app already defines a --version parameter raises ValueError. See tests/test_version_option.py.
