DESIGN.md — URL-Shortener Service ("Strata Links")

Status: Draft for review · Author: Platform · Scope: global service at 50,000 writes/s and 1,000,000 reads/s

1. Summary

A globally distributed URL-shortening service that turns long URLs into short codes (e.g. st.example/Ab3xY9) and resolves them with HTTP redirects. Design targets are dominated by a 20:1 read/write ratio, heavy read caching (Zipfian popularity), and a very large logical key space. The core is a thin redirect path (edge cache → Redis hot set → global KV store) and a fat, fully asynchronous analytics/abuse side that never blocks a redirect.

Key decisions:

Area Decision
ID generation Centralized ID lease service (Flickr ticket-server style) + Feistel scramble so codes are unique, compact (8 chars, base62), and not enumerable
Store Multi-region, eventually consistent KV store (DynamoDB Global Tables / Cassandra DC-aware), partitioned by code prefix
Reads 3-tier cache (CDN edge → Redis → store); 99% edge hit-rate target; stale-while-revalidate
Writes Multi-home to nearest region, async cross-region replication, read-your-writes via global cache write-through
Analytics Edge click logs → Kafka → Flink rollups (ClickHouse) + Parquet archive; fully async, droppable under duress

SLOs: 99.99% availability (≈4.3 min/month, 52.6 min/year budget) for redirect path; p50 30 ms / p99 150 ms region-local redirect (edge hit), p99 300 ms cross-region; link creation p99 500 ms.

2. Requirements

2.1 Functional

  • FR1 Create a short link from a URL (authenticated API or anonymous web UI), with optional custom alias, expiry, and owner attribution.
  • FR2 Resolve a code to its target via HTTP redirect (301/302/307 configurable; default 302 + shared-cache TTL so the CDN caches but we still log at the edge).
  • FR3 Per-link analytics: clicks over time, referrers, countries, devices, unique visitors.
  • FR4 Owner operations: list/update/disable/delete own links; expiry/TTL.
  • FR5 Abuse tooling: blocklist, takedown, reports endpoint, quarantine.
  • FR6 Analytics query API for owners and dashboards.

2.2 Non-functional

Target
Write throughput 50,000/s sustained (design as sustained-peak; production mean will be lower, see §9)
Read throughput 1,000,000/s sustained
Availability 99.99% redirect path; 99.9% create + analytics
Latency §1 SLOs
Durability 11 nines for link metadata; at-least-once for click events (lossy allowed only under overload, by priority)
Consistency Eventual cross-region (seconds); read-your-writes within ~1 s
Data residency EU data stays in EU (link metadata + click events) per-region stores with global code-space
Security No SSRF surface in redirect path; API auth; tenant isolation

2.3 Non-goals (v1)

QR codes, link-in-bio pages, client-side SDKs, password-protected links (planned later), A/B link rotation.

3. API (v1)

Auth: API key header Authorization: StrataKey <key> for authenticated tenants; anonymous writes allowed but heavily rate-limited and default-expiring. All timestamps RFC 3339. JSON errors: {"error": {"code": "rate_limited|not_found|blocked|invalid_url", "message": ...}} with appropriate HTTP status. All writes accept Idempotency-Key.

Method & path Purpose Notes
POST /v1/links Create: {url, ttl?, alias?, tags?} → 201 {code, short_url, expires_at?} alias requires auth + ownership check
GET /v1/links/{code} Metadata (owner-only fields gated)
PATCH /v1/links/{code} Update target URL / TTL / status bump updated_at, invalidate caches
DELETE /v1/links/{code} Disable (tombstone; code not recycled in v1)
GET /v1/links?owner_id&cursor List, keyset pagination
GET /v1/analytics/{code}?window=24h\|7d\|90d&group=country\|device\|referrer\|minute Rollups from ClickHouse, max window depends on plan
POST /v1/reports Abuse report {code, reason} public
GET /{code} The redirect endpoint (root domain) 302 + Location, Cache-Control: public, s-maxage=86400, stale-while-revalidate=604800; no click counting at origin — counting at edge (§8)
robots.txt Disallow crawlers on code space

Why 302 + CDN-cached instead of 301: 301 lets browsers pin the mapping forever (we can't update targets or count), 302 without cache defeats scale. A shared (CDN) cache with s-maxage + edge-side logging gets both: long effective caching at the edge, correct counting, and revocation bounded by s-maxage (plus active cache-bust on takedown).

Redirect-path security: Strict-Transport-Security, no cookies on the redirect domain, X-Content-Type-Options.

  • LINKS (primary): row ≈ code 8 B + URL ~512 B + metadata ~130 B ≈ ~650 B/row. Partitioned by prefix2 (first 2 code chars = 62² = 3,844 logical partitions; Feistel scrambling keeps them uniform — §5).

  • CLICKS: event schema (Avro/Protobuf), never stored per-event in OLTP; flows to Kafka (§8).
  • Tombstones for deletes; codes are never recycled in v1 (avoids a class of security bugs; ID space is ample — §5).
  • Per-region stores; owner.region_home pins personal data where residency applies; global code namespace is replicated.

5. ID Generation

5.1 Space math

Base62 (0-9A-Za-z), n chars → 62^n codes:

Length Space Duration at 4.32 B new/day
6 5.68 × 10¹⁰ 5.68e10 / 4.32e9 ≈ 13 days ✗
7 3.52 × 10¹² ≈ 815 days ≈ 2.2 yr
8 2.18 × 10¹⁴ ≈ 50,542 days ≈ 138 yr ✓

(4.32 B/day = 50,000/s × 86,400 s — worst case §9.) Decision: 8-char base62.

5.2 Options considered

Option How Pros Cons
A. Central counter / lease ("ticket server", Flickr/KGS) App nodes lease blocks (e.g. 10k sequential IDs) from a tiny HA counter; encode counter → base62 No collisions, O(1), short codes; coordination is trivial: 5e4 writes/s ÷ 1e4 per lease = 5 leases/s fleet-wide; nodes buffer ≥10 min of IDs so counter outage is survivable Sequential ⇒ enumerable (abuse: crawl all links, guess others' codes) — fixed by Feistel (§5.3); tiny HA-critical dependency
B. Hash of URL 64-bit xxHash/Murmur of URL → base62 (11 chars: ⌈64/log₂62⌉) Free dedupe, zero coordination Long codes; birthday collisions: expected ≈ n²/2N; at n=10¹² links, N=2⁶⁴=1.8e19 → ≈ 2.7 × 10⁴ collisions to handle via retry+salt; can't hand out without a DB check anyway; ugly words in random strings
C. UUIDv7 / Snowflake 128-bit or 64-bit time-ordered ULID → base62 ≈ 20–22 chars Zero coordination, sortable, per-node safe Too long for a URL code; still enumerable; great for internal row IDs, wrong for the user-facing token
D. Random + DB check Draw random code, INSERT IF NOT EXISTS, retry Simple, no counter Write amplification on collisions, retry storms under hot keys, unpredictable write latency; fine only at toy scale
E. Per-shard counters with disjoint ranges Shard i issues IDs ≡ i mod S No central point Wastes space, uneven growth re-shards the space, still enumerable

Decision: A + Feistel scramble. Uniqueness and shortness from the counter; security from permutation; hash-index (B) kept only as the async dedupe mechanism.

5.3 Feistel scramble (enumerability fix)

Map sequential counter c ∈ [0, 62⁸) through a 4-round keyed Feistel network over two 4-char halves (62⁴ ≈ 1.5e7 each). Feistel is a bijection: distinct inputs ⇒ distinct outputs, so uniqueness is preserved while the output looks random. Keep the key in KMS; rotation requires a full re-issue (accepted in v1: keys rotated only for major incidents). The result is an 8-char, collision-free, non-enumerable code.

7. Caching

Three tiers, all serving the same value (code → URL + flags):

  1. CDN edge caches — absorb the Zipf head. Target ≥99% edge hit rate. s-maxage per-link: popular links 1 day, cold-created links 5 min (heuristic by rolling edge hit-rate). stale-while-revalidate = 7 days: a cold link evicted everywhere can still be served stale while the origin is re-validated — this is what lets a tiny origin ride a viral spike.
  2. Redis hot set (per region, cluster mode). Working-set sizing: assume 99% of reads hit ≤1.5 B popular/recent links (virality decays fast): 1.5e9 × ~700 B ≈ 1.05 TB → 12 nodes × 128 GB × 70% usable ≈ 1.07 TB. ✅
  3. KV store replicas in-region.

Policies and details:

  • Hit rate math: origin reads = (1 − 0.99) × 1e6 = 1e4 rps (§9).
  • Negative caching: not_found cached 60 s at Redis and 5 s at edge → random-guess flood costs ~zero origin reads.
  • Stampede control: per-key single-flight (request coalescing) in redirect service + jittered TTLs (±10%) to prevent synchronized expiry.
  • Invalidation: TTL-based everywhere; explicit purge (takedown, owner edit) via edge purge API + a per-link generation token in the value; blocked links short-circuit at edge policy.
  • Bloom filters per KV shard (~1e9 rows × 9.6 bits ≈ 1.2 GB) reject "code never existed" without touching disk.
  • Read-your-writes: the create path write-throughs to all regions' Redis (small volume: ≤5e4/s × 700 B ≈ 35 MB/s) and returns the short_url; a first click replicating cross-region is caught by the global cache even before KV replication (seconds) completes.

  • Rollup sizing: raw events to ClickHouse = 21.6 TB/day → columnar+zstd ≈ 8–10× → ~2.4 TB/day. Minute-grain rollups only for top-N (10 M) links, 24 h: 1e7 × 1440 × ~80 B ≈ 1.15 TB/day.   • Clicks are never counted at origin (that would mean 1e4/s DB-visible "counts", contention, and lost edge hits). The edge is the source of truth for counting; origin reconciles via generation mismatch only for security-sensitive takedowns.

9. Capacity Estimates (arithmetic)

Assumption: 50k writes/s and 1M reads/s are sustained-peak (worst case). Mean load is diurnal; sizing below buys 3× region-failover headroom on top.

Traffic volumes

Writes/day   = 50,000 × 86,400            = 4.32 × 10⁹   (4.32 B/day)
Writes/year  = 4.32e9 × 365               = 1.58 × 10¹²  (1.58 T links/yr)
Reads/day    = 1,000,000 × 86,400         = 8.64 × 10¹⁰  (86.4 B/day)
R:W ratio    = 1e6 / 5e4                  = 20 : 1

ID space → §5: 8 base62 chars = 2.18e14 ÷ 4.32e9/day ≈ 138 years. ✅

Origin load with 99% cache hit (edge+Redis combined)

Origin reads   = (1 - 0.99) × 1e6         = 10,000 rps
Origin total   = 10,000 + 50,000          = 60,000 rps

App tier (16-vCPU node ≈ 15,000 rps mixed): 60,000 / 15,000 = 4 nodes → deploy 36 (12/region × 3 regions) so one region's share reroutes: 60k/24 ≤ 15k/node×(12+2 spare). ✅ (≈2.6× headroom.)

Redis (990,000 rps hits, ~150k rps/node): 9.9e5 / 1.5e5 = 6.6 → 12 nodes (4/region), 1.05 TB hot set (§7). ✅

KV store

Row writes/s (RF3)      = 50,000 × 3      = 150,000   (≈20 nodes × 7.5k w/s + compaction slack)
Row size                ≈ 650 B
Bytes/day               = 4.32e9 × 650 B  = 2.81 TB/day
Per year                ≈ 1.02 PB
Live rows w/ 18-month mean TTL = 4.32e9 × 548 ≈ 2.37 × 10¹² rows
Storage RF3             ≈ 2.37e12 × 650 B × 3 ≈ 4.6 PB steady state

This is the hard cost of the requirement. At a realistic mean of 25% of peak, live rows ≈ 5.9e11 and footprint ≈ 1.2 PB. Mitigations: default 90-day expiry for anonymous links, dormant-link GC (no click in 24 mo ⇒ archive body to object storage, keep code → pointer row), cold tier. If managed DynamoDB: ~2.4 PB ≈ $600k/mo storage list — budget review flag; Cassandra ≈ 2,400 nodes @ 1 B rows/node×RF3. Flagged as open cost question.

Kafka: 250 MB/s raw; brokers receive ×RF3 = 750 MB/s + consumers 250 MB/s → ~12 brokers (60 MB/s sustained cap each, 50% util) per 3-region cluster. 7-day RF3 retention ≈ 450 TB (§8).

ClickHouse: ~2.4 TB/day + rollups (§8) → ≈30 nodes (24-vCPU, 10 TB NVMe, 90-day hot).

Egress: edge → client 1e6 × ~800 B ≈ 800 MB/s = 6.4 Gbps avg, ×3 peak ≈ 19 Gbps — CDN absorbs.

Flink: 20 cores → 180 vCPU across regions (§8).

Bloom filters (never-exists): 9.6 bits/key ⇒ 1e9-row shard ≈ 1.2 GB; 2.37e12 keys global ≈ 2.9 TB if unsharded — hence bloom lives per-shard in Redis/KV nodes, not one global filter.

10. Replication & Multi-Region

Topology: 3 regions (e.g. us-east, eu-central, ap-southeast), each a full stack (§12).

  • Writes: served by nearest region; row's home region = writer's owner.region_home (anonymous: nearest). Durable locally, then async cross-region replication (DynamoDB Global Tables / Cassandra DC-aware + per-DC RF2, cross-DC RF via async). Conflict policy per code key: LWW on updated_at — conflicts are effectively impossible (codes unique, updates rare and owner-scoped). No multi-writer merging needed.
  • Reads: local in-region replica always (never cross-region on the hot path). Cross-region staleness target p99 < 2 s for a new link to be visible everywhere; read-your-writes patched by global Redis write-through (§7) so the creator's first click always resolves.
  • Consistency trade-off, stated plainly: a brand-new link may 404 for a few seconds in far regions. Accepted (URL shorteners tolerate eventual consistency; the alternative — synchronous global quorum — adds 150–250 ms and cross-region availability coupling to every write, violating the write p99 budget).
  • Control plane is strongly consistent: blocklist, policy, ID leases run Raft in a single quorum (3–5 nodes spread across regions). Tiny volume, must never be wrong.
  • Residency: personal data (owner PII, ip_hash derived rows, EU-owned links if configured) stored in EU with only non-PII fields (code, url, status) globally replicated.
  • Failover: GSLB health-views drain a failed region; app/Redis/Kafka provisioned so any 2 regions carry 100% (§9 math). KV store continues serving writes in surviving regions; home-region writes for drained owners are accepted by the failover region with updated_at still monotonic (HLC clocks), so LWW stays sane.

11. Abuse Prevention

Threat model: spam mass-creation, phishing/malware links, click-fraud on analytics, enumeration of the code space, cache-penetration floods of random codes, brand-alias squatting.

Vector Controls
Mass creation Anonymous: 10 writes/hr/IP, links default-expire 30 d, no aliases. Keyed: tiered quotas, verified payment/phone for high tiers, anomaly monitoring on per-tenant rates
Phishing/malware Google Safe Browsing lookup on create + re-scan on redirect-policy push; heuristics (URL shortening chains, homoglyphs, lookalike domains); per-link velocity caps on creation from suspicious hosts; quarantine-then-review for risky-but-unconfirmed (interstitial page)
Enumeration Feistel IDs (§5.3) make crawl-what-exists impossible; miss floods are rate-limited (per-IP 100 distinct-code misses/min → challenge) + negative cache + bloom
Cache penetration Per-shard bloom + negative caching means random codes never reach disk
Click fraud Edge bot heuristics (UA, JS challenge optional, IP reputation feeds), unique-visitor estimation by salted daily ip_hash, dashboards show "verified" vs raw
Alias squatting Aliases auth-only, deny-list of reserved names, dispute/takedown workflow
Takedowns POST /v1/reports → auto-gate (Safe Browsing hits auto-block) + human queue; block = KV row status=blocked + edge policy push (<1 s) + cache purge; abuse email + documented SLA

13. Failure Modes & Degradation

# Failure Impact Mitigation / behavior
1 Redis cluster (partial) loss Hit rate drops, origin load ×10–100 Origin sized for 2× origin traffic (60k→120k rps); autoscale redirect fleet; p99 degrades, no outage
2 Total cache loss + stampede Thundering herd on KV Single-flight coalescing caps fan-out per key; shed via load-shedder, serve stale at edge (SWR covers most popular links anyway)
3 KV shard/partition down Writes to affected prefix fail RF + in-region failover; writes retry to replica (RF drops to RF1 temporarily — flagged); reads from global cache + other replicas; repair on restore
4 Region outage ⅓ capacity + all home-region writes there lost GSLB drains; 2 regions carry 100% (§9); home-region writes accepted elsewhere with HLC; analytics: Kafka regional spool rerouted by edge shippers

6 Kafka down / broker loss Click loss risk Edge local spool (GB-scale, hours of buffering), at-least-once replay, priority drop of low-value event classes under sustained loss; SLO: <0.1% click loss/yr
7 Code never existed (cache penetration / enumeration flood) Origin waste Bloom + negative cache + miss-rate limiting → bounded, cheap
8 Hot viral link beyond one edge PoP Single-key overload at one PoP Anycast spreads; L2 Redis + per-link s-maxage bump; edge serves stale indefinitely
9 Split brain / stale replica serving Wrong/missing code Fencing tokens + HLC; LWW; codes never recycled so "wrong code" can never mean "someone else's URL" — worst case is 404 until sync, never a misdirect (this is a deliberate design property)
10 Bad deploy p99/err burn, wrong redirects Canary per region, auto-rollback on SLO burn, blue/green instant revert; config changes behind flags with per-region kill switches
11 DNS provider outage Total unreachability 2 independent DNS providers, low TTL on apex only (edge IPs stable/anycast), status + client guidance
12 Takedown needed while cached Blocked content still served from edge Policy push + generation token short-circuits at edge (<1 s) independent of cache TTL; purge as second belt
13 Corruption / operator error Data loss Continuous KV export to object storage + PITR, quarterly restore drills, tombstone GC with 90-day quarantine

Explicit non-dependencies of the redirect path: ID service, Kafka, analytics, dedupe index, Safe Browsing (enforced at create + via pushed policy, not inline). The redirect path is only: edge, Redis, KV, DNS.
