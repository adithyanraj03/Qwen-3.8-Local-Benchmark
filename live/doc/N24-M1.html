URL Shortener Service — Design Document

  • Status: Draft v1
  • Scope: Global URL-shortening service ("s.example") sized for 50,000 writes/s and 1,000,000 reads/s (redirects) sustained, globally.
  • Companion artifacts: load model (sim), capacity dashboard spec, chaos test plan.

1. Overview

POST /v1/shorten creates a short code (https://s.example/Ab3xK9mQ); GET /s.example/{code} returns an HTTP 302 to the original URL. The read (redirect) path is the hot path — 20:1 vs writes — and must stay cheap, cacheable, and globally fast. The design optimizes for:

  • sub-30 ms p99 redirect latency from any served region,
  • zero coordination on the redirect hot path (no cross-region call, no lock),
  • a write path that is simple, idempotent, and safe under region failure.

1.1 SLOs

Metric Target
Redirect availability (global, all regions) 99.99% (≤ 52.6 min downtime/yr)
Redirect latency p50 < 10 ms, p99 < 30 ms, p999 < 100 ms (edge→response, same region)
Create (POST /v1/shorten) p50 < 25 ms, p99 < 100 ms
Write durability local commit ack < 50 ms p99; cross-region replication lag p99 < 5 s
Cross-region staleness (read of a just-created code) ≤ 5–30 s, with documented client mitigation (§8.5)
Cache hit rate (L2) ≥ 90% at steady state

1.2 Load assumptions

Constant Value
Writes 50,000/s → 4.32 × 10⁹/day (50,000 × 86,400) → 1.577 × 10¹²/yr
Reads (redirects) 1,000,000/s → 8.64 × 10¹⁰/day → 3.154 × 10¹²/yr
Read : write ratio 20 : 1
Burst design for 2× target (100 k writes/s, 2 M reads/s) for 15 min without SLO breach
Regions 8, each a full replica of the global dataset (identical fleet)
Per region 6,250 writes/s, 125,000 reads/s

2. Requirements

2.1 Functional

  • F1. Create a short link for an http(s) URL (≤ 2048 chars, strict syntax validation).
  • F2. Redirect short code → long URL via 302 (default) or 301 (opt-in, owner-controlled).
  • F3. Custom codes (owner-chosen, uniqueness + policy checks), ≤ 20 chars.
  • F4. Link management: list, update long URL, expire (TTL), disable, delete (soft), batch create (≤ 100/req), idempotent create.
  • F5. Per-link analytics: total clicks, clicks today, time series (hourly/daily), geo + UA class breakdowns; account-level rollups.
  • F6. Abuse controls: rate limiting, policy filtering, quarantine, takedown, audit log.
  • F7. Multi-region: create/resolve from any of 8 regions; reads survive any single-region loss with no global outage.

2.2 Non-functional

  • N1. 50 k writes/s, 1 M reads/s sustained (global); 2× burst.
  • N2. Redirect path: no distributed transaction, no cross-region round-trip on the happy path.
  • N3. Codes are globally unique with vanishingly small collision probability for ≥ 10 years at design load.
  • N4. Data: append-mostly; deletes are soft (30-day tombstone); retention of raw analytics per privacy policy.
  • N5. Privacy: no raw IPs stored in analytics; GDPR erasure cascade.
  • N6. Observability: per-region and per-code metrics, SLO dashboards, SLO-burn alerts.

Design choices embedded in the diagram:

  1. Identical regions, full dataset. Every region can serve 100% of reads. Failover is a DNS/anycast weight change, not a data migration.
  2. Redirect path is read-only and local. code → long_url is a pure KV lookup; no writes occur on a redirect, so the hot path never touches the write coordinator.
  3. Click analytics is fire-and-forget. Emits to Kafka are async, buffered locally, and never add latency to the redirect or block the write path.
  4. Counters live outside the row store. 1 M/s of INCRs on link rows would create hot rows; counters go through the stream (§10).

4.2 POST /v1/shorten

{
  "url": "https://example.com/very/long/path?x=1",
  "custom_code": "my-team-launch",   // optional, policy-checked
  "expires_in": 604800,              // optional, seconds
  "redirect_status": 302,            // 301 | 302, default 302
  "tags": ["launch"]
}
// headers
//   Idempotency-Key: 7f9c...        // optional; replays return the original result
//   X-Region-Pref: eu-west         // optional routing hint

// 201 response
{
  "id": "lnk_01J8ZK...",
  "code": "Ab3xK9mQ",
  "short_url": "https://s.example/Ab3xK9mQ",
  "long_url": "https://example.com/very/long/path?x=1",
  "created_at": "2026-10-10T09:00:00Z",
  "expires_at": null
}

Errors: 400 invalid input, 404 unknown id, 409 custom code taken/reserved, 415 unsupported scheme, 422 URL fails policy (private IP, malformed), 429 rate limited (with Retry-After and RateLimit-* headers, RFC 9603 style), 5xx only for true internal faults.

Idempotency: key → (request hash, result) for 24 h; mismatched hash on same key → 409.

4.3 GET /s.example/{code}

  • 200 never returned — always 301/302 with Location, or 404, 410 (expired), 429, 451 (quarantined by legal takedown).
  • Cache-Control: public, max-age=60 for 301s (edge-cacheable); public, max-age=5 for 302s (short edge grace; the authoritative cache is per-region L2).
  • Response headers: X-Region: <serving region>, X-Cache: HIT|MISS, X-Served-By: <edge|l1|l2|db>.
  • 404 handling: negative cache 5 s (see §7.4) to blunt code-guessing and replication-lag 404s.

5. Data Model

Storage: a DynamoDB/Cassandra-class wide-column store, one links table, code as partition key (uniform, no hot partitions). Row count grows at 4.32 B/day.

5.1 links

Column Type Notes
code string(8), PK base62, §6
long_url string ≤ 2048 avg ~300 B assumed in capacity math
owner_id uuid, nullable null = anonymous
created_at int64 (HLC ms) Hybrid Logical Clock — immune to clock skew
updated_at int64 (HLC ms) LWW for concurrent owner updates
expires_at int64, nullable evaluated at redirect time; expired → 410 (row kept for audit)
status u8 active disabled quarantined tombstoned
flags u16 custom_code private no_analytics legacy_redirect_301
url_sha sha256(32) dedupe + analytics join key

~400 B/row all-in (8 code + 300 URL + 40 metadata + ~50 key/index/record overhead). Click counters are deliberately not in this table — see §10.

5.2 Secondary tables

  • owner_links (owner_id, created_at DESC) → code — list API; written at create only.
  • url_index (owner_id, url_sha) → code[] — optional dedupe ("you already shortened this").
  • Tombstones (30 d) kept for audit + GDPR cascade, then compacted.

No secondary index is read on the redirect path — it is a single PK lookup by code.

5.3 Consistency

  • Within a region: strong consistency on the primary replica; reads of owner-managed objects can pin to primary.
  • Across regions: eventual, async (§8). Codes are unique by construction (§6), so cross-region write conflicts on the same key are near-impossible; concurrent owner updates to one code resolve via HLC LWW (owner-gated anyway).

6. ID Generation — Options and Trade-offs

6.1 The space arithmetic (why code length is a hard constraint)

Writes add 4.32 × 10⁹ new codes/day (50,000 × 86,400) and 1.577 × 10¹²/yr. For a base62 alphabet (62 chars), the space per code length and time-to-exhaustion at full load:

Length Space (62ⁿ) Days to exhaustion @ 50 k/s Fill at 1 yr Fill at 10 yr
6 5.68 × 10¹⁰ 5.68e10 / 5e4 = 1.14 × 10⁶ s ≈ 13.1 days 27,700% n/a
7 3.52 × 10¹² 3.52e12 / 4.32e9 = 815 days ≈ 2.2 yr 1.577e12 / 3.52e12 = 44.8% 448%
8 2.18 × 10¹⁴ 2.18e14 / 4.32e9 = 50,541 d ≈ 138 yr 0.72% 7.2%
9 1.35 × 10¹⁶ ≈ 790 yr 0.012% 0.12%

For pure-random codes with retry-on-collision, the expected number of draws per new code is 1 / (1 − p) where p ≈ n/S (fill fraction). At a 7-char space after 1 year (p ≈ 45%) that is ~1.81 draws/code on average — sustained ~50% extra unique-constraint writes and a fat tail on create latency. This kills 6-char outright and makes 7-char untenable beyond a few months.

Cost: a per-region coordination point; overflow if a region sustains > 2²⁶/3600 ≈ 18.6 k/s (3× average) — needs a spillover path.

6.3 Recommendation

Option B (random 8-char + retry) as the baseline, with Option E as the documented migration target if measurements show collision retries or storage-locality pain:

  1. Mint code = random(2⁴⁷-ish), encoded in base62[8] (fixed length, no leading-zero ambiguity: alphabet is the standard base62 set 0-9a-z).
  2. Write with a unique constraint; on the rare collision → mint again (≤ 3 attempts) and return 409 only on custom codes. Expected retry load: < 0.8% at year 10 (p ≈ 7.2%, expected draws 1.077).
  3. No central ID service. Any node in any region can mint; this is what makes the write path survivable and the design simple.
  4. Monitoring: track n/S fill fraction from create telemetry; alert at 30% fill; at 50% the runbook migrates new codes to 9-char (old codes keep working forever — codes are immutable identifiers; decoder accepts both lengths). At our load, 8-char is good for ≥ 10 years (7.2% fill).
  5. Custom codes: validated (3–20 chars, [A-Za-z0-9_-]), checked against reserved words, profanity/trademark lists, then the same unique-constraint write.

Why not 7-char: §6.1 arithmetic. Why not a counter: the enumerable-ID downsides (C) outweigh the 1-char saving, and a random 8-char costs us nothing on the hot read path.

7. Caching

7.1 Hierarchy (per region)

Layer Tech Size TTL Notes
L0 Edge/CDN per CDN policy 301: 60 s; 302: 5 s Caches the response for very hot codes; global, not per-region state
L1 in-process (e.g., Caffeine) 50k entries ≈ 20 MB 5 min, jittered Sub-microsecond hit; serves the redirect service's hottest keys
L2 Redis cluster ~100 M hot keys ≈ 40 GB 1 h ± 20% jitter The primary read cache; cluster-sharded, 1 replica per shard
L3 wide-column store (N=3) full dataset durable source of truth

Value stored per key: long_url + status + expires_at + redirect_status ≈ 350–400 B.

7.2 Working-set sizing

Assumption (validated against telemetry; Zipf-like click distributions are extremely skewed): 100 M keys serve ≥ 90% of all reads.

100,000,000 keys × 400 B = 40 GB per region   (fits a ~12-shard Redis cluster with headroom)

If measurement shows 90% actually spans ~1 B keys, L2 grows to ~400 GB — still one cluster; the miss-rate math below changes, not the architecture.

7.3 Miss-rate arithmetic

global reads               1,000,000/s
L1 hit (hottest ~50k)      ~2–5%          → 25–50k/s served from RAM, ~0.1 ms
L2 hit (assume 90% overall) 90%           → 900k/s served from Redis, ~1 ms
L2 miss                    10%            → 100,000/s to the store
per region (÷8)                                  12,500 PK reads/s
per store node (3 replicas)                      ≈ 4,200 reads/s each

4.2 k reads/s per node on a 10 k+ IOPS-class store is a comfort margin, and it also sizes the cache-down failure mode: if L2 fails region-wide, the store absorbs 12.5 k/s/region — ~3× the normal load — which it handles, at degraded p99 (see §12, FM-1).

7.4 Backfill, stampede, negative cache

  • Jittered TTL (±20%) and single-flight backfill: on L2 miss, one coroutine per code fetches from the store; concurrent requesters await it. Prevents viral-key TTL-expiry stampedes (FM-7).
  • Negative cache: 404/expired codes cached 5 s. Blunts (a) code-guessing/brute-force abuse and (b) cross-region 404s during the replication window for a just-created code (§8.5).
  • Invalidation (owner update/delete): local pub/sub → L2 DEL + L1 eviction (per-node, via a versioned invalidation message). TTL is the backstop; a lost invalidation heals within the TTL.
  • Hot-key guard: per-key local rate meter; a single code at 10 M/s still only costs one node's L1 (it's in RAM). Beyond a region's ~125 k/s fair share, L0/CDN absorbs the rest.

8. Replication & Multi-Region Strategy

8.1 Topology

8 regions; every region holds the full global dataset (write-accepted locally, replicated everywhere). No primary region, no geo-pinning of data.

8.2 Write flow

  1. POST /v1/shorten lands in the nearest region (edge pins by client location).
  2. Local: mint code → write links (local commit, N=3, quorum ack) → 201 to client. Ack is local-only by default (p99 < 50 ms, no cross-region call in the write path).
  3. Async fan-out: the region's WAL/CDC stream ships to the other 7 regions.
  4. Each receiving region applies to its local store (idempotent, key = code; conflict ≈ impossible, §5.3).

8.3 Replication bandwidth (shown)

writes/region          50,000 / 8            = 6,250/s
bytes per replicated row ≈ 400 B
per region egress      6,250 × 400 B × 7 peers = 17.5 MB/s ≈ 140 Mbps

140 Mbps/region is nothing on modern interconnect; cross-region replication is a latency problem, not a bandwidth one.

8.4 Consistency & RPO/RTO

  • Within region: strong (quorum read/write on links).
  • Across regions: eventual; target replication lag p99 < 5 s, alert at 2 s.
  • RPO: ≤ 5 s of unreplicated writes during a region loss — i.e., a link created in the failing region in its final seconds may not exist elsewhere. Mitigations:
  • Durable mode (paid tier, opt-in): ack only after 2 remote regions persist the row (adds ~1 RTT, ~20–60 ms; RPO → 0).
  • Client retry guidance: on 201 followed by cross-region 404s within 30 s, the creator's SDK retries the resolve with the X-Region hint.
  • RTO: region failover = DNS/anycast weight shift; any surviving region serves 100% of reads immediately, and writes immediately (writes are region-agnostic). RTO ≈ 30 s (mostly DNS/edge propagation).

8.5 The 5-second window (read of a just-created code from another region)

code created in us-east; reader 2 s later in eu-west may get 404. This is inherent to async replication and is mitigated, not eliminated:

  1. Negative cache is only 5 s (not longer), so the 404 self-heals fast.
  2. Creator SDK: POST /v1/shorten response carries X-Region: us-east; the SDK passes X-Region-Pref on the first resolve, or the edge re-checks the minting region once for codes whose create telemetry says age < 30 s (a small "recent codes" bloom in the edge, updated via the replication stream).
  3. Documented SLO: read-your-own-write is guaranteed within the minting region; cross-region within ~5–30 s.

9. Abuse Prevention

9.1 Edge controls (cheapest first)

  • Rate limiting: per-IP token bucket (10 rps, burst 30) on the public redirect endpoint; per-API-key (writes 100/min, reads 10 k/min); per-account daily create quota (default 10 k/day). Fast-fail 429 with Retry-After; no queuing (a flood must never build a backlog).
  • IP reputation / ASN policy: datacenter ranges get stricter buckets; known-bad ASN lists applied at the edge.
  • Edge cache for 404s (negative cache, §7.4) makes guessing codes cost the attacker an edge hop, not a store hop.

9.2 Create-time policy

  • Strict URL validation: http/https only; length ≤ 2048; RFC-3986 conformance; reject private/loopback/link-local destinations (SSRF guard, even though we never fetch the URL); reject obviously malformed percent-encoding.
  • Custom codes: reserved-word list (brand + protocol schemes), profanity filter, one custom code per account per hour; all custom codes pass a review queue if from new accounts.
  • Proof-of-work / JS challenge on creates from high-risk networks (datacenter IP + new account + unusual UA).
  • Duplicate detection: same (owner, url_sha) within 24 h → return the existing code (also a cost saver).

9.3 Runtime scoring & quarantine

  • Per-code risk score from the analytics stream (§10): click velocity anomalies (burst 100× baseline in 60 s), IP/geo concentration (one /24 doing 90% of clicks), UA distribution (bot fingerprint mass), click-to-create delay (instant same-IP clicks = fraud loop), and graph similarity to quarantined codes.
  • Actions by score: watch → throttled (per-IP cooldowns, CAPTCHA on click) → quarantined (451 with X-Reason: policy) → tombstoned (legal takedown, 410, audit-logged, cascade to analytics).
  • False-positive control: quarantine is reversible by owner appeal (self-serve) within 72 h; FP SLO < 0.1% of active codes, tracked weekly.

9.4 Click-fraud & integrity

  • We redirect, we never proxy or render the target — the service cannot be used to host content (malware, phishing payloads, HTML) or to launder traffic past a referrer. Location is the only payload.
  • Fraud does not affect redirect correctness (we never refuse a click based on analytics — abuse action is at the code level, after review), but analytics consumers get is_suspicious flags and per-IP+code dedupe windows for counting.

9.5 Governance

  • Takedown API with full audit log (actor, timestamp, code, reason, evidence ref).
  • Quarterly abuse reviews; model retrain data from quarantined + appealed codes.

  • /v1/links/{code} counters: ~5–10 s stale (batched INCRBY from 1 s windows). Documented as "approximate, delayed < 15 s".
  • Dashboard series: 1-min freshness; hourly/daily rollups final after 24 h (late events reprocessed).
  • Exactly-once-ish: Flink keyed by (code, ts_bucket, ip_hash) with bounded dedupe (a replayed click in the same second from the same source is not double-counted); end-to-end at-least-once with consumer-side idempotency.
  • The analytics pipeline is never in the critical path — Kafka down ⇒ events buffered on local disk (10 min bounded) ⇒ dropped only if overflow; redirects and creates are unaffected (FM-11).
  • GDPR: erasure of a link cascades: counters dropped, series tombstoned, raw events purged by url_sha (IP is already hashed per-day and never reversible).

11.2 Storage

growth/day   4.32e9 × 400 B        = 1.728 × 10¹² B ≈ 1.73 TB/day
growth/yr    1.728 × 10¹² × 365    ≈ 631 TB ≈ 0.63 PB   (global logical dataset)
physical/yr  0.63 PB × 3 replicas  ≈ 1.9 PB/region       (every region holds the full dataset)
3-yr horizon 1.9 PB × 3           ≈ 5.7 PB/region
fleet        5.7 PB ÷ 48 TB/node  = 119 nodes → plan 144/region (21% headroom)
global       144 × 8 regions      = 1,152 storage nodes

Cost lever (optional, phase 4): tiered replication — the 4 highest-traffic regions keep full copies; the other 4 keep a hot subset (~25% of keys ≈ 90% of reads, ~200 TB/yr each) and fall through cross-region for the tail. Cuts the storage fleet ~40–50% at the cost of a p99 tail for the ~10% cross-region reads; not needed for SLO, only for money.

11.5 Sanity checks

  • Store read load at 10% miss: 4.2 k reads/s/node (§7.3) — < 5% of a healthy node's capacity. ✔
  • Code space at year 10: 7.2% fill (§6.1) — < 1.1 expected draws/code. ✔
  • Replication: 140 Mbps/region — < 2% of a 10 GbE uplink. ✔
  • Worst-case cache-down: store takes 12.5 k reads/s/region (3× normal) — within capacity, p99 degrades (FM-1). ✔
  • Burst 2× (1.5 M reads/s global): 375 cores/region at ~80% — inside the burst budget; edge sheds the excess as 429 if the 2× is sustained > 15 min. ✔

FM-10 Object store / lake unavailable analytics freshness redirects/creates unaffected; Flink checkpoints buffer to Kafka (7 d retention) dashboards stale until restored; no SLO impact
FM-11 Kafka down (region) click events local-disk spill buffer (10 min bounded); events best-effort; overflow = drop + alert up to 10 min of analytics gap; zero impact on links
FM-12 Bad global config/secret push potential global outage staged push (canary region first, 15-min bake), versioned + one-command rollback (< 5 min); ID-space secrets are hour-keyed so a bad push can't corrupt already-minted codes ≤ 15 min canary exposure
FM-13 Store split-brain / partition (region isolated) region writes isolated region keeps serving reads; writes buffered WAL locally (bounded 5 min), replay on heal; client acks continue (local commit) cross-region lag until heal; no data divergence (HLC + code uniqueness)

Priority rule under load: correctness of existing links > replication > writes > analytics. Shed in that reverse order.

13. Rollout Plan

Assumes greenfield (no existing traffic to migrate; codes are new). Durations are calendar weeks; each phase has entry/exit gates.

Phase 0 — Design & prototype (weeks 1–4)

  • Reference architecture in 1 region; ID generator with collision test harness (§6.3); load model simulator reproducing 50 k W/s / 1 M R/s traffic shapes.
  • Exit: simulated SLOs met at 1×; row-size and working-set measurements (validate 400 B/row, 100 M hot keys).

Phase 1 — Private beta (weeks 5–8)

  • 1 region live; 50–100 internal/partner users; target 10 k reads/s sustained (1% of design).
  • Abuse controls active in watch-only mode; analytics v0 (raw events + counters only).
  • Exit: 2-week soak, p99 < 30 ms, zero data-integrity incidents, abuse watch-mode FP data collected.

Phase 2 — Public beta, multi-region (weeks 9–14)

  • 4 regions (2 Americas, 2 EMEA); replication live; full SLO dashboards; abuse scoring live (actions on); analytics v1 (counters + TSDB + dashboards).
  • Weekly chaos: storage node kill, Redis shard kill, Kafka broker kill, region-lag injection (5 s).
  • Exit: 100 k reads/s sustained (10% of design) with all SLOs green for 14 days; replication lag p99 < 5 s; FP rate < 0.1%.

Phase 3 — GA, full footprint (weeks 15–20)

  • 8 regions; durable mode enabled for paid tier; full abuse actions; takedown API + audit.
  • Load: ramp to 100% design load (50 k W/s, 1 M R/s) via shadow-traffic mirroring of partner traffic + synthetic harness, then 15-min 2× burst drill.
  • Exit (launch gate): SLOs met at 1× for 72 h; 2× burst absorbed; region-kill chaos with RTO < 30 s demonstrated; runbooks (FM-1..13) tabletop'd.

Phase 4 — Steady state (week 21+)

  • Quarterly: capacity review vs §11, working-set re-measurement, chaos including full-region failover, ID-space fill review.
  • Standing monitors: code-space fill (alert 30%, runbook at 50% → 9-char migration for new codes, §6.3); cache hit < 85% for 24 h; replication lag p99 > 2 s.
  • Cost optimization (optional): tiered replication for the 4 low-traffic regions (§11.2) once fleet > 1,000 storage nodes.

Rollback & safety properties

  • Per-region blue/green; rollback = traffic weight shift, no data migration.
  • The dataset is append-mostly and codes are immutable identifiers: any version rollback keeps all previously minted codes resolvable (decoders accept 8- and 9-char codes; schema is additive-only).
  • Feature-flag all new behavior (durable mode, 9-char minting, abuse actions) so each is independently killable in < 5 min (FM-12).

14. Open Questions

  1. 7-char pressure: product wants 6–7-char codes — requires Option E (partitioned counter) or accepting 7-char for a bounded campaign window with a hard 9-char fallback; needs product decision before Phase 1 freeze.
  2. Permanent (301) links: owner-requested 301s get 60 s edge caching (§4.3); do we allow 301 → 302 downgrade? (Currently: no, to keep edge semantics simple.)
  3. Tiered replication threshold: trigger at fleet cost or at p99 tail regression? Decide with first two capacity reviews.
  4. Multi-tenant isolation: are 50 k W/s from one customer acceptable on the shared store? (Currently yes — partition keys are uniform; revisit if a single customer exceeds ~5 M creates/day.)
