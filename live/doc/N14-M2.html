Typer Architecture

Typer is a type-hints-based CLI framework. Users declare commands as plain Python functions; Typer compiles those declarations into a Click command tree that parses the actual command line. It sits on top of a vendored copy of Click in typer/_click/ — Typer never imports the installed click package; everything is from . import _click (e.g. typer/core.py:16).

Main modules and dependencies

Layering, bottom to top:

_click/ (vendored Click)
   ↑
models · _types · _typing · exceptions · colors     (data + leaf utilities)
   ↑
utils (reflection) · params (Option/Argument) · _completion_shared
   ↑
core (TyperArgument/TyperOption/TyperCommand/TyperGroup, _main) · rich_utils
   ↑
main (Typer class + declaration→Click compiler) · completion · testing
   ↑
__init__ (public API) · cli (meta-CLI)

main.py is the only module that depends on both the runtime layer (core) and the declaration layer (models, utils, params); completion.py is the only other module that uses params/utils at runtime (to synthesize its own options), which keeps the runtime layer from knowing about user declarations.

Request flow: decorated function → parsed command line

Consider:

app = typer.Typer()

@app.command()
def main(name: Annotated[str, typer.Argument()] = "World"):
    print(f"Hello {name}")

app()  # e.g. `myapp Foo`

  1. Decoration (import time) — record, don't compile. Typer.command() (typer/main.py:753) wraps f in a decorator that appends a CommandInfo(callback=f, …) to app.registered_commands (typer/main.py:890-911). add_typer() and @app.callback() do the same with TyperInfo (typer/main.py:1108-1131, 728-749). No signature is inspected yet; the app object is a bag of metadata.

  2. Invocation. app() → Typer.__call__ (typer/main.py:1133-1154) installs the pretty traceback hook except_hook (typer/main.py:61-109) once, then calls get_command(self)(*args, **kwargs). Any user exception is re-raised after tagging it with a DeveloperExceptionConfig attribute (typer/main.py:1145-1153) so the hook knows how to render it.

  3. Compilation (first call only, per invocation). get_command() (typer/main.py:1173-1208) decides the shape: - callback registered, or sub-apps, or >1 command → get_group() → get_group_from_info() (typer/main.py:1283-1357), which recursively compiles every registered command and sub-app (a nameless add_typer is flattened into its parent, typer/main.py:1311-1320); - exactly one command → get_command_from_info() (typer/main.py:1392-1434).

Along the way: - solve_typer_info_defaults() (typer/main.py:1248-1280) resolves each DefaultPlaceholder (the "unset vs. explicit None" sentinel from typer/models.py:170-197) through an explicit priority chain: add_typer() value > @subapp.callback() value > typer.Typer() value > default; solve_typer_info_help() (typer/main.py:1211-1245) adds docstring fallback for help text. - For every callback, get_params_convertors_ctx_param_name_from_function() (typer/main.py:1373-1389) runs get_params_from_function() (typer/utils.py:107-186): inspect.signature(func, eval_str=True) + get_type_hints(), splits Annotated[X, OptionInfo|ArgumentInfo] (typer/utils.py:94-104), rejects mixed declaration styles with dedicated error types (typer/utils.py:22-92), folds default_factory into default for Click (typer/utils.py:175-176), and emits ParamMetas. - Each ParamMeta goes through get_click_param() (typer/main.py:1632-1794): decides option vs. argument (explicit Option/Argument info, or .../no-default ⇒ required argument, default value ⇒ option, typer/main.py:1639-1652), maps the Python annotation to a Click ParamType via get_click_type() (typer/main.py:1530-1625: click_type > parser > builtins — int/float with min/max → ranges, Path → TyperPath (typer/models.py:648), file shims → types.File, Enum/Literal → TyperChoice (typer/_types.py:12)), turns bool options into --flag/--no-flag pairs (typer/main.py:1705-1719), and returns a TyperOption/TyperArgument (subclasses of Click's Parameter, typer/core.py:435/245). Parameter callbacks are wrapped by get_param_callback() (typer/main.py:1797-1846), which infers which arguments are ctx/param/value from annotations or names. - The user function itself is wrapped by get_callback() (typer/main.py:1496-1527): it applies value convertors (Path → param_path_convertor, Enum → generate_enum_convertor, plus list/tuple variants, typer/main.py:1437-1493) and injects the current Context when a parameter is annotated with it. - If add_completion=True (default), the eager --install-completion/--show-completion options — declared as a real Python signature in typer/completion.py:64-97 and compiled through the same pipeline (typer/main.py:112-116) — are appended to the command's params (typer/main.py:1184-1186, 1202-1204).

The result is a ready TyperCommand or TyperGroup whose callback is the wrapped user function.

  1. Parsing. Command.main(args) → _main() (typer/core.py:158-242): args default to sys.argv[1:] (typer/core.py:170-171); a shell-completion instruction in the environment short-circuits everything via _main_shell_completion() (typer/core.py:882-900, dispatch in typer/completion.py:105-145); otherwise make_context() builds an _OptionParser from each parameter's add_to_parser() (typer/core.py:588-625 for options, 431-432 for arguments), parse_args consumes the argv, each ParamType.convert validates/coerces values (e.g. TyperPath.convert typer/models.py:696-735, TyperChoice.convert typer/_types.py:71-93), env vars fill gaps (TyperOption.resolve_envvar_value typer/core.py:686-703), prompts fire when configured (typer/core.py:705-728), and eager parameters are processed first (sorted at typer/_click/core.py:96) — which is how --version-style options exit before required options are demanded.

  2. Dispatch and exit. For groups, TyperGroup.invoke() (typer/core.py:1088-1119) resolves the subcommand via resolve_command() (typer/core.py:1171-1186, with typo suggestions via get_close_matches), builds the sub-context and invokes the subcommand's wrapped callback with the parsed values. Errors exit through _main()'s handlers (typer/core.py:198-242): ClickException → rich_utils.rich_format_error when rich is on (typer/core.py:206-212), Abort/Exit → clean exit codes; uncaught user exceptions propagate to Typer.__call__ and are rendered by except_hook (typer/main.py:61-109), which hides frames inside typer/ and typer/_click/.

Three design decisions that are good

  1. Two-phase design: declarative info objects, lazy compilation. The decorators only append CommandInfo/TyperInfo records (typer/main.py:890-911, 1108-1131); the Click tree is built only when the app is invoked (get_command, typer/main.py:1173). This is what makes sub-app composition via add_typer possible, and it forces an explicit, auditable default-resolution chain (solve_typer_info_defaults, typer/main.py:1248-1280, built on the DefaultPlaceholder sentinel, typer/models.py:170-197) instead of implicit Python default-value semantics. Import time stays side-effect-free.

  2. Subclass-and-override on a vendored Click, with marked divergence. TyperOption/TyperCommand/TyperGroup (typer/core.py:435, 903, 991) override exactly the methods where behavior diverges — help records (typer/core.py:752), flag declaration parsing (typer/core.py:547-586), subcommand resolution with suggestions (typer/core.py:1171-1186) — while battle-tested parsing/validation stays in Click. Every override is commented # Typer override (e.g. typer/core.py:346-349, 753-755), so the diff against upstream is reviewable. Keeping a vendored _click means the runtime is deterministic across Click releases.

  3. One reflection pipeline reused for user params and Typer's own options. get_params_from_function (typer/utils.py:107) plus get_click_param (typer/main.py:1632) is the single path from Python signature to Click parameter. Typer dogfoods it for its built-in --install-completion/--show-completion options, which are declared as an ordinary annotated function (typer/completion.py:64-97) and compiled at typer/main.py:112-116. Typer's own CLI is therefore subject to the same rules and validation errors (mixed-style detection, typer/utils.py:124-129) as user code — and the new add_version_option feature below follows the same pattern.

Two decisions I would change

  1. main.py is a ~2000-line god module. It mixes the public Typer class with its huge doc-annotated __init__ (typer/main.py:135-519), the declaration→Click compiler (typer/main.py:1163-1899), value convertors (typer/main.py:1437-1493), and run()/launch() (typer/main.py:1902-2022) — of which launch() is unrelated to CLI construction. I would split it into app.py (the Typer class), compile.py (info → Click), convertors.py, and a small launch.py, each with a narrow import surface. The current file makes the compiler the least testable part of the codebase despite it being its core.

  2. Copied-and-adapted Click code instead of patching the vendored copy. _main() is "originally copied from _click.main()" (typer/core.py:158-169), and TyperOption.get_help_record() "duplicates all of Click's logic only to modify a single line" (typer/core.py:752-755); TyperPath is "based originally on code from Click 8.3.1" (typer/models.py:648-650). Since the entire Click is vendored in typer/_click/, these could instead be small targeted patches or mixins into the vendored code — the codebase already uses that pattern for _typer_param_setup_autocompletion_compat (typer/core.py:45-82) and except_hook (typer/main.py:61). Copies drift from upstream (the # Ref: comments show individual Click PRs being backported by hand), doubling the maintenance cost on every re-vendoring.
