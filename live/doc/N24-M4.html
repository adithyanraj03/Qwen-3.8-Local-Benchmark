Design: Global URL-Shortener Service ("sh.rt")

Status: draft v1. Owner: infra/platform. Reviewers: SRE, security, data.

A URL-shortener that resolves https://sh.rt/<code> to a target URL, designed for a sustained peak of 50,000 writes/s and 1,000,000 reads/s worldwide, with per-link click analytics.

1. Requirements

Functional

  • F1 Create a short link from a long URL; optional custom alias, expiry, and per-customer domain.
  • F2 Resolve a short code with an HTTP redirect (301 when safe and cacheable, 302 when click accounting or unscanned).
  • F3 Delete/deactivate a link (resolution returns 410).
  • F4 Per-link click analytics: counts by time bucket, country, referrer class, device class; queryable via API and dashboard.
  • F5 Duplicate-URL dedup: same long URL + same owner returns the same code (best-effort).
  • F6 Bulk creation (up to 1,000 links per request).

Non-functional

# Requirement Target
N1 Write throughput 50,000 POST /shorten/s sustained peak
N2 Read throughput 1,000,000 redirects/s sustained peak
N3 Redirect latency p50 < 30 ms, p99 < 150 ms (edge hit); p99 < 300 ms (origin)
N4 Write latency p99 < 150 ms
N5 Availability (redirect path) 99.99% (~52 min/year error budget)
N6 Availability (write path) 99.9%
N7 Durability 11 nines; RPO < 1 s for link data
N8 Analytics freshness p95 < 60 s from click to dashboard
N9 Consistency Read-your-write for creator within its region (< 1 s); global convergence < 5 s
N10 Security Codes unguessable; links malware-scanned; abuse rate-limited

Non-goals

  • No interstitial pages or JS-based redirects (hurts latency and cacheability).
  • No full content proxying/archiving of target pages.
  • No real-time personalization of the redirect target (A/B routing is a future phase).
  • Input URLs capped at 4 KB; no FTP/gopher schemes.

2. High-Level Architecture

Three regions (us-east, eu-west, ap-southeast), each with edge PoPs, a stateless app fleet, a distributed cache, and a shard of the global key-value store. Writes are geo-partitioned; reads are served from the nearest region. Kafka + stream processing carry click and change events to an analytics store; nothing on the redirect path depends on analytics.

Key properties:

  • The redirect path is edge cache -> regional cache -> local KV replica. It depends on at most one datastore and no synchronous RPCs to other regions.
  • Analytics is fully asynchronous (Kafka). An analytics outage never affects redirects.
  • Each KV shard has exactly one write leader (in the owner's region); other regions apply the change log asynchronously.

3. API

JSON over HTTPS, versioned path prefix, API key auth for writes (Authorization: Bearer <key>). Reads are unauthenticated.

Create a short link

POST /v1/shorten
Idempotency-Key: <uuid>            (required for retries; 24 h window)
{
  "url": "https://example.com/very/long/path?a=1",
  "alias": "spring-sale",           (optional; 3-32 chars, [a-zA-Z0-9-])
  "expires_at": "2027-01-01T00:00:00Z",  (optional)
  "domain": "sh.rt",                (optional; customer domain)
  "metadata": {"campaign": "q4"}    (optional; opaque, <= 2 KB)
}

201 Created
{ "code": "aB3xZ9kQ", "short_url": "https://sh.rt/aB3xZ9kQ",
  "status": "pending_scan", "created_at": "..." }

400 invalid url | 403 domain not verified | 409 alias taken
413 url too long | 422 url on blocklist | 429 rate limited (Retry-After)

Resolve (hot path)

GET https://sh.rt/{code}

301 Moved Permanently   (scanned-clean link; Cache-Control: public, max-age=31536000)
302 Found               (unscanned, expiring, or accounting-required; no-store)
  Location: <target>
404 Not Found           (never existed; cached negatively 60 s)
410 Gone                (deleted or expired)

Management and stats

GET    /v1/links/{code}                 -> metadata + status
DELETE /v1/links/{code}                 -> tombstone (idempotent)
GET    /v1/links/{code}/stats?from=&to=&granularity=minute|hour|day
                        -> [{bucket, clicks, by_country{...}, by_referrer{...}}]
POST   /v1/shorten/bulk                 -> up to 1,000 links, per-item results

All mutating endpoints return X-RateLimit-Limit/Remaining/Reset. Idempotency keys make client retries safe against at-least-once delivery.

Storage layout:

  • links - the hot key-value store, sharded by hash(short_code) into 1,024 shards. Row is ~1 KB with overhead. Immutable after creation except status/expires_at transitions (small, idempotent, last-writer-wins).
  • url_dedup - secondary table sharded by hash(url_hash); conditional put ("insert if absent, else return existing"). Because it lives on a different shard than links, dedup is best-effort: a rare race yields two codes for one URL, which is acceptable.
  • Cold tier - links inactive for 18 months move to object storage; a cache miss that finds nothing locally consults an object-storage-backed resolver before returning 404 (negative cache absorbs the cost).
  • Accounts/API keys - separate small service (PostgreSQL); not on the redirect path.
  • Analytics - lives only in ClickHouse (see section 9), never in the KV store.

5. ID Generation - Options and Trade-offs

The code must be short, globally unique, unguessable, and cheap to mint at 50k/s.

Space arithmetic (base62 alphabet):

62^7  = 3.52e12 codes   -> exhausted in 3.52e12 / 4.32e9 = 815 days at peak
62^8  = 2.18e14 codes   -> 138 years at peak writes
Option Coordination Code length Collisions Enumerable by scrapers Dedup Ops complexity
A. Random base62 + unique check none 8 probabilistic, retry loop no separate hash index low
B. Central counter, base62-encoded 1 DB row, batched 6-8 none yes - leaks volume hash index low
C. Segment-allocated counter + format-preserving encryption (FPE) batched segments (0.5 txn/s global) 8 none no (permuted) hash index medium (key mgmt)
D. Snowflake-style 64-bit (ts+worker+seq) worker lease 11 none semi (time-ordered) hash index medium (clock risk)
E. Truncated hash of URL none 7 birthday collisions deterministic free medium (collision handling)

Notes on the arithmetic behind the weaknesses:

  • A: with 4.75e12 codes issued (5 years at average rate), collision probability per insert is 4.75e12 / 2.18e14 = 2.2% at 8 chars - tolerable retries, but at 7 chars the space itself dies in ~2-4 years. Also needs a conditional-write path anyway.
  • B: a plain counter hands scrapers a free enumeration of every link (/000001, /000002, ...) and leaks business volume.
  • D: 41-bit ms timestamp + 10-bit worker + 12-bit sequence = 4,096 IDs/ms/worker = 4.1M/s per worker (ample), but 2^63 needs 11 base62 chars - 40% longer URLs - and NTP jumps need monotonic guards.
  • E: dedup is free, but truncated hashes collide (birthday math as in A) and give up custom aliases' symmetry; scanning a hash of a known URL lets anyone re-mint your code.

Recommendation: Option C. App servers lease segments of 100,000 sequential IDs from a DB counter (UPDATE ... SET next = next + 100000 RETURNING), then encode FPE(counter) in base62 with AES-FF1 over the base62 alphabet.

Counter fetch rate = 50,000/s / 100,000 per lease = 0.5 txns/s globally  (trivial)
Local buffer at peak = 100,000 / 5,000 per-node-s = 20 s of write outage tolerated
                       (prefetch at 50% -> effectively invisible)
FPE cost             = ~100k encryptions/s per core -> < 1 core per write node

FPE turns the sequential counter into an unguessable-looking 8-char code with zero collisions. On total segment exhaustion (138+ years, or a key rotation), fall back to random-8 with conditional put. Custom aliases occupy the same namespace and are checked against the counter space with a conditional write.

6. Read Path and Caching

sequenceDiagram
  autonumber
  participant B as Browser
  participant E as Edge PoP cache
  participant C as Regional cache
  participant K as Local KV replica
  participant Q as Kafka

  B->>E: GET https://sh.rt/aB3xZ9kQ
  alt Edge hit, code pinned and 301 cached
    E-->>B: 301 + Location (p50 ~10 ms)
  else Edge miss
    E->>C: lookup code (singleflight-coalesced)
    alt Cache hit (~96%)
      C-->>E: mapping
    else Cache miss
      E->>K: quorum read (1 of 3)
      K-->>E: mapping
      E->>C: SET mapping, TTL 6 h +/- 25% jitter
    end
    E-->>B: 301 if scanned-clean, else 302 no-store
  end
  E--)Q: click event (async, local disk buffer on error)
  Note over Q: CDC + click events feed analytics, never the redirect path

Four tiers, each absorbing most of the traffic of the next:

  1. Browser/CDN cache: scanned-clean links answer with 301 + 1-year Cache-Control; repeat clicks from the same client never reach us.
  2. Edge PoP cache (our own, in ~40 PoPs): local LRU of the hottest codes, 301 served at the PoP. Viral "hot key" codes are pinned here with a cluster-wide broadcast so a single trending URL never concentrates on one shard.
  3. Regional distributed cache (Memcached-style, consistent hashing, ~24 TB RAM total): target 96% hit rate for traffic that misses the edge.
  4. Local KV replica: the remaining ~4% (peak 40k reads/s) hits the in-region replica, p99 < 15 ms.

Stampede and hot-key defenses:

  • Singleflight request coalescing at every tier: concurrent misses for one code trigger exactly one downstream read.
  • Probabilistic early expiration: refresh a entry slightly before TTL with probability rising as TTL approaches, instead of a synchronized expiry thundering herd.
  • Jittered TTLs (base 6 h for active links, +/- 25%).
  • Negative caching: 404s cached 60 s at edge; scanner-style enumeration attacks are absorbed by negative cache + per-IP rate limits (section 8).

Invalidation: link create/status-change events flow through CDC to Kafka; a consumer proactively warms or evicts regional caches within ~1 s. Deletes evict all tiers; edge entries carry a 60 s max staleness bound via short edge TTLs on pending_scan links (they resolve as 302 no-store until scanned, then flip to cacheable 301).

7. Replication and Multi-Region

Within a region: every KV shard has 3 replicas (same region, 3 AZs). Writes commit at quorum (2/3); reads at local quorum 1/3 for redirect (with read-repair).

Across regions: geo-partitioned write leadership.

  • Each shard's write leader lives in the owner's home region (by account registration region). Cross-region traffic for writes is proxied to the leader region (rare on the redirect path; writes only).
  • The change log (CDC) replicates asynchronously to the other regions: steady-state lag < 500 ms, RPO < 1 s.
  • Conflicts are structurally avoided: link rows are immutable; only status/expires_at mutate, those operations are idempotent and commutative, resolved last-writer-wins with per-region fencing tokens. The dedup index is per-region with async merge; a duplicate code pair after a partition heals by keeping the older and tombstoning the newer.

Why not strongly-consistent single-leader writes? A single global leader for 50k writes/s is feasible throughput-wise, but every write pays 90-250 ms cross-region RTT and the leader is a global blast radius. Geo-partitioning keeps writes local, and the workload tolerates eventual global reads (a link created in us-east is usually clicked first in us-east).

Read routing: DNS anycast/geo-DNS sends resolvers to the nearest region; a region serves reads entirely from its own replicas and caches, so cross-region dependency on the read path is zero in steady state.

Region failure: health-checked DNS fails traffic over in 60-120 s. Surviving regions absorb +50% load (fleet sized at 1.5x peak, section 10). Cache cold-start is mitigated by warming from the still-current change log and by origin rate-limits that ramp (see failure modes).

8. Abuse Prevention

Redirect path (reads):

  • Per-IP token bucket at the edge: 600 reads/min generous for NATs; burst 100. Exceed -> 429 + Retry-After, served at the edge without touching origin.
  • Per-code hot-key guard: a single code exceeding 50k reads/s at one PoP is pinned and served from memory; abusive repeat-clicking of one code is throttled per IP.
  • Random-code scanning: 404-heavy IPs ( > 100 misses/min) get a 5-minute shadow ban; negative cache already absorbs the storage cost.
  • Bot tagging for analytics: UA lists + heuristics mark bot clicks; they still redirect, but are excluded from stats.

Create path (writes):

  • Per-API-key tiers: free 10 writes/min, paid per plan; anonymous 5/min with CAPTCHA escalation. Enforced at the gateway with a distributed token bucket (Redis, per-key sharded).
  • Quotas and budgets: daily caps per account; hard per-tenant concurrency limits so one tenant cannot exhaust the write fleet.
  • Payload validation: URL scheme/host validation, 4 KB cap, IDN normalization, blocklist of known-malicious registrable domains (checked at write time, updated via config push).

Content safety (async, off the hot path):

  • New links from untrusted senders resolve as 302 no-store and are queued to the safety scanner (reputation + third-party malware feeds). blocked status propagates via CDC and evicts caches within ~1 s. Clean links flip to cacheable 301.
  • Reported/abused links enter a review queue; shortlinks to redirect chains > 3 hops are flagged.

9. Analytics Pipeline

Every edge resolution emits a click event (fire-and-forget, local disk buffer on Kafka unavailability) - the redirect never waits on it.

flowchart LR
  EDGE["Edge PoPs"] -- "click events ~600k/s avg" --> K[("Kafka")]
  CDC["KV change stream"] -- "link events" --> K
  K --> FL["Flink jobs - dedupe, bot filter, geo, sessionize"]
  FL -- "rollups" --> CH[("ClickHouse")]
  FL -- "1% raw sample" --> S3[("Object storage - 400 d")]
  K --> SC["Safety scanner"]
  SC -- "status updates" --> KV[("Sharded KV")]
  CH --> SAPI["Stats API"]
  CH --> DASH["Dashboards"]
  S3 -. "reprocessing / backfill" .-> FL
  • Event schema (~300 B): code, ts, ip_hash, country, referrer_class, device_class, status, edge_id, link_status. ip_hash is salted daily (privacy).
  • Stream jobs (Flink): dedupe by (edge_id, code, ip_hash, 10 s window), bot filter, GeoIP enrichment, then aggregate to clicks_min(code, minute) and clicks_hour(code, hour, country, referrer_class). Exactly-once via Kafka transactions; event-time watermarks tolerate 5 min edge buffering.
  • Storage (ClickHouse): clicks_min retained 14 days, clicks_hour 90 days, clicks_day(code, day, country, referrer_class) 3 years. 1% raw-event sample kept 400 days in object storage for reprocessing and schema evolution (Kappa-style replay from Kafka for the last 7 days, Lambda-style sample beyond).
  • Serving: Stats API queries ClickHouse; dashboards read the same tables. Freshness p95 < 60 s (Kafka lag alarm at 30 s).

Error budget: 99.99% = 52.6 min/year for redirects. Any burn > 10% of the monthly budget triggers a reliability review and feature freeze on the redirect path.

Phases (each with entry/exit gates; no phase starts with open P0s from the previous one):

  1. P0 - Single region, correct-not-fast (weeks 1-6). 8 KV shards, one region, Redis cache, synchronous scan, no analytics. Gate: functional API complete; chaos test kills a replica without errors; 1k writes/s sustained.
  2. P1 - Scale the write path (weeks 6-14). Shard to 1,024; segment+FPE ID service; Kafka CDC; idempotency keys. Gate: load test 15k writes/s, 300k reads/s at SLO; shard rebalancing drill with zero dropped redirects.
  3. P2 - Multi-region reads (quarter 2). Stand up eu-west, ap-southeast with replicas + caches; geo-DNS; edge PoP caches with hot-key pinning. Gate: 600k reads/s with 96% hit rate; region-drain drill passes with < 2% error spike.
  4. P3 - Active-active writes (quarter 3). Regional write leaders, fencing tokens, dedup heal job, cross-region proxied writes. Gate: 50k writes/s mixed-region load; partition-injection test shows convergence < 5 s and zero lost links.
  5. P4 - Analytics v2 + full ceiling (quarter 4). Flink exactly-once, ClickHouse rollups, stats API GA; sustained 50k/1M soak test; game days (cache burn-down, region loss, Kafka kill) each quarter. Gate: analytics freshness p95 < 60 s under full load; error budget burn < 20%/month.

Release mechanics throughout: stateless services deploy canary 1% -> 10% -> 100% per region with auto-rollback on p99/5xx deltas; schema changes are expand-migrate-contract; KV shard topology changes run behind a dual-read shadow for one week; every phase ships with a written rollback (config flag or DNS) exercised in staging before promotion.

13. Open Questions

  • Do we offer customer domains at GA (TLS automation cost) or start with sh.rt only?
  • Should 301 be default even for unscanned links (faster, but a blocked link can linger in browser caches up to the edge TTL)? Current answer: no - 302 until scanned.
  • Analytics retention beyond 3 years: object-storage Parquet export vs ClickHouse cold storage.
  • GDPR/CCPA: is ip_hash salted-daily sufficient for "personal data", or do we need per-tenant opt-out of geo enrichment?
