1. Overview and Goals

A global URL-shortening service: users submit a long URL and receive a short code (https://sho.rt/aB3xZ9). Resolving a short code issues an HTTP 302 redirect to the original URL. The service also records click analytics and exposes them via an API and dashboards.

The design is dominated by two facts:

  • Reads outnumber writes 20:1 (1M/s vs 50k/s), and reads are heavily skewed toward popular links. The system is therefore built around a deep, layered cache in front of a horizontally sharded write store.
  • The write rate is enormous (4.3 billion new links/day, see §11), which constrains ID-space sizing, storage growth, and analytics volume. Every section below shows the arithmetic that drives its choices.

Guiding principles: favor boring, horizontally scalable components; make the common path (cache-hit redirect) as short as possible; degrade gracefully rather than fail closed; keep click accounting out of the OLTP path.

2. Requirements

2.1 Functional

4. API Design

Short domain root path is the redirect surface; everything else lives under /v1 on the API domain (api.sho.rt) to avoid collisions with codes.

4.1 Create a link

{
  "url": "https://example.com/very/long/path?a=1",
  "custom_alias": "my-brand",      // optional
  "ttl_seconds": 86400,            // optional
  "domain": "sho.rt"               // optional, for vanity domains
}

201 Created
{
  "code": "aB3xZ9",
  "short_url": "https://sho.rt/aB3xZ9",
  "url": "https://example.com/very/long/path?a=1",
  "expires_at": "2026-11-15T00:00:00Z",
  "created_at": "2026-11-14T12:00:00Z"
}

400  invalid url / alias taken / url blocked   { "error": { "code": "alias_taken" } }
402  quota exceeded
429  rate limited + Retry-After

4.2 Resolve (redirect)

GET https://sho.rt/{code}
302 Found
  Location: <original url>
  Cache-Control: public, max-age=60      // popularity-tiered TTL, see §7.3
410 Gone        // expired or deleted
404 Not Found   // never existed (negative-cached)

4.3 Management and stats

GET    /v1/links/{code}                 metadata for owner
DELETE /v1/links/{code}                 soft delete
GET    /v1/links/{code}/stats?from=..&to=..&granularity=hour
GET    /v1/links?limit=50&cursor=..     list owner's links
GET    /v1/stats/top?window=7d          top links for owner

4.4 Conventions

  • Errors: RFC 7807-style JSON with stable machine-readable code values.
  • Rate-limit headers on every response: X-RateLimit-Limit/Remaining/Reset.
  • Idempotency: Idempotency-Key header on create; repeated keys within 24 h return the original result (stored in Redis, keyed by API key + idempotency key).
  • Pagination: opaque cursors, never offsets (the table is too large for OFFSET).
  • All timestamps UTC, ISO 8601.

5. Data Model

OLTP store: MySQL 8 (InnoDB), sharded by hash(code) % 16 (§8). Only what the hot path and CRUD need lives here — click counters are deliberately excluded to avoid write amplification (a counter in the row would add up to 1M updates/s of churn to a table that already takes 50k inserts/s).

-- Sharded across 16 logical shards; code is the PK so the redirect is a PK lookup.
CREATE TABLE links (
  code        CHAR(8)     NOT NULL,          -- base62, see §6
  domain      VARCHAR(63) NOT NULL DEFAULT 'sho.rt',
  url         VARCHAR(2048) NOT NULL,
  owner_key   BINARY(16)  NULL,              -- API key id; NULL = anonymous
  created_at  DATETIME(3) NOT NULL,
  expires_at  DATETIME(3) NULL,
  deleted_at  DATETIME(3) NULL,
  flags       SMALLINT UNSIGNED NOT NULL DEFAULT 0,  -- bit0 pending-scan, bit1 blocked, bit2 recycled
  PRIMARY KEY (domain, code),
  KEY idx_owner (owner_key, created_at),
  KEY idx_expiry (expires_at)                -- background reaper for TTL
);

-- Custom aliases must be globally unique; kept in a small, single-leader,
-- strongly consistent cluster so alias preemption is a serializable check.
CREATE TABLE aliases (
  domain   VARCHAR(63) NOT NULL,
  alias    VARCHAR(32) NOT NULL,
  shard    TINYINT     NOT NULL,            -- where the links row lives
  code     CHAR(8)     NOT NULL,
  owner_key BINARY(16) NOT NULL,
  PRIMARY KEY (domain, alias)
);

CREATE TABLE api_keys (
  key_id    BINARY(16) PRIMARY KEY,
  user_id   BINARY(16) NOT NULL,
  plan      VARCHAR(16) NOT NULL,           -- free | pro | enterprise
  secret_h  BINARY(32) NOT NULL,            -- HMAC of secret with KMS key
  quota_rps INT NOT NULL, quota_daily BIGINT NOT NULL,
  revoked_at DATETIME(3) NULL
);

CREATE TABLE blocklist (           -- replicated globally via control plane
  pattern_id BIGINT PRIMARY KEY,
  kind       ENUM('domain','url_hash','regex'),
  pattern    VARCHAR(255) NOT NULL,
  severity   TINYINT NOT NULL,
  source     VARCHAR(32) NOT NULL,
  updated_at DATETIME(3) NOT NULL
);

Other stores:

Store Contents Why
Redis (per region) code → url hot map, negative cache, rate-limit counters, idempotency keys latency
ClickHouse per-code rollups (1-min/hour/day), per-owner rollups, geo/referrer breakdowns cheap aggregations, stats API
Object storage (S3-compatible) raw click events as Parquet (90 d), daily DB snapshots, ID-bank audit log replay/backfill, durability
Kafka (per region) clicks.raw, clicks.clean, links.events decoupling, fan-out

Data lifecycle: links with no clicks for 18 months move to an archive table (same schema, cold storage, still resolvable via a slower path); raw click events are aggregated then dropped after 90 days; rollups are kept 2 years in ClickHouse, then yearly summaries to object storage.

6. ID Generation Options and Trade-offs

Requirements: globally unique, unguessable enough to prevent enumeration (sho.rt/000001 leaking volume), short (≤ 8 chars for usability), cheap to issue at 50k/s without a per-create coordination call.

Space arithmetic (base62 = 26+26+10 = 62 symbols), against the creation rate of 1.58×10¹² links/year (§11.1):

Length Space Exhaustion at 1.58×10¹²/yr
6 62⁶ = 5.68×10¹⁰ 35 days — unusable
7 62⁷ = 3.52×10¹² 2.2 years
8 62⁸ = 2.18×10¹⁴ 138 years

Conclusion: 8 characters, or 7 chars only with aggressive recycling (§6.5).

6.1 Option A — hash of the URL (truncated MD5/SHA-256 → base62)

  • ✅ Stateless, no coordination, natural dedup (same URL → same code).
  • ❌ Collisions require lookup-and-retry loops (unbounded worst case); truncated hashes weaken collision resistance (a 48-bit truncation has ~50% collision probability near √(2⁴⁸) ≈ 1.7×10⁷ links — far below our volume, so we'd need ≥ 56 bits ≈ 10 chars, defeating the purpose); no TTL/recycling control; dedup requires a lookup anyway (index on hash(url) = extra write cost).
  • Verdict: wrong tool for a high-entropy write stream. Useful only as a dedup hint for authenticated users.

6.2 Option B — UUIDv4 / UUIDv7, base62-encoded

  • ✅ Zero coordination, 122 bits of space, v7 is time-sortable.
  • ❌ 128 bits → 22 base62 chars: far too long for a shortener. Truncating to 8 chars (48 bits) reintroduces collisions: birthday bound √(2⁴⁸) ≈ 1.7×10⁷ — at 4.3×10⁹ inserts/day we'd collide constantly.
  • Verdict: rejected; the format wastes bits we don't need.

6.3 Option C — central counter + base62 (batch-leased)

A logical counter; API servers lease ranges (e.g. 10,000 values at a time) from the ID bank and serve them from memory.

  • ✅ Trivially unique, exactly 8 chars, near-zero coordination cost (50k/s ÷ 10k per lease = 5 leases/s to the bank), cheap to audit.
  • ❌ Sequential values leak creation volume to competitors (sho.rt/aB3xZ9 vs aB4yA0 on the same day ⇒ growth estimate); mitigated by per-lease random offset within the range and by interleaving shard-space bits; a crashed API node loses up to one lease (10k values — 0.000000005% of the space, irrelevant).
  • Verdict: recommended core mechanism.

6.4 Option D — Snowflake-style (timestamp | worker | sequence)

64 bits → 11 base62 chars.

  • ✅ No single hot row (worker IDs assigned by the bank), monotonic, embeds creation time (helps recycling and debugging).
  • ❌ 11 chars is too long unless we steal bits (e.g. 34-bit timestamp from a custom epoch + 16-bit worker + 14-bit seq = 64 bits → still 11 chars at 62⁶·⁸; packing to 48 bits gives only 14-bit sequence = 16k/worker/second — tight at 50k/s across many workers); clock skew between regions can duplicate IDs unless worker IDs are globally fenced.
  • Verdict: viable but strictly worse than C for our constraints.

6.5 Option E — pre-generated ID bank ("KGS" style) + recycling

The bank pre-generates random 8-char strings into a queue; API nodes pop batches. Randomness kills the volume-leak problem of C. Recycling: codes of links archived/inactive ≥ 18 months are re-queued for reuse (with a grace period and a recycled flag so old analytics can be disambiguated by time window).

  • ✅ Unguessable, exactly 8 chars, decouples write path from any DB hot row.
  • ❌ Generation is itself a throughput task (trivial offline); random IDs have worse DB locality (random PK inserts → page fragmentation; mitigated by batching and by the fact that we shard by hash anyway, so locality was never a thing).

Decision: Option C+E hybrid — the ID bank leases randomized batches (lease range of the counter, values emitted in random order with per-lease offset). 8-char base62. Recycling enabled after 18 months of inactivity, which extends the 138-year runway indefinitely. Custom aliases bypass the bank and are checked against the strongly consistent aliases table.

7. Caching

Four layers between the client and the DB; each exists to absorb a different slice of the 1M reads/s.

7.1 Layers

  1. Browser / HTTP cache: Cache-Control: public, max-age=60 on 302s (popularity-tiered: hot links 300 s, normal 60 s, cold 0 s). We use 302, not 301, so we keep counting clicks; the max-age is the knob that trades click fidelity for load.
  2. Edge PoP cache (CDN layer): code → url map + negative cache for 404s (TTL 1 h — codes are immutable once created; deletes propagate as a versioned tombstone push). Sized at ~5M entries × 1 KB ≈ 5 GB per PoP — fits in RAM on stock edge hardware.
  3. Regional Redis: read-through + write-through on create; ~50M entries × 1 KB ≈ 50 GB per region (3 shards × 32 GB nodes with replica). TTLs jittered ±20% to avoid synchronized expiry.
  4. In-process LRU on API nodes: 100k entries × 1 KB ≈ 100 MB; catches thundering-herd retries after a Redis failover.

7.2 Consistency

Codes are immutable (create-only semantics; "update" = new code), so caches never need invalidation on the happy path — only on delete/block, which is handled by pushing tombstones from links.events to edge and Redis. Stale redirects after a delete are bounded by the TTL (≤ 5 min) and are acceptable.

7.3 Stampede protection

  • Singleflight: concurrent misses for the same code on the same node share one downstream lookup.
  • Serve-stale: on Redis/DB error, edge serves expired entries up to 24 h with stale-if-error=86400.
  • Negative caching prevents a scan of bots hammering random codes from reaching the DB: 1M/s of junk codes costs the DB nothing.

7.4 Hit-rate budget (drives §11 sizing)

Assume Zipf-like traffic: top ~1% of active links carry ~50% of clicks. Targets: edge hit ≥ 90%, regional Redis hit ≥ 90% of edge misses, DB sees ≤ 1% of total reads. Sensitivity: if Redis hit rate drops to 70%, DB read load goes from 5k/s to 15k/s — still within replica capacity (§11.4), so the design degrades gracefully rather than cliff-edging.

8. Replication and Multi-Region Strategy

8.1 Topology

Three regions (us-east, eu-west, ap-southeast), each a full data plane. 16 DB shards; each shard's primary lives in one region (shards grouped 0–5, 6–10, 11–15), each primary has:

  • 1 semi-sync replica in another AZ of the same region (RPO 0 for the region),
  • 1 async replica in a second region (disaster tolerance, read traffic).

Reads are served by the nearest replica. Writes are routed to the shard primary's region.

8.2 Why not active-active multi-writer?

The OLTP rows have no CRDT-mergeable state except flags and deleted_at, but custom-alias uniqueness and ID issuance are global invariants. Multi-leader per shard would force conflict resolution on exactly those invariants for no benefit (writes are 5% of traffic and tolerate ~200 ms extra). So: single leader per shard, globally placed; multi-region for reads, DR, and locality of user-facing APIs.

8.3 Read staleness

Async cross-region replicas lag ~100–500 ms. A create in us-east followed immediately by a read in eu-west may miss. Mitigations: the create response includes the URL and instructs Cache-Control priming at the edge; the API client that created the link knows the mapping; on a local-replica miss for a code not in the negative cache, the resolver does a one-shot read against the primary region (a "read-your-writes" fallback, < 1% of traffic).

8.4 Write routing

hash(code) % 16 is computed at the edge/API from a shard map distributed by the control plane (versioned, so resharding is a coordinated cutover with dual routing). A create in the wrong region costs one extra WAN RTT (~80 ms) on a path with a 500 ms p99 budget — acceptable. Alternative considered: region-local ID spaces with a region prefix char (8 chars → 7 free chars per region = 62⁷ = 3.5×10¹² per region, still 2+ years combined) — rejected because it complicates recycling, alias uniqueness, and resharding for a saving of one RTT on 5% of requests.

8.5 Control plane

  • ID bank: 3-node Raft group (leader in us-east); leases batches of 10,000; at 50k/s that's 5 leases/s — trivial for Raft. Bank down ⇒ API nodes drain local buffers (each holds ≥ 2 leases ≈ 40 s of traffic at fair share) then create returns 503 with Retry-After (writes degrade; reads do not).
  • Config: shard map, feature flags, blocklist versions — pushed via a pub/sub channel, versioned, last-known-good kept on disk.
  • Failover: automated, control-plane-driven promotion of a same-region sync replica on primary loss (target < 30 s); fencing via Raft-leased write tokens.
  • DNS/GSLB: health-based steering with 30 s TTL on the API domain; the short-link domain is anycast to the edge, which is region-independent.

9. Abuse Prevention

The service is a public target for spam, link farms, and abuse of free tiers.

  • Rate limiting (two-tier): token bucket at the edge (per IP, per API key) with regional Redis as the shared counter; API-layer enforcement as backstop. Defaults: anonymous 10 creates/min (burst 20); free key 100/min; paid per plan. Resolve path: 600 req/s per IP before bot-class throttling.
  • Bot classification: UA + JS-challenge heuristics tag traffic; bot-class resolves are served from edge only and never trigger DB lookups.
  • URL safety: on create, synchronous check against the blocklist bloom filter (domain + URL-hash, < 1 ms); async deep scan (Safe Browsing + in-house classifier). Unverified links from low-reputation principals get flags=pending and are served through a lightweight interstitial or capped at 100 clicks/day until scanned.
  • Reputation scoring: per principal (API key / IP / ASN), updated from block rates and user reports; low reputation ⇒ stricter limits + longer verification.
  • Click fraud: analytics-side dedupe window (same code + /24 IP + UA class within 60 s counts once), bot filtering, and outlier caps (a single code getting > 100k clicks/min triggers a quarantine review, not a hard block — viral links are real).
  • Negative-cache poisoning: unknown-code 404s are cached per IP+code, not globally, so a scanner storm doesn't evict real entries.
  • Hard stops: global kill-switch flag (serve a static page for creates), per-region create throttle under overload (shed writes, keep reads — reads are the revenue and the user-visible promise).

10. Analytics Pipeline

Click events are produced at the edge (resolve) and by the API (create/delete), streamed regionally, aggregated, and served from ClickHouse.

flowchart LR
    subgraph prod["Producers"]
        POP["Edge PoP - click events"]
        API["API - create and lifecycle events"]
    end
    POP -->|"protobuf, batched 1s"| K1["Kafka topic clicks.raw"]
    API --> K2["Kafka topic links.events"]
    K1 --> FR["Flink - dedupe, bot and fraud filter"]
    K2 --> FR
    FR -->|"clean stream"| K3["Kafka topic clicks.clean"]
    K3 --> R1["Flink - 1-minute rollup"]
    K3 --> R2["Flink - hourly and daily rollup"]
    K3 -->|"Parquet, 90-day retention"| OS[("Object storage - raw archive")]
    R1 --> CH[("ClickHouse")]
    R2 --> CH
    CH --> ST["Stats API - cached counters"]
    CH --> DB2["Dashboards and alerting"]
    OS -->|"backfill replay"| R2
    MM["Kafka MirrorMaker"] -.->|"cross-region replication"| K3

Event schema (protobuf, ~100 B): code, ts, edge_id, ip_prefix (/24 v4, /48 v6, hashed), country, ua_class, referer_domain, status_code, request_id.

Processing guarantees: producers are at-least-once; Flink jobs are idempotent — rollups are keyed by (code, window_start, bucket) and merged with max/sum semantics, so replays don't double-count. Raw events in object storage are the source of truth for backfills (e.g. after a filter-logic bug: replay 90 days into a shadow table, diff, swap).

Serving: stats API reads 1-min rollups from ClickHouse through a 30 s Redis cache (F6 freshness ≤ 60 s is met by the 1-min window + 30 s cache). Top-link leaderboards are precomputed per owner per hour.

Freshness vs cost: 1M events/s ÷ 100k partitions… concretely: 3 regional Kafka clusters at 6 brokers, 24 partitions per topic, 1 MB/s per partition (100 MB/s total ÷ 100 partitions) — comfortable on NVMe brokers. Flink parallelism 32 per job, keyed state in RocksDB, checkpoint to S3 every 30 s.

11. Capacity Planning

All arithmetic below uses the sustained targets; bursts (N1/N2) are absorbed by the headroom factors shown.

11.1 Volumes

Writes:  50,000/s × 86,400 s/day            = 4.32 × 10⁹ links/day
         × 365                              ≈ 1.58 × 10¹² links/year
Reads:   1,000,000/s × 86,400               = 8.64 × 10¹⁰ redirects/day
         × 365                              ≈ 3.15 × 10¹³ redirects/year
Avg reads per link-year: 3.15×10¹³ / 1.58×10¹² ≈ 20   (average; Zipf means
popular links see 10³–10⁶× this — hence the cache design)

11.2 ID space

See §6 table: 8 chars = 2.18×10¹⁴ ≈ 138 years at this rate; with recycling, effectively unbounded.

11.3 OLTP storage

Record budget: code 8 B + domain ~10 B + url avg 200 B (cap 2 KB) + timestamps/flags/owner ~100 B + InnoDB page + secondary-index overhead ≈ 512 B/link.

Daily:  4.32 × 10⁹ × 512 B  ≈ 2.2 TB/day
Yearly: 2.2 TB × 365        ≈ 810 TB/year raw
Replication: × 3 copies     ≈ 2.4 PB/year
Compression (URLs compress ~3× with InnoDB/ZSTD): ≈ 800 TB/year effective
5-year hot+archive footprint: ~4 PB  → fine on NVMe + object-storage archive

11.4 Serving capacity

API tier. A resolve handler is ~1 ms CPU (JSON-free 302 + cache lookup); budget 5,000 resolves/s per 8-vCPU node (p99 headroom included):

1,000,000 / 5,000 = 200 nodes → +50% headroom = 300 nodes ≈ 100 per region

Write tier. Create = validation + blocklist check + 1 insert + 1 cache write ≈ 4 ms CPU → 2,000 creates/s per node:

50,000 / 2,000 = 25 nodes → +60% headroom = 40 nodes ≈ 13 per region

Database. Per-shard budget: 5,000 writes/s (small PK inserts, group commit on) and 10,000 reads/s on replicas:

Shards needed for writes: 50,000 / 5,000 = 10 → provision 16 (failover absorbs
  a lost shard: 50,000/15 = 3,333/s still under budget; resharding runway)
DB reads after cache tiers (§7.4): 1,000,000 × 5% × 10% = 5,000/s
  → 5,000 / 16 shards ≈ 310 reads/s per replica — trivial

Redis. 50 GB hot set (§7.1) per region → 3 shards × 32 GB nodes + replicas. Ops: 50k edge-miss GETs + 50k SETs + rate-limit counters ≈ 150k ops/s per region cluster — one Redis shard handles ~100k/s, so 3-way split is comfortable.

Kafka/analytics. 1M events/s × 100 B = 100 MB/s; 8.64 TB/day raw; 90-day retention = 778 TB raw → Parquet+snappy ~4:1 ≈ 195 TB archive. Rollups: assume 10% of daily links get clicks (4.3×10⁸) × 1,440 one-min windows × 48 B ≈ 30 TB/day raw rollup → ClickHouse compresses ~10:1 ≈ 3 TB/day; 2-year retention ≈ 2.2 PB → keep 1-min rollups 30 days (90 TB compressed), hourly 2 years (~1.5 TB), daily forever.

Bandwidth. Redirect response ≈ 1 KB: 1M × 1 KB = 1 GB/s egress, of which the edge serves ≥ 90% from PoPs; origin egress ≈ 100 MB/s spread over 3 regions. Click stream: 100 MB/s internal.

11.5 Latency budget (p99 resolve)

Edge hit:      DNS+TLS ~10 ms + lookup 1 ms + 302        ≈ 15 ms   ✅ ≤ 50 ms
Redis hit:     + WAN intra-region RTT ~2 ms + singleflight ≈ 30 ms  ✅
DB hit:        + PK lookup ~2 ms + replica lag handling   ≈ 60 ms   ✅
Cross-region fallback (§8.3): + 80 ms RTT                 ≈ 150 ms  ✅ ≤ 300 ms
Create:        validate 5 ms + lease amortized ~0 + insert+semi-sync commit 30 ms
               + regional fan-out async                  ≈ 50 ms, p99 500 ms ✅

12. Failure Modes and Mitigations

# Failure Detection Mitigation / behavior Blast radius
1 Regional Redis down Health checks, error rate API serves from in-process LRU, then DB replicas; edge stale-if-error 24 h; auto-failover to replica +30 ms p99 in region; no data loss

13. Rollout Plan

Each phase has an exit gate; nothing proceeds until the prior gate is green.

Phase 0 — Single-region MVP (weeks 1–6). One region, unsharded MySQL + primary/replica, single Redis, API + edge cache (CDN provider), counter-leased IDs (Option C), manual failover. Synthetic redirect canaries from 5 geos. Gate: 5k writes/s and 100k reads/s sustained, p99 within budget, restore-from- snapshot drill passed.

Phase 1 — Hardening + abuse controls (weeks 6–12). Rate limiting (edge + Redis), blocklist bloom + async scan pipeline, idempotency keys, negative caching, singleflight, kill-switches, dashboards + paging SLOs. Load-test to 2× target in staging with production-shaped traffic (Zipf replay from sampled logs). Gate: chaos drills (Redis kill, DB primary kill) with zero user-visible read errors; abuse drill (spam burst) doesn't move p99 > 10%.

Phase 2 — Sharding + analytics pipeline (weeks 12–20). Split MySQL into 16 shards (dual-write migration, shadow-read verification, cutover per shard); deploy regional Kafka + Flink rollups + ClickHouse; stats API GA. ID bank moves to Raft-backed service with batch leasing. Gate: migration drills show < 0.1% row diff; analytics freshness ≤ 60 s; 100k writes/s sustained.

Phase 3 — Multi-region (weeks 20–30). Deployment below becomes real: eu-west then ap-southeast, each added as (a) read-only replica region, (b) GSLB-served for reads, (c) shard-primary home for its shard group. Kafka MirrorMaker + cross-region async replicas live. Read-your-writes fallback shipped before step (c).

14. Open Questions

  1. 301 mode: enterprise users will ask for permanent redirects (better client perf, worse analytics). Proposal: opt-in per link, with click counting via edge-served redirect + Link: <beacon> header — needs a privacy review before GA.
  2. Dedup: should authenticated users get the same code for the same URL? Cheap win for API-heavy customers; requires a hash(url) secondary index (+~30% write cost). Deferred to Phase 4 behind a flag.
  3. Recycling policy: 18 months is a guess — needs measurement of the true click-decay curve after Phase 1 traffic; recycled links must never shadow a code with live analytics history in the same window.
  4. Custom-alias cluster: single Raft group is fine at ~1% of creates (500/s); revisit if vanity-domain programs push alias volume higher.
  5. Multi-tenancy: enterprise isolation (dedicated shard groups) is deliberately out of scope for v1; the shard map makes it feasible later.
